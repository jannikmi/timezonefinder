# Prototypes

Exploratory studies of the package's present design and of ideas for its future. Each prices options against what ships today, so a decision can be trusted, revisited or extended from a measurement that still describes the code. **A study's subject is what the package has now or might have next.** What it used to have may be named where that explains a choice, but no study covers it: once a study's subject is replaced, the study is deleted together with any dependency only it needed, after whatever stops a re-proposal has moved into the matching decision file. Git keeps the code.

**Nothing here ships.** `MANIFEST.in` excludes the directory from the sdist, no packaged module imports one, and CI never runs a study.

**One thing here is tested, and it is not the exploratory part.** `tests/test_query_stage_profile.py` imports `query_stage_profile` and asserts two invariants of its stage ladder — that no rung binds a *checked public* accessor the lookup does not call, and that a rung opens the candidates the lookup opens. Contributor memory quotes the shares that ladder decides, and a copy of the lookup drifts in ways no number reveals, so those two properties are gated rather than left to the next reader. It runs in the default `make test` selection and skips when the `proto` group is absent. Everything else in every script is deliberately untested.

The ruff *linter* and mypy skip this directory (`[tool.ruff.lint]` in `pyproject.toml`, and the mypy hook's exclude); `ruff format`, `pyupgrade` and the whitespace hooks still apply, so a study is formatted and syntax-checked but not held to the rules.

They are run by hand, against the data in the checkout, and each one records its conclusion in a `FINDINGS` block at the top of the file. Expect them to need adjustment before they run again.

| Script | What it studies, and what it found |
|---|---|
| `latlng_index_bench.py` | **The trade-offs between longitude/latitude-aligned index structures within the 400–800 KB index budget**: flat equal-angle grids, equal-area banded grids and grid trees, aligned with the ocean meridians and not, beside touch-inclusive controls. Each is compiled from the packaged boundaries and answers through the real `TimezoneFinder` in the shipped index's place, against a control of the shipped cells with its candidate lists re-ordered by the converter's own rule. Three choices carry the result and are worth keeping when the question is re-asked: cells computed from the integer coordinates the kernel reads, owning their north and east edges as the kernel's boundary convention does, so a zone across an aligned border is not a candidate; refinement only where borders are, reached by arithmetic rather than a search, which is where the grid tree beats flat grids; and a lookup unrolled per depth, since a generic loop over the levels lost to a flat grid. Shapes outside the budget are left out on purpose — above it the [index cap](../contributing/project/project-purpose-runtime-constraints-and-non-goals.md) refuses them, below it they give up selectivity the cap would pay for — and which grid tree configuration is best within it is `grid_tree_config_sweep.py`'s question. The verdict and the refused families are in the [aligned-index decisions](../contributing/improvements/decisions/longitude-latitude-aligned-index-decisions.md). |
| `grid_tree_config_sweep.py` | **Which grid tree configuration the shortcut index should ship**, as a hyperparameter search within the 800 KB cap: root sizes aligned with the 7.5° ocean meridians, one to three levels with a block side each, refining every multi-zone cell or selectively under byte budgets. Exact counts on any machine prune the space to a Pareto frontier; paired timing against the shipped cells on server hardware screens it, replicated runs and an incumbent ladder that keeps the smaller index when speed is level decide it, and a second machine on freshly drawn points confirms it. Its decision rule is fixed in the module docstring before any deciding run, and its stages hand each other JSON that refuses data it was not taken on. The verdict goes to the [aligned-index decisions](../contributing/improvements/decisions/longitude-latitude-aligned-index-decisions.md). |
| `hole_boundary_redundancy.py` | That **96.4% of hole rings are a verbatim copy of some zone's boundary polygon** (release 2026c), which is what holes being stored as references rests on — see the *Holes as Boundary References* section of `docs/data_format.rst`. Also that the holes matching nothing are not geometric outliers but are fully covered by other zones, so they are an *ordering* question; the zone-precedence engine explored for them was rejected, because making timezone answers depend on hand-maintained political configuration is a real accuracy liability for a case that needs no resolution at all. Reads the upstream GeoJSON, so re-running it against a new release re-verifies the assumption. |
| `hole_removal_impact.py` | That **hole polygons cannot be dropped**, which is the natural next step after the deduplication above and looks safe until measured. Rewrites the hole files of a mirrored data directory and diffs `timezone_at`: dropping only the holes with no boundary twin changes 159 of 6,048 hole-interior answers, dropping all of them changes 1,404 — wrongly (`Asia/Hebron` → `Asia/Jerusalem`, `America/Argentina/Cordoba` → `America/Asuncion`). The companion script's finding that every hole is fully *covered* by other zones is true and insufficient: coverage says the right zone is among the shortcut candidates, ordering decides whether it is reached first. Re-measured 2026-09-02 against the format-3 dataset; the reshaped shortcut index moved the totals ~18 % from the figures on issue #513 and the format-3 payload left every headline count identical, both leaving the conclusion untouched. |
| `hole_precedence_relation.py` | That **no ordering can make holes droppable**, which closed #513. Derives, from the geometry alone and without consulting the shortcut index, the zone precedence relation a hole-free lookup would need — 216 edges over 218 zones, every one of the 756 holes needing at least one — and finds **7 two-cycles**: second-order enclaves (Baarle, Nahwa inside Madha inside the UAE, the Hopi reservation inside the Navajo Nation) where each zone of a pair must precede the other. Precedence is a relation between zones and containment is a relation between rings, so nesting two levels deep maps opposite ring relations onto one zone pair; the Dubai/Muscat witnesses lie inside the *same hole*. The per-cell formulation the H3-independence decision forbids fails too — all seven pairs share a cell needing both orders. The size-derived rule proposed on the issue fails separately on 20 of 216 edges, systematically on the ocean zones. |
| `polygon_block_encoding.py` | That the boundary polygons should be stored in **blocks carrying their own latitude range and coordinate frame**, and that issue #449's delta+varint encodings should not be built. It measures the thing that proposal would have made worse — the long tail, where `on_land` runs p50 1.00 µs against p99 39.71 µs and query time correlates 0.92 with vertices tested but only 0.76 with candidate count, so the tail is one ray cast across a huge ring. Both #449 candidates decode *sequentially* in front of that ray cast; a per-block latitude range instead removes ~98 % of the edge tests, and a per-block coordinate frame reaches varint's size without the serial decode — the byte counts are finding 5's, and are stated only there, because the two copies had already drifted apart — by 2,528 B on the block-FOR row and 236 B on the varint one. Its correctness gate encodes 410 polygons and replays 1,463 real query pairs against the shipped kernel: 0 round-trip failures, 0 disagreements. It then settles wall clock too, which the work count alone could not: a paired order-alternated whole-query A/B gives −24 % on a random workload and −48 % on-land, 41 of 41 rounds, with the **median unchanged** — the filter costs nothing on the path that reads no geometry, and it cannot live at the numpy level, where it would cost 2.73 µs of dispatch per query. Its correctness gate caught that `HoleArray` subclasses `PolygonArray`, so a boundary-keyed index answered 6 of 5,000 points wrongly. The C extension — the tracked configuration, and the one thing this script could not settle — was measured when the index shipped: −20 % random and −42 % on-land on minima, 41 of 41 rounds, paired in one process. **Both halves have since shipped, so nothing here is live evidence for pending work.** The latitude index landed first — its ring-rotation section is gone and `scripts/block_index.py` owns that question — and the frame-of-reference payload landed as polygon layout 3, in the bit-packed `B = 128` form this script recommended. Its one stated open question, whether byte-aligned widths beat bit-packed ones, was answered against byte-aligned by that work and the answer is recorded in the script. |
| `query_stage_profile.py` | **Where a `timezone_at` query actually spends its time**, per stage, per acceleration backend and per coordinate access mode - taken with three instruments that fail differently (exact `line_profiler` counts scaled by an `ITIMER_REAL` sampler's time share, a prefix ladder, and the line profiler itself for ordering only), on which the batch API, shortcut ordering and the native candidate loop all rest. A unique-zone query is ~1 us of which no stage is geometry; an ambiguous one is ~10 us of which the polygon loop is ~73%; the two point-in-polygon kernels are within 15% of each other, so numba's edge is the FFI marshalling it avoids rather than a faster kernel. Three of its findings have since been acted on: the memory-mapped mode once spent 4.9 us per candidate polygon rebuilding a FlatBuffers accessor (now ~0.8 us, via a precomputed offset table); the shortcut lookup was a decoded dict (now a table read indexed by arithmetic); and the prologue it named as the addressable two-thirds of a unique query lost its larger half when the H3 cell computation became integer arithmetic. Its `FINDINGS` block leads with the re-take on the new index. |
| `dependents_analysis.py` | **Who uses timezonefinder** — not a design study but a repeatable survey, kept here because it informs the same decisions a compatibility promise or a deprecation rests on: how much of the ecosystem a break would reach, and whether that includes well-known organisations. GitHub offers no API for the "Used by" list, so it scrapes the dependents page, looks every repository up through GraphQL (stars, fork parent, archived, last push, owner type) and attributes owners to companies with a regex list kept in the script; the report lists every organisation owning a dependent for skimming, forks are excluded from the star ranking and a user's profile naming a company is reported as weak evidence only. Its first finding limits every other one: GitHub's page stops paging after roughly 2,000 entries whatever its headline count says, so only the most recently indexed dependents are reachable and a missing name is not evidence of absence. The scrape resumes from its own checkpoint, and the counts it prints are a snapshot that goes stale on its own. Standard library only — it needs a GitHub token (`gh auth token`), not the `proto` group. |
| `pytzwhere_headline_comparison.py` | **The headline improvements over the predecessor `pytzwhere`**, re-measured rather than quoted from the origin story: startup, peak and added RSS, cold-query and per-query latency on a uniform and an on-land sample, coverage, crashes and on-disk size, each package in its own process and `pytzwhere` in an isolated `uv` environment pinned to the last stack it runs on. This package is measured once per point-in-polygon path (numba, the C extension, pure Python), forced by hiding modules from the import system, and the paths must agree answer for answer. Its main finding is that numba carries no headline: a default install, which uses the C extension, adds ~30x less memory than `pytzwhere`, starts ~20x faster and answers the median query 8-12x faster, while the pure-Python fallback keeps the median but has a slower tail than `pytzwhere`. On-disk size is the one metric that regressed everywhere. Cited from `docs/alternatives.rst`, which states magnitudes only. |
