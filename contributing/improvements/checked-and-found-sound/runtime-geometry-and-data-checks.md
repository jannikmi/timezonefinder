# Runtime, geometry, and data checks

Do not re-raise these findings without new evidence.

- **Exception handling:** the broad `except Exception` in `MemoryCoordAccessor`/`FileCoordAccessor.__init__` cleans up partial state and re-raises; `utils.close_resource`'s suppression list is documented at length and includes `BufferError` on purpose; `TimezoneFinder.__del__` uses a two-tier handler that warns on the unexpected case; and `scripts/reporting.py`'s `main` catches `Exception` to print a traceback and return an exit code.

- **Resource lifetime and tool idioms:** `coord_accessors.py`'s bare `open()` (Ruff `SIM115`) deliberately creates a handle that outlives the call and is closed by `cleanup()`; the `profile` name probes in `scripts/hex_utils.py` and `scripts/shortcuts.py` (Ruff `B018`) are the standard `line_profiler` idiom; `scripts/measure_memory.py`'s `subprocess.run` without `check=` (Ruff `PLW1510`) inspects `returncode` and raises with the child's output; and `np_binary_helpers.py`'s six near-identical `get_*_path` helpers preserve six importable, singly declared path names rather than one string-keyed lookup.

- **Workflows and global facade:** `.github/workflows/benchmark.yml`, `benchmark-comment.yml`, `check_data_updates.yml`, and `release_data_update.yml` were read in full and yielded nothing beyond version drift that is now guarded. `timezonefinder/global_functions.py`'s module-level `TF_INSTANCE` and `global` statement (Ruff `PLW0603`) are deliberately documented as not thread-safe, with per-thread instances as the alternative. `scripts/hex_utils.py`'s antimeridian and pole clipping in `get_corrected_hex_boundaries` is covered by `tests/hex_utils_test.py`.

- **Data integrity and package boundaries:** the general directory validators live in private `timezonefinder/_data_integrity.py` so the installed CLI can call them; `scripts/data_integrity.py` retains only the packaged-upstream deduplication expectation that would reject valid custom data. Their `PolygonArray`/`HoleArray` instances release accessors through `__del__`. `packages/timezonefinder-data/timezonefinder_data/__init__.py` and `scripts/data_releases.py` were read in full and found sound. `timezonefinder/zone_names.py` deliberately lets `read_zone_names` take a default path while requiring one for `write_zone_names`, because defaulting the write side to `DEFAULT_DATA_DIR` could rewrite the installed dataset in `site-packages`.

- **The blocked point-in-polygon kernel's per-call and per-edge overheads are both closed by polygon layout 3** — checked 2026-09-05, and neither half is worth re-raising.

  * *Skipping the block index for a single-block ring buys nothing reachable.* 29.7 % of boundary polygons fit in one block, and for those the latitude filter can never reject anything, since every caller has already rejected the point against the ring's bounding box and a single block's latitude range *is* that box's. The route out was for `PolygonArray.pip` to call the unblocked kernel when a ring owns one block. There is none a packed ring can reach: `inside_polygon_int` and `pt_in_poly_python` read an unpacked `int32` coordinate array, which a packed ring only produces through `decode_ring` — a full ring decode per test, to save one block-range comparison measured at tens of nanoseconds (`small` 537 ns clang / 818 ns numba against `medium` 567 / 891).
  * *The bounding-box precondition that makes the filter redundant holds on two routes*, which is the part a future change could break. The hole loop goes through `PolygonArray.pip_with_bbox_check`, which does both steps; the boundary path does not — `TimezoneFinder.inside_of_polygon` calls `outside_bbox` itself and then `PolygonArray.pip` directly, and is reached from `timezone_at` as well as `certain_timezone_at`. A caller reaching `pip` without a bounding-box rejection would make a single block's filter genuinely selective.
  * *The per-edge overhead — once measured at ~48 % per scanned edge on clang and ~96 % on numba — is already implemented.* Those figures were taken on the layout 2 kernel and named a per-edge wrap test and a recomputed latitude comparison. Layout 3 has neither: a block stores its bridging vertex, so the loop runs over the block's own `n` edges with no wrap-around case, and both kernels carry the comparison with `y1 = y2; y_gt_y1 = y_gt_y2`. See `inside_polygon_packed_int` and `pt_in_poly_packed`, whose docstrings state the no-wrap property as a property of the layout.
  * *What generalises:* a per-edge or per-call overhead is a property of a kernel, not of a query path, so a format change invalidates it. These figures were read for eleven days as though they described the code. Re-read such a finding against the current kernel **before ranking it**, not before implementing it — otherwise it holds a rank that costs every later pass the reading it takes to find there is nothing to do.

- **A failed certainty probe does not by itself prove a shortcut omission.** `certain_timezone_at()` tests every candidate but the point-in-polygon kernel has no promised side for a point exactly on a stored boundary. At the exact South Pole, and at border offsets smaller than the package's coordinate grid, an exhaustive scan can find no containing packaged polygon either. Diagnose an index omission only when exhaustive point-in-polygon testing finds a containing polygon absent from the cell's candidates; `None` alone establishes only that no candidate contained the quantized point.
