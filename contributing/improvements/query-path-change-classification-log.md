# Query-path change-classification log

This log classifies changes since the anchor in the [query performance measurement baseline](query-performance-measurement-baseline.md), so later passes do not have to re-derive whether the recorded denominators still apply.

The dated entries are kept for their generalisable half, which is what makes them worth more than the bookkeeping they were written for; add new ones above the oldest as changes land. The 2026-08 entries sit *before* the declared anchor and bear on freshness only through the rules they state; the 2026-09 ones sit after it, as does everything named in the paragraph below.

**The anchor itself is stale, and the freshness command names a different commit from the one the baseline declares.** Established 2026-09-05 by a discovery round. The [baseline](query-performance-measurement-baseline.md) states its anchor as `6adf161` and then hands out a freshness diff against `e1c3e15`, which it lists two sentences later as a *superseded* anchor — so the command reports non-empty whatever the tree looks like, and a pass that runs it learns nothing. Against the declared anchor the diff is non-empty too: 17 runtime files, 1,740 insertions, over six commits (`7c06d0c` the frame-of-reference payload, `82703f2` the lazy public surface, `95741be` the ocean prefix check and batch land lookup, `64aa293`, `d64d38a`, `cac02a1`). The frame-of-reference payload is the one that matters and the baseline's prose already describes its effect, so the *narrative* is current and the *operand* is not. Re-anchoring is a measurement pass: it needs [PROF-1](items/data-pipeline-and-developer-tooling/prof-1-the-stage-ladder-measures-the-checked-public-accessors.md) taken first, or the ladder it re-records is the one with two rungs bound to the wrong accessors.

- **2026-09-06, `njit` coming off the three scalar helpers, and the candidate loop's zone id gather deleted: not inert, and the two backends differ by design.** `is_valid_lat`, `is_valid_lng` and `coord2int` are plain Python functions in `timezonefinder/utils.py` now, and `_zone_id_among` reads the one zone id it needs instead of gathering every candidate's. It removes a **count**: two `njit` dispatches per query and two more on an ambiguous one, plus one numpy call per ambiguous query. Paired inside one process, arms alternated, 25 rounds a side, 2,500 fixture points, clang then numba: random **-4.8 / -12.3 %**, on_land -7.7 / -13.0 %, ambiguous -15.7 / -16.6 %, 20-25 of 25 rounds; unique **+0.8 % (12/25) clang, -8.0 % (23/25) numba**. **The generalisable half:** removing a dispatch is worth nothing on the configuration that never paid for it. Without numba `njit` is a no-op, so a unique query executes the same statements and reads neutral - the estimators straddle there (+0.8 % min, -0.8 % median) and a null A/B of the harness against itself puts its band at ±1 %. `validate_coordinates` fell 270 -> 212 ns on numba and stayed at 211 on clang: falling *to* the untouched backend's figure rather than below it is the signature of a dispatch removal, and distinguishes it from making the work cheaper. Inlining the helpers at their call sites was measured and rejected as a design - ~40 ns more for a second definition of where the world ends. `FINDINGS` re-taken on both backends; **the anchor was not moved**, following the entry below.
- **2026-09-05, the hole ids of a candidate polygon looked up without an exception: real on the ambiguous stratum, and at the edge of what this machine resolves.** What it removes is a **count**, which is the durable half: **0.498 raised-and-caught `KeyError`s and 0.779 generator objects per ambiguous query** over the committed fixtures, plus the 0.498 `in_any_polygon` calls that iterated nothing - 1,225 of the 1,322 packaged boundary polygons own no hole, and the majority path used to build a generator, enter it, raise, catch and return to establish that. Per hole-less candidate, 160 ns -> 88 ns. Paired inside one process with `_hole_ids_of` and `inside_of_polygon` rebound to the generator form, arms alternated round by round, 41 rounds a side, 2,000 fixture points: ambiguous **-4.0 % min / -0.8 % median clang (25/41)** and **-4.7 % / -4.1 % numba (33/41)**, on_land -2.0 / -5.3 % and -1.7 / -1.5 %, random -1.1 / -1.1 % and -1.7 / -0.2 %, unique +0.2 / +1.1 % and +0.4 / +0.2 % with the estimators straddling, which is the internal control. **Read it as order 2-4 % of an ambiguous query and ~1 % of a mixed wall clock, and do not quote a second decimal**: the clang estimators disagree on the median. **The methodological half, and the reason this is recorded rather than just fixed:** the entry that proposed it predicted -4.9 % from a prototype that compared a *subclass instance* against a base instance, and rebinding one method on one instance reads lower - two live finders differ in heap layout and cache residency, not only in the code under test. A prototype that builds a second object is measuring the second object too; rebind instead.
- **2026-09-05, the candidate loop's bounding-box columns and vertex counts read through buffer views: not inert, and the largest single move on the ambiguous stratum since the frame-of-reference payload.** What it removes is a **count**: four numpy 0-d scalar extractions per candidate in `outside_bbox`, one per point-in-polygon call for the vertex count, and one per hole resolution in `HoleArray._resolve` - which over the committed fixtures is ~4.2 + 0.78 + a hole's worth per ambiguous query, and zero on the unique-shortcut stratum, which never enters the loop. Paired inside one process with the views rebound to numpy indexing, arms alternated round by round, 25 rounds a side, 2,000 fixture points, answers asserted equal every round: ambiguous **-11.3 % clang / -11.0 % numba** (25/25 and 23/25 rounds), on_land -5.6 / -5.9 %, random -4.8 / -4.7 %, unique -0.2 / +1.0 % with the estimators straddling, which is the internal control. The side traded away is construction heap and it was measured rather than argued: **+4.4 KiB**, against +233 KiB the `.tolist()` form used by `block_offsets` would have cost for the same columns. **The generalisable half:** a `memoryview` over an already-loaded array indexes to a Python `int`, accepts a numpy integer as the index, and copies nothing - so on a hot loop it buys what a `list[int]` conversion buys without the second copy of the data, and it is the form to reach for whenever a per-candidate or per-point loop reads a stored column. What it needs is native byte order, which `np.load` gives wherever the packaged little-endian binaries are already assumed. The profiler's `FINDINGS` were re-taken on both backends in the tracked mapped mode in the same pull request; the **anchor was not moved**, because it is already stale by six commits (see below) and re-anchoring wholesale belongs to the pass that repairs the ladder.
- **2026-09-03, the coordinate bounds moving into `configs.py`.** `validate_coordinates` compared against `MIN_*` / `MAX_*` globals instead of literals. Three forms rotated round by round, min/median ns per whole call - literals **244/249**, `MIN_LAT_VAL <= lat <= MAX_LAT_VAL` **250/253**, `-MAX_LAT_VAL <= lat <= MAX_LAT_VAL` **295/299**. **The generalisable half, and the whole of what this entry is still for:** on a specialising interpreter a module global is nearly free to read and `UNARY_NEGATIVE` is not, so a constant a hot path compares against is declared in the sign it is used in. The stage figures it quoted are superseded by the 2026-09-06 entry, which rewrote that stage.
- **2026-09-03, the zone position table read once per finder, and `certain_timezone_at` sharing the shortcut enumeration: both inert for the ladder.** Neither is on the profiled `timezone_at` path: `_iter_boundary_ids_of_zone` is reached only from `certain_timezone_at` and `get_geometry`, and the enumeration `certain_timezone_at` now shares was already what it inlined. `AbstractTimezoneFinder.__init__` gains one `None` assignment, which is the whole of what construction pays for the lazy read. What the first change removes is a **count**: one file open, header parse and mapping per call, for a 890-byte immutable array, down to one read per finder - measured on the committed fixtures at 48.1 ms -> 2.90 ms (on land) and 55.2 ms -> 3.57 ms (random) per 500 `certain_timezone_at` calls, 21 of 21 rounds to the cached form.

- **2026-08-23, the negative-id guard on the public id-taking methods: inert.** It adds a check to four public methods and moves the internal callers onto private accessors with identical bodies, so the query path executes the same number of calls over the same statements. Nothing in the `zone name` block or the ladder above it changed.
- **2026-08-23/24, the batch lookups: not inert on the ambiguous stratum, and measured.** The candidate loop became shared with the batch path, so an ambiguous `timezone_at` executes **exactly one more Python method call**. That count is the durable fact; the time it costs read as order 1 % of an ambiguous query across two paired runs whose estimators straddled, and must not be quoted to a second decimal. Kept deliberately: the alternative was a second copy of the stop-index and untested-last-zone logic, which is the drift this file exists to prevent, and `test_batch_and_scalar_agree_over_every_committed_point` is what makes the remaining duplication safe. The unique stratum, ~89 % of a random workload, executes not one changed statement.
- **2026-08-24, per-cell preparation shared across a batch: inert for the scalar path, and a real batch win.** Splitting a cell's preparation out of the loop that works it, and memoising it by shortcut entry inside a batch. Scalar `timezone_at` measured neutral with the estimators disagreeing in both backends, which is what neutral looks like; the batch path's ambiguous stratum gained **-3.8 % (clang) / -6.3 % (numba)**, both estimators agreeing. **The generalisable half:** what a batch can amortise is whatever is a property of the *cell* rather than of the point, so that is the line to split a per-point loop along. The prices it quoted are superseded - the 2026-09-06 entry deleted the zone id gather, which was a third of what that tuple held.
- **2026-08-24, reading a batch's arrays once per stage rather than once per point.** `int(entries[i])` and the two `float(...[i])` in the ambiguous resolvers are numpy scalar extractions: **242 ns per point** for the three against **103 ns** for the same values taken through `tolist()` up front. That is loop overhead, paid whether or not the point's cell was already prepared. Measured over 2,000 ambiguous fixture points, three paired rounds, `in_memory=False`, min / median ns per point: `TimezoneFinderL` **878 -> 755 (-14.1 %) / 936 -> 809 (-13.5 %)** — it also stopped using a dict, its answer being a pure function of the entry — and `TimezoneFinder` **10,021 -> 9,937 (-0.8 %) / 10,599 -> 10,554 (-0.4 %)**, where ~10 µs of geometry per point is what makes the same nanoseconds invisible. Both estimators agree in sign in both classes. **The general rule, and the reason this is recorded rather than just fixed:** a numpy scalar extraction inside a Python loop costs more than most of the loop bodies in this repository, so hoist the whole column out of the loop wherever a batch is walked point by point.
- **2026-08-25, the shortcut compiler's hole-side overlap fix and its antimeridian frame: both inert for timings.** Each changes `scripts/`, not `timezonefinder/`, so not one statement on the query path moved; what they move is the packaged `shortcuts.bin`, for **21 of 288,122 cells** (17 of which stopped resolving to a single zone) and **3 of 288,122** (none of which changed stratum, all three already holding a candidate list). The committed benchmark fixtures were checked against those cells rather than assumed clear: **no `unique_shortcut` or `random` point falls in one**, so no fixture point changed stratum and the fixtures did not need regenerating; 7 of 10,000 `on_land` and 2 of 5,000 `ambiguous_shortcut` points now test one additional candidate, a bounding-box rejection on ≤0.03 % of a fixture. The ladder, the denominators and every share above stand, and `docs/benchmark_results_*.rst` were deliberately **not** re-measured: re-running them would replace every committed figure with a fresh machine's for a change nothing can resolve. `docs/data_report.rst` was regenerated, since it counts the index rather than timing it.
