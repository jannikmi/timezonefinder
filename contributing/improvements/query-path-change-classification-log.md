# Query-path change-classification log

This log classifies changes since the anchor in the [query performance measurement baseline](query-performance-measurement-baseline.md), so later passes do not have to re-derive whether the recorded denominators still apply.

The dated entries are kept for their generalisable half, which is what makes them worth more than the bookkeeping they were written for; add new ones above the oldest as changes land. The 2026-08 entries sit *before* the declared anchor and bear on freshness only through the rules they state; the 2026-09 ones sit after it, as does everything named in the paragraph below.

**The anchor itself is stale, and the freshness command names a different commit from the one the baseline declares.** Established 2026-09-05 by a discovery round. The [baseline](query-performance-measurement-baseline.md) states its anchor as `6adf161` and then hands out a freshness diff against `e1c3e15`, which it lists two sentences later as a *superseded* anchor — so the command reports non-empty whatever the tree looks like, and a pass that runs it learns nothing. Against the declared anchor the diff is non-empty too: 17 runtime files, 1,740 insertions, over six commits (`7c06d0c` the frame-of-reference payload, `82703f2` the lazy public surface, `95741be` the ocean prefix check and batch land lookup, `64aa293`, `d64d38a`, `cac02a1`). The frame-of-reference payload is the one that matters and the baseline's prose already describes its effect, so the *narrative* is current and the *operand* is not. Re-anchoring is a measurement pass: it needs [PROF-1](items/data-pipeline-and-developer-tooling/prof-1-the-stage-ladder-measures-the-checked-public-accessors.md) taken first, or the ladder it re-records is the one with two rungs bound to the wrong accessors.

- **2026-09-05, the candidate loop's bounding-box columns and vertex counts read through buffer views: not inert, and the largest single move on the ambiguous stratum since the frame-of-reference payload.** What it removes is a **count**: four numpy 0-d scalar extractions per candidate in `outside_bbox`, one per point-in-polygon call for the vertex count, and one per hole resolution in `HoleArray._resolve` - which over the committed fixtures is ~4.2 + 0.78 + a hole's worth per ambiguous query, and zero on the unique-shortcut stratum, which never enters the loop. Paired inside one process with the views rebound to numpy indexing, arms alternated round by round, 25 rounds a side, 2,000 fixture points, answers asserted equal every round: ambiguous **-11.3 % clang / -11.0 % numba** (25/25 and 23/25 rounds), on_land -5.6 / -5.9 %, random -4.8 / -4.7 %, unique -0.2 / +1.0 % with the estimators straddling, which is the internal control. The side traded away is construction heap and it was measured rather than argued: **+4.4 KiB**, against +233 KiB the `.tolist()` form used by `block_offsets` would have cost for the same columns. **The generalisable half:** a `memoryview` over an already-loaded array indexes to a Python `int`, accepts a numpy integer as the index, and copies nothing - so on a hot loop it buys what a `list[int]` conversion buys without the second copy of the data, and it is the form to reach for whenever a per-candidate or per-point loop reads a stored column. What it needs is native byte order, which `np.load` gives wherever the packaged little-endian binaries are already assumed. The profiler's `FINDINGS` were re-taken on both backends in the tracked mapped mode in the same pull request; the **anchor was not moved**, because it is already stale by six commits (see below) and re-anchoring wholesale belongs to the pass that repairs the ladder.
- **2026-09-03, the coordinate bounds moving into `configs.py`: measurable, and an order of magnitude below what the suite can see.** `is_valid_lat` / `is_valid_lng` and the message describing them now read `MIN_*` / `MAX_*` globals instead of literals, on a stage `validate_coordinates` runs on **every** query and which is 33-36 % of a unique one. It is not free, against the entry that predicted it would be: `validate_coordinates` with the pure-Python validators the tracked no-numba configuration runs, three forms rotated round by round, min/median ns per whole call - literals **244/249**, `MIN_LAT_VAL <= lat <= MAX_LAT_VAL` **250/253**, `-MAX_LAT_VAL <= lat <= MAX_LAT_VAL` **295/299**. So the global load costs ~5 ns per query, ~0.5 % of a unique-shortcut query, and the negation the pre-negated constants avoid would have cost ten times that. **The generalisable half:** on a specialising interpreter a module global is nearly free to read and `UNARY_NEGATIVE` is not, so a constant that a hot path compares against is declared in the sign it is used in. The ladder and every share above it stand; the `validate_coordinates` stage is ~2 % heavier than the anchor says, which is inside the second decimal the baseline forbids quoting anyway.
- **2026-09-03, the zone position table read once per finder, and `certain_timezone_at` sharing the shortcut enumeration: both inert for the ladder.** Neither is on the profiled `timezone_at` path: `_iter_boundary_ids_of_zone` is reached only from `certain_timezone_at` and `get_geometry`, and the enumeration `certain_timezone_at` now shares was already what it inlined. `AbstractTimezoneFinder.__init__` gains one `None` assignment, which is the whole of what construction pays for the lazy read. What the first change removes is a **count**: one file open, header parse and mapping per call, for a 890-byte immutable array, down to one read per finder - measured on the committed fixtures at 48.1 ms -> 2.90 ms (on land) and 55.2 ms -> 3.57 ms (random) per 500 `certain_timezone_at` calls, 21 of 21 rounds to the cached form.

- **2026-08-23, the negative-id guard on the public id-taking methods: inert.** It adds a check to four public methods and moves the internal callers onto private accessors with identical bodies, so the query path executes the same number of calls over the same statements. Nothing in the `zone name` block or the ladder above it changed.
- **2026-08-23/24, the batch lookups: not inert on the ambiguous stratum, and measured.** The candidate loop is now shared with the batch path, so an ambiguous `timezone_at` executes **exactly one more Python method call** than the anchor. That count is the durable fact; the time it costs is at the edge of what this machine resolves. A first paired run read +0.51 % (clang) with both estimators agreeing; a three-way interleaved re-run a day later put the same comparison at +2.12 % min / +0.70 % median, with the estimators straddling. **Read it as order 1 % of an ambiguous query, ~0.6 % of a mixed wall clock, and do not quote a second decimal.** Kept deliberately: the alternative was a second copy of the stop-index and untested-last-zone logic, which is the drift this file exists to prevent, and `test_batch_and_scalar_agree_over_every_committed_point` is what makes the remaining three-line duplication safe. The unique stratum, ~89 % of a random workload, executes not one changed statement. Everything above the ladder's `zone name` block stands; the ambiguous `candidate loop` block is ~1 % heavier than the anchor says.
- **2026-08-24, per-cell preparation shared across a batch: inert for the scalar path, and a real batch win.** Splitting a cell's preparation (`candidates_of`, `zone_ids_of`, `stop_index_of` — 898 ns against 10,228 ns for a whole ambiguous point, so an **8.8 % ceiling**) out of the loop that works it, and memoising it by shortcut entry inside a batch. Measured paired against the commit before it, 244 rounds a side: scalar `timezone_at` **-0.41 % min / -0.08 % median, 111/244 (clang)** and **+0.33 % / -0.89 %, 130/244 (numba)** — estimators disagreeing in both, which is what neutral looks like. On the batch path, 240 rounds a side: **-3.8 % (clang) / -6.3 % (numba)** on the ambiguous stratum, both estimators agreeing. The ladder's per-query figures are unchanged by it.
- **2026-08-24, reading a batch's arrays once per stage rather than once per point.** `int(entries[i])` and the two `float(...[i])` in the ambiguous resolvers are numpy scalar extractions: **242 ns per point** for the three against **103 ns** for the same values taken through `tolist()` up front. That is loop overhead, paid whether or not the point's cell was already prepared. Measured over 2,000 ambiguous fixture points, three paired rounds, `in_memory=False`, min / median ns per point: `TimezoneFinderL` **878 -> 755 (-14.1 %) / 936 -> 809 (-13.5 %)** — it also stopped using a dict, its answer being a pure function of the entry — and `TimezoneFinder` **10,021 -> 9,937 (-0.8 %) / 10,599 -> 10,554 (-0.4 %)**, where ~10 µs of geometry per point is what makes the same nanoseconds invisible. Both estimators agree in sign in both classes. **The general rule, and the reason this is recorded rather than just fixed:** a numpy scalar extraction inside a Python loop costs more than most of the loop bodies in this repository, so hoist the whole column out of the loop wherever a batch is walked point by point.
- **2026-08-25, the hole-side overlap fix in the shortcut compiler: inert for timings.** It changes `scripts/`, not `timezonefinder/`, so not one statement on the query path moved; what it moves is the packaged `shortcuts.bin`, for **21 of 288,122 cells** — 17 of which stopped resolving to a single zone. The committed benchmark fixtures were checked against those cells rather than assumed clear: **no `unique_shortcut` or `random` point falls in one**, so no fixture point changed stratum and the fixtures did not need regenerating; 7 of 10,000 `on_land` points and 1 of 5,000 `ambiguous_shortcut` points now test one additional candidate, which is a bbox rejection on 0.03 % of two fixtures. The ladder, the denominators and every share above stand, and `docs/benchmark_results_*.rst` were deliberately **not** re-measured: re-running them would replace every committed figure with a fresh machine's for a change nothing can resolve. `docs/data_report.rst` was regenerated, since it counts the index rather than timing it.
