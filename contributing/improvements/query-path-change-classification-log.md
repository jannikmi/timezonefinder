# Query-path change-classification log

This log classifies changes since the anchor in the [query performance measurement baseline](query-performance-measurement-baseline.md), so later passes do not have to re-derive whether the recorded denominators still apply.

The dated entries are kept for their generalisable half, which is what makes them worth more than the bookkeeping they were written for; add new ones at the top of the list as changes land. Every entry here sits after the declared anchor, as does everything named in the paragraph below. The changes from before it bear on freshness only through the rules they state, and are in [query-path changes before the measurement anchor](query-path-changes-before-the-measurement-anchor.md).

**The anchor itself is stale, and the freshness command names a different commit from the one the baseline declares.** Established 2026-09-05 by a discovery round. The [baseline](query-performance-measurement-baseline.md) states its anchor as `6adf161` and then hands out a freshness diff against `e1c3e15`, which it lists two sentences later as a *superseded* anchor — so the command reports non-empty whatever the tree looks like, and a pass that runs it learns nothing. Against the declared anchor the diff is non-empty too: 17 runtime files, 1,740 insertions, over six commits (`7c06d0c` the frame-of-reference payload, `82703f2` the lazy public surface, `95741be` the ocean prefix check and batch land lookup, `64aa293`, `d64d38a`, `cac02a1`). The frame-of-reference payload is the one that matters and the baseline's prose already describes its effect, so the *narrative* is current and the *operand* is not. Re-anchoring is a measurement pass; the ladder it would re-record with is sound again, the last mis-bound rung having been repaired on 2026-09-06.

- **2026-10-12, on `de96f5c`, the lookups reading −180° as +180° and −90° as the point one unit north: inert on the unique path, by count; per query reaching a candidate, six bytecodes more and one Python call fewer.** `utils.query2int` replaced the two `coord2int` calls in `_zone_id_among`, `certain_timezone_at` and `timezones_at`. Counted with `sys.settrace` opcode events over 200 fixture points: a unique `timezone_at` executes 138 bytecodes and 12 calls on both; every other point differs by exactly +6 and −1, in `timezone_at` and `certain_timezone_at` alike (`timezones_at` carries the identical edit), apart from one that took a longer path in whichever finder was traced second, which is process state rather than the change. A paired whole-lookup A/B (121 rounds, roles swapped as a second pair, C extension, mapped, CPython 3.14.2 on Apple arm64) read `no difference` for `timezone_at` on the ambiguous, random and unique strata and for `certain_timezone_at` on the ambiguous one. A 256-point ambiguous batch read `unresolved` in five of six 241-round pairs, the base winning 54–68 % of rounds by best rounds 0.6–3.4 % faster: of order 1 % of that batch if real. The tracked suite agrees: three local base/head pairs (`benchmark_core`, 50 rounds, no numba) read the ambiguous batch rows −0.2 to −2.4 % and every row inside its noise, where CI's same-runner comparison read them −5.5 to −7.2 % with the unique batch row, which executes nothing changed, at −5.1 %. The ladder's conversion rung is rebound to `query2int`; `FINDINGS` and the anchor stand. **The generalisable half:** one call that scales both axes pays for its comparisons, where `query2int` calling `coord2int` per axis lost about 70 % of paired rounds, 1–3 % of an ambiguous `timezone_at`.
- **2026-10-12, on `5144eb5`, the shortcut index mapping a coordinate to its entry: inert per query, by count; a batch call executes 4 more bytecodes, whatever its size.** `ShortcutIndex.entry_at` / `entries_at` took the H3 cell computation over from every lookup method. Counted with `sys.settrace` opcode events over 200 fixture points, the lookup functions of `5144eb5` against the change's in one process: a unique query executes 138 bytecodes and 13 Python calls on both, an ambiguous one 343.6 and 24.94. The ladder keeps its separate `h3.latlng_to_cell` and `shortcuts.entry_of` rungs: they are the same C call and Python call `entry_at` makes, split so the two stages are priced apart. A paired whole-lookup A/B (121 rounds, roles swapped as a second pair) read `no difference` on every stratum, scalar and batch, on clang and numba, with 3 of 18 rows `unresolved` in both directions; the ladder, `FINDINGS` and the anchor stand. **The generalisable half:** a structural change meant to execute nothing new is settled by the count, not the clock. Holding the cell id in a local costs two bytecodes per query, which is why `entry_at` is one expression, and no timing here could have shown it: on a 4-vCPU Intel Xeon 2.8 GHz Linux container under CPython 3.13, an in-process pair read the identical unique-stratum code +6.7 % in one process and −4.8 % in another, each stable with the roles swapped.
- **2026-09-06, `njit` coming off the three scalar helpers, and the candidate loop's zone id gather deleted: not inert, and the two backends differ by design.** `is_valid_lat`, `is_valid_lng` and `coord2int` are plain Python functions in `timezonefinder/utils.py` now, and `_zone_id_among` reads the one zone id it needs instead of gathering every candidate's. It removes a **count**: two `njit` dispatches per query and two more on an ambiguous one, plus one numpy call per ambiguous query. Paired inside one process, arms alternated, 25 rounds a side, 2,500 fixture points, clang then numba: random **-4.8 / -12.3 %**, on_land -7.7 / -13.0 %, ambiguous -15.7 / -16.6 %, 20-25 of 25 rounds; unique **+0.8 % (12/25) clang, -8.0 % (23/25) numba**. **The generalisable half:** removing a dispatch is worth nothing on the configuration that never paid for it. Without numba `njit` is a no-op, so a unique query executes the same statements and reads neutral - the estimators straddle there (+0.8 % min, -0.8 % median) and a null A/B of the harness against itself puts its band at ±1 %. `validate_coordinates` fell 270 -> 212 ns on numba and stayed at 211 on clang: falling *to* the untouched backend's figure rather than below it is the signature of a dispatch removal, and distinguishes it from making the work cheaper. Inlining the helpers at their call sites was measured and rejected as a design - ~40 ns more for a second definition of where the world ends. `FINDINGS` re-taken on both backends; **the anchor was not moved**, following the entry below.
- **2026-09-05, the hole ids of a candidate polygon looked up without an exception: real on the ambiguous stratum, and at the edge of what this machine resolves.** What it removes is a **count**, which is the durable half: **0.498 raised-and-caught `KeyError`s and 0.779 generator objects per ambiguous query** over the committed fixtures, plus the 0.498 `in_any_polygon` calls that iterated nothing - 1,225 of the 1,322 packaged boundary polygons own no hole, and the majority path used to build a generator, enter it, raise, catch and return to establish that. Per hole-less candidate, 160 ns -> 88 ns. Paired inside one process with `_hole_ids_of` and `inside_of_polygon` rebound to the generator form, arms alternated round by round, 41 rounds a side, 2,000 fixture points: ambiguous **-4.0 % min / -0.8 % median clang (25/41)** and **-4.7 % / -4.1 % numba (33/41)**, on_land -2.0 / -5.3 % and -1.7 / -1.5 %, random -1.1 / -1.1 % and -1.7 / -0.2 %, unique +0.2 / +1.1 % and +0.4 / +0.2 % with the estimators straddling, which is the internal control. **Read it as order 2-4 % of an ambiguous query and ~1 % of a mixed wall clock, and do not quote a second decimal**: the clang estimators disagree on the median. **The methodological half, and the reason this is recorded rather than just fixed:** the entry that proposed it predicted -4.9 % from a prototype that compared a *subclass instance* against a base instance, and rebinding one method on one instance reads lower - two live finders differ in heap layout and cache residency, not only in the code under test. A prototype that builds a second object is measuring the second object too; rebind instead.
- **2026-09-05, the candidate loop's bounding-box columns and vertex counts read through buffer views: not inert, and the largest single move on the ambiguous stratum since the frame-of-reference payload.** What it removes is a **count**: four numpy 0-d scalar extractions per candidate in `outside_bbox`, one per point-in-polygon call for the vertex count, and one per hole resolution in `HoleArray._resolve` - which over the committed fixtures is ~4.2 + 0.78 + a hole's worth per ambiguous query, and zero on the unique-shortcut stratum, which never enters the loop. Paired inside one process with the views rebound to numpy indexing, arms alternated round by round, 25 rounds a side, 2,000 fixture points, answers asserted equal every round: ambiguous **-11.3 % clang / -11.0 % numba** (25/25 and 23/25 rounds), on_land -5.6 / -5.9 %, random -4.8 / -4.7 %, unique -0.2 / +1.0 % with the estimators straddling, which is the internal control. The side traded away is construction heap and it was measured rather than argued: **+4.4 KiB**, against +233 KiB the `.tolist()` form used by `block_offsets` would have cost for the same columns. **The generalisable half:** a `memoryview` over an already-loaded array indexes to a Python `int`, accepts a numpy integer as the index, and copies nothing - so on a hot loop it buys what a `list[int]` conversion buys without the second copy of the data, and it is the form to reach for whenever a per-candidate or per-point loop reads a stored column. What it needs is native byte order, which `np.load` gives wherever the packaged little-endian binaries are already assumed. The profiler's `FINDINGS` were re-taken on both backends in the tracked mapped mode in the same pull request; the **anchor was not moved**, because it is already stale by six commits (see below) and re-anchoring wholesale belongs to the pass that repairs the ladder.
- **2026-09-03, the coordinate bounds moving into `configs.py`.** Its stage figures are superseded by the 2026-09-06 entry, which rewrote that stage; the rule it established - a constant a hot path compares against is declared in the sign it is used in, since `UNARY_NEGATIVE` costs and a module global nearly does not - lives with its measurement above `MIN_LNG_VAL` in `timezonefinder/configs.py`.
- **2026-09-03, the zone position table read once per finder, and `certain_timezone_at` sharing the shortcut enumeration: both inert for the ladder.** Neither is on the profiled `timezone_at` path: `_iter_boundary_ids_of_zone` is reached only from `certain_timezone_at` and `get_geometry`, and the enumeration `certain_timezone_at` now shares was already what it inlined. `AbstractTimezoneFinder.__init__` gains one `None` assignment, which is the whole of what construction pays for the lazy read. What the first change removes is a **count**: one file open, header parse and mapping per call, for a 890-byte immutable array, down to one read per finder - measured on the committed fixtures at 48.1 ms -> 2.90 ms (on land) and 55.2 ms -> 3.57 ms (random) per 500 `certain_timezone_at` calls, 21 of 21 rounds to the cached form.
