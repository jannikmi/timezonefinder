# Improvement sequencing and preconditions

Check these explicitly before taking an item, and name the blocking one when you skip it.

```
[format 4, pending and unreleased] ─→ unclaimed; promote a format item into it while it lasts

DOC-10 (plan, maintainer-approved) ─→ DOC-9 ─→ DOC-6
DOC-8 independent; cheaper after DOC-9

PY-1 (maintainer decision: the Python window) ─→ GH-721

independent: GH-524
```

- **Only DOC-6 is blocked, and DOC-9 is what now blocks it.** The maintainer decided on 2026-09-06 to move `docs/` off Sphinx to MkDocs — recorded in the [documentation source format decisions](decisions/documentation-source-format-decisions.md) — which withdrew the four semantic-line-break slices, since consolidated into that record, into [DOC-9](items/data-pipeline-and-developer-tooling/doc-9-migrate-the-documentation-from-sphinx-to-mkdocs.md): it rewrites the same files wholesale, so their line breaks are set as the Markdown is written. **DOC-9 is itself blocked on [DOC-10](items/data-pipeline-and-developer-tooling/doc-10-plan-the-mkdocs-migration-for-maintainer-review.md)**, which writes the migration plan and its losslessness contract and puts both to the maintainer — required the same day, because a 5,332-line wholesale rewrite cannot be reviewed for omissions and the plan is what makes its diff reviewable. **DOC-9 must also record the wrapping convention** in the [documentation maintenance rules](../development/documentation-maintenance-rules.md), which state none today — the convention is recorded only for the README, in the [markup rules](../development/documentation-markup-links-and-generated-pages.md) — and which that migration rewrites anyway. DOC-6 is the real block: a check that rejects a hard-wrapped paragraph fails on every page not yet converted, and it is cheaper to write against Markdown than against reStructuredText. DOC-8 blocks nothing and is blocked by nothing, but it must not land against an open release branch — it renames the file that branch is editing and the script that assembles it — and its one docs-build complication disappears if it follows DOC-9.

- **Regenerating the packaged data is a normal thing for an item to do**, and no item is parked for needing it. Two things it has to respect: it must not collide with the weekly data-update pipeline, which opens *and auto-merges* its own pull requests, so rebase before the final gate; and it must not be incidental — `diff -rq` against a copy of the data directory taken before the regeneration should list only binaries the change had a reason to move, since a file left byte-identical costs the release nothing and git no longer holds a baseline to compare against.
- **Format changes are cheaper in a row than spread out, so rank them together once one lands.** A `DATA_FORMAT_VERSION` bump numbers a release, not a change: while one sits unreleased on `master`, the next format change rides the same number and the ordered two-distribution release is paid once for both. The ranking prices each format item as if it paid that release alone, which is right for the first one and wrong for every one after it — so when a bump is pending, promote the other format items rather than reading their entries literally. **Format 4 is pending now** — the aligned grid tree took it, as the held format-2 window bullet below records — and the one ranked item with a format change, IDX-8, cannot ride it until its prototype measurement and a maintainer decision clear, so the promotion above currently has nothing to promote.
- **The packaged binaries are not committed, and a format item compiles its own in CI.** Since 2026-08-31 `data/` is git-ignored: `make bootstrap` obtains the declared release, and CI takes the dataset from the run recorded in `DATA_BUILD_RUN` whenever the declared version is one PyPI does not have. Every format item declares such a version, and `compile_data.yml` is what produces the run for it — `gh workflow run compile_data.yml --ref <branch>`, then commit the run id. Budget one dispatch per regeneration; the [data-pipeline rules](../development/data-pipeline-format-versioning-and-release-order.md) carry the mechanics and the [format-release decisions](decisions/data-format-version-marker-and-release-batching-decisions.md) carry why committing the binaries instead was refused.
- **The held format-2 window closed on 2026-08-30 when the latitude block index landed**, so `DATA_FORMAT_VERSION` 2 now means polygon layout 2 and shortcut layout 2. Nothing further may ride it: format 2 published as `timezonefinder-data` 2.2026.3 on 2026-08-30, and the frame-of-reference payload took `DATA_FORMAT_VERSION` to 3 the day after — the second ordered two-distribution release the sequential-encoding split knowingly accepted. **Format 4 is the open window now**, and only until a 4.x publishes: the aligned grid tree took it, together with the held deterministic tie-order rebuild, and nothing else claims it. **A measurement cannot be batched the way a change can** — PERF-10 was to ride this release and could not, because what it had measured was the cells the release replaced. An item whose evidence is about the structure another item is changing has to be re-measured after that item lands, not held for its release. The hold is what put the block index *before* uncommitting the binaries rather than after it, against the older ordering's argument that uncommitting them first makes every later regeneration cheap in history — that reasoning still holds and was simply outweighed, since ~61 MiB of pack growth is recoverable by GH-522 while a second ordered two-distribution release is not. That publication has since happened, and the binaries have since stopped being committed, so both halves of that trade are settled. The [format-batching decisions](decisions/data-format-version-marker-and-release-batching-decisions.md) carry the mechanics.
- **GH-522's technical precondition is met, but the maintainer parked the rewrite until repository size creates a concrete need.** A history rewrite used to be undone by the next data update, which re-added ~61 MiB immediately; since the binaries stopped being committed nothing does that. The one route that remained — a format branch committing its own regeneration — closed when `compile_data.yml` gave it a run artefact to use instead, so the rewrite no longer has to be timed against what is unmerged. Technical readiness does not make the irreversible SHA and tag rewrite timely; the item's observed-need trigger does.
- **Publish the data distribution before the code release that requires it**, on every change that bumps `DATA_FORMAT_VERSION`. Since PR #529 this is *enforced*: the release job refuses to go on if no published `timezonefinder-data` satisfies the bound in the wheel it is about to publish. The rule stays stated because the guard blocks the wrong order without performing the right one — it tells you the data release is missing, it does not make it. Worth knowing: the guard runs only on tag refs, so **no pull request ever exercises it**, and the first time it can speak is the run that is already publishing. Dry-running it against a locally built wheel costs a minute and is the only way to learn its answer while the version is still spendable.
- **One free-threading slice is left, and it waits on the Python window.** GH-721 ships `abi3t` wheels for 3.15t and later, which setuptools accepts from 84.2.0; those wheels claim an interpreter the package supports only once PY-1's decision adds 3.15. `cp314t` wheels are refused unless issue #721 collects demand for them. **Six pieces of this family already landed and are not entries:** the polygon offset table, the read-only loaded arrays with their state-contract test, the `setup.py` guard that withholds the abi3 claim on every free-threaded interpreter, the `free-threaded` tox env that CI runs on a uv-fetched 3.14t, thread-safety documentation that states one answer - concurrent lookups on a shared instance are safe, and one instance per thread is for throughput, which rests on every lazily kept value being a read-only array identical from any thread (the `TimezoneFinder` class docstring states that condition) - and the assertion that a finder construction and a lookup leave the GIL disabled, which `tests/test_free_threading.py` holds on a free-threaded interpreter in CI. **Nothing the package installs may re-enable the GIL**: a new runtime dependency without `Py_mod_gil` turns it back on for the whole process, and that test is what refuses one.
- **The candidate loop has already been made ~35 % cheaper once, so price against the current baseline and not against any figure you remember.** Fetching a candidate's coordinates fell from ~4.9 µs to ~0.83 µs when the coordinate accessors stopped re-walking the FlatBuffers structure per lookup, which moved the vertex count below which a candidate costs more to *fetch* than to test, and took the mapped mode from ~30 % slower than in-memory to within ~5 % of it. Anything ranked on the *time* in that loop inherits that: what is left may now sit inside the batch suite's noise floor. That does not refuse an item — it prices it; a native candidate loop was refused on exactly that price, and [GH-364](items/lookup-geometry-and-data-format/gh-364-a-native-candidate-loop.md) says what would revive it. *The measured baseline* below is current as of its anchor; re-read it rather than an entry's prose. **A count is the cheaper instrument, and on its own it is half an answer.** What a change removes in candidates *tested* can be enumerated over the packaged index today, and that number survives a new machine and a data update alike, which is why it is still the thing to reach for first. What it does not survive is candidates that cost different amounts: a count is a *workload share* only when the things counted are interchangeable, and in the candidate loop they are not. Measured 2026-09-08 (Apple arm64, C extension, in-memory, packaged 2026c) the full predicate runs ~1,170 ns for a hole-free polygon and ~12,471 ns for the one owning 95 holes, a 10.7x spread that no count can see; 22.7 % of the candidates sitting in a tested prefix own at least one hole. So enumerate first, because it is cheap and portable - then establish what the counted things cost before reading the count as a share of anything. Candidate ordering itself is settled and shipped: `scripts/shortcut_ordering.py` compiles the order against estimated full-predicate work rather than against a count, and its module docstring carries the model and its limits.
- **A batch form is not worth adding while its last step is per-point string work**, which is the ordering the batch `timezone_at_land` was held for and the shape any future batch method should copy. The ocean check ended `timezone_at_land` as a `re.match` per answer; batching that reintroduces exactly the work a batch exists to remove. It shipped as a prefix comparison first and then as an id-indexed flag array on `ZoneNames`, which a batch applies as one mask over the whole answer — cheaper per point than the scalar method, rather than merely equal to it.
- **API-3 is gated on publicly voiced user interest**, read from discussion #671. Never implement it; only report whether interest has appeared.
- **Do not re-propose anything in the topic decision files linked from the [register rules](improvement-register-rules.md) without new evidence.**
