# Query performance measurement baseline

Every timing quoted in this file comes from one run of `prototypes/query_stage_profile.py`, whose `FINDINGS` block holds the full per-stage breakdown. Repeated here is only what the ranking needs: the denominators, and how to tell whether they still describe the tree.

- **Taken at** `2b6d301` (**this SHA is an operand, not a citation** — the freshness command below diffs against it, so a history rewrite invalidates it and the baseline has to be re-anchored and re-measured in the same pass) — Apple arm64, CPython 3.14.2, data 2026d, fixture set v4, the C extension against memory-mapped data, 2,000 points per stratum and the minimum of 15 rounds. **Figures taken before the shortcut index became an aligned grid tree are not comparable stage by stage**, because the cell computation and the table read are now one call: a ladder that splits them prices a call the lookup does not make. The superseded tables are kept in the `FINDINGS` block, labelled as such.
- **The denominators**, as whole `timezone_at()` calls on the tracked configuration: a unique-cell query **~0.56 µs** and it contains no geometry at all; an ambiguous one **~2.7 µs**; a uniformly random one **~0.67 µs** and an on-land one **~0.84 µs**. Every share below is a share of one of these, and the entry says which — a share of an ambiguous query is not a share of a workload. **The two coordinate-access modes do not differ**: mapped and `in_memory=True` read within ~2 % of each other on every stratum and every rung. **They are GIL-enabled figures**, and the profiler cannot produce any other kind: it imports `line_profiler`, which re-enables the GIL for the process whatever interpreter it runs on. A free-threading claim about this path needs `tests/test_free_threading.py`, not this ladder. The numba column is not restated here; `docs/benchmark_results_acceleration_paths.rst` is where the backend ranking lives, and it is regenerated rather than quoted.
- **Freshness check**, before ranking anything on one of them:

  ```
  git diff --stat 2b6d301..HEAD -- timezonefinder/ DATA_VERSION packages/timezonefinder-data/pyproject.toml
  ```

Empty ⇒ the numbers describe the current tree. Non-empty ⇒ classify what changed. A docstring, an `__all__` list or a rename leaves them standing and is worth recording here so the next pass does not re-derive it; a change to the lookup flow, the polygon math, the coordinate accessors, the shortcut reader or the packaged data does not. The packaged binaries are not in the diff because they are not committed — the two stamps that stand in for them are, and no regeneration reaches `master` without moving one.

**Report the diff before ranking on these, and read the [classification log](query-path-change-classification-log.md) whenever it is non-empty** — it holds what each intervening commit is and whether it moves a denominator. A pass that finds a lookup-flow change there has found a stale baseline, not a note to work around.

- **A ladder rung must bind the symbol the lookup binds, and stop where the lookup stops — both have been got wrong here, so check a rung's binding before quoting it.** `prototypes/query_stage_profile.py` bound the *checked public* `zone_ids_of` and `zone_name_from_id` where `timezone_at` calls the unchecked internals. **Both are repaired**: the `zone_ids_of` rung went by deletion when the candidate loop stopped building the array, and `zone_name_from_id` was rebound to `tf.zone_names.name_of` on 2026-09-06 — it had read 58-64 ns for a call costing 37-38, 8.2-8.7 % of the unique ladder rather than 5.2-5.3 %. Separately, the `bbox rejection` and `hole checks` rungs ran to `stop_index_of` rather than to the lookup's `break`, opening more candidates per ambiguous query than the lookup opens; they are now handed the real trip count. Against the real function the ladder reads **-11 % on the unique stratum and +1 % on the ambiguous one**, the residual being the bound-method call and attribute chain the ladder does not pay - so a rung is a share of the ladder, never of the call. Do not reuse a figure that priced a since-deleted call. The whole-query rows, the denominators and the counts here come from the real function and were never affected.
- **One laptop took these, so rank on what survives leaving it, and let no time or share here decide an item until it is re-taken on x86-64 Linux** — the [deployment-hardware rule](../development/trade-off-surfacing-and-validation.md#validate-it-during-implementation) makes a laptop figure exploration, not evidence. In descending order of how well a figure travels:

  1. **Counts, which are exact and machine-independent** — a line's hit count does not depend on the hardware, only on the code. **1.02** candidate polygons tested per ambiguous query, **0.048** per uniformly random one and **0.114** per on-land one — so **95 %** of a random workload is answered with no geometry at all; **zero** FFI crossings and zero buffer acquisitions per candidate since the frame-of-reference payload, where there were one of each on the clang/mapped path; one numpy call per ambiguous query — the candidate slice, since the zone id gather was deleted, where there were two. State what a change removes as a count first, and use time only to size it.
  2. **Shares within one query**, which travel but not uniformly: the stages are bound by different things — memory latency for the mapped accessor, interpreter dispatch for the Python prologue, floating-point throughput for the kernel — so another machine re-weights them against each other. Read a share as an order of magnitude, never to one percentage point.
  3. **Absolute nanoseconds, which are this machine's alone.** Never rank on one, and never compare one to a figure from CI or from a report page.
- **Rank the `clang` / `in_memory=False` column, not the development machine's.** A dev checkout runs numba on whatever laptop is to hand; a plain `pip install` in a constrained container runs the C extension against memory-mapped data, which is why `docs/benchmarking_methodology.rst` makes that the tracked configuration for CI too. Both are measured, so this costs nothing but the discipline of reading the right column.
- **A share of a stratum is not a share of a workload.** Uniformly random points are **4.6 %** ambiguous and on-land points **11.2 %**, and an ambiguous query costs **~4.9x** a unique one, so ambiguous work is only **~19 %** of a realistic mixed wall clock and unique work **~81 %**. Multiply the stratum share through before comparing two items that live on different strata — that multiplication is a property of the fixtures, not of the machine, so it survives the move. **The ambiguous share of a random workload falls every time the cells get smaller or tighter**, which is the asymmetry to keep in mind: a unique-path regression costs more of a real workload than an ambiguous-path win of the same size, and the gap widens with each such change.
- **A stage's share bounds its upside and says nothing about its downside, so a small stage is a constraint rather than an opportunity.** For any stage the ladder puts in single digits — `zone_name_from_id` at ~5 % of a unique query, `last_change read` and `query2int` at a few percent of an ambiguous one — ask whether a change keeps it free, never whether it makes it faster, and settle it on a whole-query A/B rather than on a microbenchmark of the stage. Making such a stage *slower* is not bounded the same way: the `searchsorted` layout refused for the table read measured **+93 % of a unique query**, and since the large majority of a random workload is answered on the unique path, a regression there is amplified rather than diluted. `docs/benchmarking_methodology.rst` carries the three A/B designs that got this wrong before it was settled.
- **Where a unique query's time actually is, and therefore where a real win has to come from:** `validate_coordinates` **196 ns** and the shortcut `entry_at` **284 ns** — **~96 % of the unique ladder in two calls, before any geometry**, or ~85 % of the whole call once the ladder's own residual is paid, and ~74 % of a uniformly random one. `entry_at` is the largest single stage of a query that needs no geometry, so it is the one stage of that prologue where a redesign can pay rather than merely has to stay free; it is also the one that absorbed the cell computation, so compare it against *both* of the stages it replaced. The batch path attacks the same prologue from the other side — it hoists validation, the integer scaling and the cell arithmetic out of the loop and resolves only ambiguous points one at a time — and `docs/benchmark_results_batch_break_even.rst` carries what that is currently worth.
- **A second machine class exists, and it is CI's.** The benchmark workflow measures base and head in one job on the same runner (Linux, the C extension, no numba - the tracked configuration), which is the cross-check this section asks for and the only figures here not taken on one laptop. **Read a ratio from it as a magnitude, and name the run.** Two runs of the same comparison on the same CPU class read the grid-tree index's scalar gain as 1.47x and 1.38x - the runner's own jitter is larger than many real changes, which is exactly why the same-runner comparison exists and also why its third digit is not a number. On that run the shape was: scalar `timezone_at` **~1.3-1.5x** on the random and unique-cell strata, `timezone_ids_at` **~5x** on random points and **>20x** where a single zone covers the cell, and the mapped finder's construction heap **~-20 %** with `TimezoneFinderL`'s roughly halving.

  Three things to read from it, each of which generalises past that run. The **memory figures are `tracemalloc` heap and near-deterministic**, so a large one is signal and not jitter, unlike the query rows where a few percent is the runner's own noise. The **batch rows move far more than the scalar ones** whenever a change touches the prologue, because a batch amortises it. And a **row whose fixture is a classification by the index is not a comparison at all** across a change to that index: CI warns about the differing `fixture_version` itself, and the one row that read as a regression was the re-labelled stratum - the same points, asked of both sides, were level. Attribute a branch's figure to a stage only where a paired A/B isolated it.
- **The 2x rule, for what none of the above fixes.** Act on a difference only if it survives any single stage turning out 2x cheaper or 2x more expensive elsewhere. It keeps the large calls (a 37 % workload share stays large at half the size) and refuses the ones that only exist on this laptop. An item that fails the rule and still matters needs a second machine class — the profiler is one script over committed fixtures, so a run in a Linux x86 container is the cheap way to get one; record it as a second column here, described the way `scripts/describe_benchmark_machine.py` describes a benchmark run's machine.
- **Re-measuring belongs to the change that invalidates it**, not to a follow-up pass. A pull request that moves the critical path re-runs the profiler on both backends (a few minutes each), and updates the `FINDINGS` block, this anchor and every share it moved, in that same pull request. Numbers left behind do not announce themselves: an entry ranked on a share that is no longer true reads exactly like one that is, which is the failure this file exists to prevent.
