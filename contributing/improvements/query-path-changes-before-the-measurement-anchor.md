# Query-path changes before the measurement anchor

Changes to the query path that landed before the anchor of the [query performance measurement baseline](query-performance-measurement-baseline.md), so its denominators already include them and no freshness question turns on them. **They are kept for the rules they state**, which is the part worth more than the bookkeeping they were written for; anything landing after the anchor is classified in the [query-path change-classification log](query-path-change-classification-log.md).

## Rules about measuring a change to this path

- **A structural change meant to execute nothing new is settled by the count, not the clock.** Two separate changes - the shortcut index taking the cell computation over from every lookup method, and one `query2int` call replacing two `coord2int` calls in the candidate loop - were established inert by `sys.settrace` opcode events over 200 fixture points, and neither could have been settled by timing: on a 4-vCPU container an in-process pair read *identical* unique-stratum code +6.7 % in one process and -4.8 % in another, each stable with the roles swapped. Where such a change is not quite inert, say so as a count: reading the two meridians a polygon owns costs a candidate-reaching query six more bytecodes and one Python call fewer.
- **Holding a value in a local costs bytecodes.** That is why `ShortcutIndex.entry_at` is one expression, and why a per-axis helper calling another per-axis helper lost ~70 % of paired rounds, 1-3 % of an ambiguous `timezone_at`, against one call that scales both axes.
- **Removing a dispatch is worth nothing on the configuration that never paid for it.** Taking `njit` off the three scalar helpers moved every stratum on numba (random -12.3 %, ambiguous -16.6 %) and read neutral on clang, where `njit` is a no-op decorator and a unique query executes the same statements. The signature of a dispatch removal is a stage falling *to* the untouched backend's figure rather than below it - `validate_coordinates` 270 -> 212 ns on numba, unchanged at 211 on clang - which is how to tell it from making the work cheaper. Inlining those helpers at their call sites was measured and rejected as a design: ~40 ns more, for a second definition of where the world ends.
- **A numpy scalar extraction inside a Python loop costs more than most loop bodies in this repository.** Three of them per point were **242 ns** against **103 ns** for the same values taken through `tolist()` up front; hoist the whole column out wherever a batch is walked point by point. A `memoryview` over an already-loaded array is the other form to reach for: it indexes to a Python `int`, accepts a numpy integer as the index and copies nothing, which on the candidate loop was **-11.3 %** of an ambiguous query for **+4.4 KiB** of construction heap, against +233 KiB for the `.tolist()` form of the same columns. It needs native byte order, which `np.load` gives for the packaged little-endian binaries.
- **Removing a raised-and-caught exception from the majority path is a count worth taking.** Resolving a candidate's hole ids without one removed **0.498 raised-and-caught `KeyError`s and 0.779 generator objects per ambiguous query** - the large majority of boundary polygons own no hole, and the majority path was building a generator, entering it, raising, catching and returning to establish that. Order 2-4 % of an ambiguous query and ~1 % of a mixed wall clock; the estimators disagreed on the median, so it must not be quoted to a second decimal.
- **A prototype that builds a second object is measuring the second object too.** The entry that proposed the hole-id change predicted -4.9 % from a prototype comparing a *subclass instance* against a base instance; two live finders differ in heap layout and cache residency, not only in the code under test. Rebind a method on one instance instead.
- **What a batch can amortise is whatever is a property of the *cell* rather than of the point**, so that is the line to split a per-point loop along. Sharing per-cell preparation across a batch was neutral for the scalar path and **-3.8 % (clang) / -6.3 % (numba)** on the batch path's ambiguous stratum.
- **One copy of the candidate loop, shared between the scalar and batch paths, is worth one extra Python method call per ambiguous query.** The alternative was a second copy of the stop-index and untested-last-zone logic, which is the drift that duplication causes; `test_batch_and_scalar_agree_over_every_committed_point` is what makes the remaining duplication safe.
- **A constant a hot path compares against is declared in the sign it is used in**, since `UNARY_NEGATIVE` costs and a module global nearly does not. The measurement lives above `MIN_LNG_VAL` in `timezonefinder/configs.py`.
- **A table read once per call where once per finder would do is a count, and the ratio can be large.** Reading the zone position table per `certain_timezone_at` call - one file open, header parse and mapping for a 890-byte immutable array - measured 48.1 ms -> 2.90 ms per 500 calls once read per finder, 21 of 21 rounds. Construction pays one `None` assignment for the lazy read.
- **A converter-only change moves no statement on the query path, and the question it owes is about the fixtures instead.** Two such changes moved a few cells of the packaged index each; the committed fixtures were *checked* against those cells rather than assumed clear, which is what establishes that no fixture point changed stratum and none needed regenerating. `docs/benchmark_results_*.rst` were deliberately not re-measured, because re-running them replaces every committed figure with a fresh machine's for a change nothing can resolve; `docs/data_report.rst` was regenerated, since it counts the index rather than timing it.
- **Adding a check to a public method while the internal callers move onto private accessors with identical bodies is inert**, and the ladder above it does not change.
