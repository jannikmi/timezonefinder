# BENCH-2 — the committed benchmark pages are measured on whichever machine happens to render them

## Related memory

- [Benchmarking and performance validation](../../../development/benchmarking-and-performance-validation.md)
- [Prepare and publish a code release](../../../workflows/prepare-and-publish-code-release.md)
- [Benchmarking tooling and dependency decisions](../../decisions/benchmarking-tooling-and-dependency-decisions.md)
- **Location:** `Makefile`'s `reports` target and the `benchmarks` / `latency` / `memory` targets it depends on, `scripts/render_benchmark_reports.py`, the `measure` job in `.github/workflows/benchmark.yml`, and the report-refresh step in the code-release workflow.
- **What it is.** `docs/benchmark_results_*.rst` are the package's published performance claims, and they are rendered only by a human or agent running `make reports` on whatever machine is in front of them. CI never renders them: the `measure` job records the tracked core subset (`benchmarks-ci`) and a memory footprint, uploads them as artifacts and compares head against merge base — it does not run the full suite, the latency measurement or the renderer. So the pages carry one unrepeatable local run, and a busy host inflates their dispersion columns without touching the code they describe.
- **Why it is ranked here:** it is not a package defect and no user-visible behavior depends on it, but the pages are what the documentation asserts about performance, and today nothing can reproduce or check them. It sits above the readability work and below anything that changes an answer.
- **The failure it removes, observed rather than supposed.** PR #581 shipped PERF-1 without regenerating, so `master` published `timezone_at_land()` at 5.32 ms — #580's figure, measured before the regex removal. A local re-run of the merged code gave 4.81/4.83 ms. The release workflow now checks for exactly this staleness, which makes the gap visible; it does not make the replacement measurement reproducible.
- **The shape that fits this repository: CI renders, the release consumes.** Add a dispatchable job that runs `make reports` on a runner and uploads the rendered pages as an artifact; the release's refresh step downloads that artifact for the release SHA and commits it, instead of measuring locally. This is the mechanism the data pipeline already uses — `compile_data.yml` produces a wheel, `DATA_BUILD_RUN` records the run id, and every consumer takes the artifact from it — so it adds a pattern the repository already maintains rather than a new one.
- **Why the renderer must not commit from CI.** The `pull_request` half of `benchmark.yml` deliberately holds no write permissions and no secrets because it executes untrusted head code, which is why the comparison comment is posted by the separate privileged `benchmark-comment.yml` over `workflow_run`. A job that commits rendered pages to `master` would add an unattended write path to the branch — the same class of exposure GH-501 exists to gate — for a file a release already touches by hand. Uploading an artifact keeps the measurement in CI and the commit in the release.
- **What it costs to run.** `make reports` is the full `benchmarks` suite plus `latency` plus `memory` plus the data report, under `--isolated --group test --group compare`; the CI job today installs neither the `compare` group nor the full suite. So this is materially heavier than `benchmarks-ci` and belongs on `workflow_dispatch` — dispatched by the release — rather than on every push to `master`.
- **Trade-off:** it replaces one uncontrolled variable with another. A local run varies with whatever else the machine is doing, which is unbounded and invisible in the page; a CI run varies with which CPU the pool serves, which is bounded, measured and printable. `ubuntu-latest` spread the tracked min 134-158 % across 11 runs of an identical lookup path purely on hardware, so a CI-rendered page must print the CPU (`scripts/describe_benchmark_machine.py` already produces it) or it trades a knowable error for an unknowable one.
- **Decision needed:** should the published pages describe CI hardware instead of the maintainer's machine? They currently read *Measured on Darwin arm64, Python 3.14.2* — the configuration a reader is most likely to share — and moving them to CI changes that to a Linux x86_64 runner of an unpinned CPU class. **(a)** Render in CI and publish the runner's numbers: reproducible, checkable, and re-renderable by anyone, at the price of documenting hardware no user has and absolute figures that move ~1.5x with the pool. **(b)** Keep rendering locally and rely on the release-time noise gate: the numbers stay representative of a real desktop, but no second party can reproduce them and the gate can only reject a run, never improve one. **(c)** Render both — CI for the tracked tables, local for the cross-package comparison, which needs `tzfpy` and is about relative standing rather than absolute speed. Recommended: **(a)**, because the pages' purpose is to be checkable and a printed CPU class makes their error legible, where a busy laptop's does not.
- **Validation:** the rendered artifact must be byte-reproducible against a re-run on the same CPU class within the noise threshold `scripts/benchmark_noise.py` derives; the release step must fail when the artifact's commit does not match the release SHA, the same way the data wheel's run id is checked; and a test must assert the pages name the machine they were measured on.
- **Status:** needs a decision — the option above; the implementation is otherwise specified and free.
- **Last touched:** 2026-09-02 — recorded after #581 published a pre-PERF-1 figure and the release workflow gained a staleness check that cannot make the replacement reproducible.
