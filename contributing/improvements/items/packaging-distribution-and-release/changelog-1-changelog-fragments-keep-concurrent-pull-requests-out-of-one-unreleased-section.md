# CHANGELOG-1 — changelog fragments keep concurrent pull requests out of one unreleased section


## Related memory

- [Changelog and release-note policy](../../../development/changelog-and-release-note-policy.md)
- [Prepare and publish a code release](../../../workflows/prepare-and-publish-code-release.md)
- **Location:** the `X.X.X (unreleased)` section of `CHANGELOG.rst`, the changelog policy that sends every non-exempt pull request there, and the code-release workflow that rewrites and dates that section.
- **What it is.** Every non-exempt pull request edits one file, and internal changes append at the same `Internal:` boundary. The current unreleased section spans roughly 160 physical lines, so independently authored changes repeatedly contend on a release artifact whose final curation is needed only once. Rebasing each pass onto current `master` shortens the conflict window but does not remove this shared append point.
- **Why it is ranked here:** this is an unblocker for concurrent improvement passes rather than a package defect. It removes the remaining routine cross-PR merge hotspot after discovery coverage was split, but it sits below correctness, format, and measurement work because conflicts are recoverable and affect contributor throughput rather than runtime behavior.
- **Recommended transition:** leave the existing unreleased bullets in `CHANGELOG.rst` as a frozen baseline and require each new non-exempt change to add one uniquely named plain-RST fragment instead. The next code release combines that baseline with the fragments, performs the policy's existing end-state rewrite, dates the result, consumes the fragments, and starts a fresh empty unreleased section. This avoids turning every existing bullet into a migration file while removing new author-time edits to the central changelog immediately.
- **Fragment contract:** encode user-facing versus `Internal:` placement in the filename or directory rather than inside prose; keep one user-visible change per fragment; retain the existing credit and provenance form in the fragment text; and reject empty, malformed, unclassified, or duplicate fragment identities. Contributor-memory-only changes remain exempt and create no fragment.
- **Implementation seam:** use a repository-local assembler and validator with no new dependency. It must order inputs deterministically, render a reviewable combined unreleased section, preserve all dated history below it, and make release preparation fail when unconsumed fragments or an invalid rendered changelog would be published.
- **Trade-off:** authors lose an always-materialized single-file preview of unreleased notes between releases and gain independent merge units. A deterministic preview command and CI validation preserve reviewability; `CHANGELOG.rst` remains the published release artifact, so users and packaging do not depend on RST include directives or fragment-aware renderers.
- **Validation:** structural tests cover classification, uniqueness, deterministic ordering, credit-bearing RST, the contributor-memory exception, and fragment consumption. A migration fixture proves that combining the frozen baseline with fragments changes no existing unreleased text before intentional release curation, and the release workflow test proves that a release cannot leave fragments behind.
- **Not solved by stacking or a merge queue.** Basing an independent pass on another open pull request serializes it behind unrelated work, while a merge queue can only discover and replay the same content conflict later. Both remain useful for true dependencies or final integration, but neither removes the shared edit.
- **Status:** open — free; the transition and acceptance criteria are specified, and the file layout is a small reversible contributor choice.
- **Last touched:** 2026-09-01 — recorded after the discovery-coverage map was split to remove the same concurrency bottleneck from contributor memory.
