# PYPI-1 — the PyPI project holds 11.37 GB of pre-split releases


## Related memory

- [Data distribution, packaging, and release decisions](../../decisions/data-distribution-packaging-and-release-decisions.md)
- **Location:** not the repository — the `timezonefinder` project on PyPI. Split out of GH-317, which was about artifact *count* and is answered; this is what was actually driving that issue.
- **The numbers, re-read off the index 2026-08-29 and unchanged from 2026-08-20:** 11.37 GB across **241 files and 57 versions**, against a nominal 10 GB project quota that was already hit once (a support request and the deletion of every release up to 3.4.2 recovered the space; 3.4.2 is still the oldest surviving version, so that cleanup is visible in the history). The project already sits *above* the nominal figure, so the granted limit has been raised at least once and its current value is not something the index reports.
- **The cause, and the cut line is finer than "pre-8.x".** Every release that bundled the boundary data runs 28–55 MB per file, and that includes 8.0.0 through 8.2.5 — 8.2.x are in fact the **largest per-file in the whole project** at 55.0 MB. Pre-8.x is 9.89 GB across 48 versions and 203 files; the data-bundled 8.x adds a further 1.48 GB. A deletion would have to choose its boundary rather than inherit one.
- **The pressure has already been removed by something else.** Storage added per year: 3.32 GB in 2024, 4.53 GB in 2025, 0.92 GB in 2026 to date. **8.3.0, uploaded 2026-08-19, is the first release after the distribution split: 1.0 MB across 4 files.** From it forward a code release adds ~1 MB rather than ~500 MB, so the growth rate that made the quota a live concern is approximately zero. `timezonefinder-data` carries the payload in a project of its own with its own quota, holding 51.94 MB — order 190 data releases of headroom.
- **Decided 2026-08-29 by the maintainer — leave the releases in place. Deleting published releases is a last resort, taken only when the project's storage is actually full, never as routine hygiene.** That is a standing rule about published artifacts rather than a reading of this project's growth curve, and it is deliberately the stronger ground: it holds whatever the growth rate turns out to be, so a later pass cannot revive the deletion by re-pricing the headroom. **It generalises past PyPI to any published artifact this project has handed to someone else**, and is recorded here rather than in the [distribution and release decisions](../../decisions/data-distribution-packaging-and-release-decisions.md) only because that module is at its word budget — this item is `conditional` and therefore never deleted, so the rule keeps a permanent home. The trigger is the index refusing an upload, never a size reading.
- **Refused, with the reason each loses.** *Delete pre-8.x* (48 versions, recovering 9.89 GB) and *delete everything data-bundled through 8.2.5* (56 versions, recovering the full 11.37 GB) both spend a permanently irreversible action — PyPI never re-accepts a version number, and a deletion breaks every pin and every lockfile hash referencing it — to buy headroom against a growth rate the split has already flattened. The second is the worse of the two on the same reasoning, reaching one release back from current. *Yanking* is not the softer version of this: it is reversible but **frees no storage**, so it answers a different question.
- **What would make this live**, and it is the only thing that would: PyPI actually refusing an upload. That is the whole trigger, and it is deliberately the latest possible one — a warning that the limit is near is advance notice that the question is coming, not authority to delete, and a size reading is not evidence at all, since 11.37 GB against a limit that has already been raised says nothing about how much is left.
- **Unpriced, deliberately:** per-version download counts. pypistats exposes no per-version endpoint, so "does anybody still install 6.5.9" needs BigQuery rather than one command. The project runs ~230k downloads/day overall, so even a small tail is a real number of installs — which argues the same way as the decision, and did not need measuring to do so.
- **Value:** none until the trigger fires. Nothing in the register depends on this item.
- **Status:** conditional on PyPI actually refusing an upload — not a candidate for any pass, and not routine cleanup.
- **Last touched:** 2026-08-29 — put to the maintainer and decided; numbers re-verified against the index, the 8.x half of the cut line corrected, and the post-split growth rate established.
