# GH-332 — reduced timezone dataset as a second distribution


## Related memory

- [Data distribution, packaging, and release decisions](../../decisions/data-distribution-packaging-and-release-decisions.md)
- [Improvement sequencing and preconditions](../../improvement-sequencing-and-preconditions.md)
- **Tracks:** issue #332, which carries the reframing and the costs.
- **Why it is ranked here:** 63 zones instead of 444 on the 2026c release — counted from the vendored table rather than remembered; "~90" was in the entry and in `docs/data_format.rst` until it was checked — and the distribution split turned it from a build-time switch into a packaging decision.
- **Decided, 2026-08-21 — no hand-maintained mapping.** Shipping with one was declined: until the official table exists it is the same liability the zone-precedence engine was rejected for. That decision stands and is unaffected by what follows; only its precondition changed.
- **Unparked, 2026-09-02; unblocked, 2026-09-03.** The official table exists and is now in the tree: `tests/fixtures/reduced_zones/mapping.json` holds the release asset verbatim, `source.txt` beside it records the release and digest it was verified against, `update_data.sh` re-takes it with every data update, and `tests/auxiliaries.py:convert_to_reduced_timezone` converts a location expectation through it whenever the packaged data is the reduced variant. So the mapping half is done and this entry no longer waits on anything.
- **Status:** needs a maintainer decision on whether the reduced dataset is published at all, and as what. Nothing sequences it any more, so this is the only thing left in front of it. Note what the vendored mapping does *not* cover: it converts a zone name, so the expectations reached through `single_location_test` hold on either dataset, while the ocean cases in `TEST_LOCATIONS_AT_LAND` do not — under the reduced data an ocean zone merges into a *land* representative, which changes what `timezone_at_land` returns rather than what it is called. That is this item's work, not a gap in the mapping. The costs on the issue are unchanged; they were never the reason for the park.
- **Decision needed:** does the reduced `timezones-now` dataset become a published artifact, and in what shape? *Consequences:* the mapping, the converter switch (`update_data.sh --dataset=same-since-now`) and the test-suite conversion already exist, so what is left is entirely a packaging and release commitment — and the shape chosen decides whether the remaining work is a release-pipeline change or a documentation change. Reversal is the expensive part: a PyPI project name is claimed permanently and its releases cannot be deleted, and PYPI-1 already records this project holding 11.37 GB. *Options:* **(a)** a second distribution, `timezonefinder-data-reduced`, versioned on the same `<format>.<year>.<letter>` axis and installed instead of `timezonefinder-data` — the shape the 2026-08-06 comment on issue #332 proposed, buying a user a ~63-zone dataset with one dependency swap, at the cost of a second release axis to keep in step with the format version, a second ~52 MB-per-release PyPI project, and every zone name in `README.rst` and `docs/1_usage.rst` becoming dataset-dependent (the failure that already put `'Europe/Paris'` on eleven full-dataset examples). **(b)** ship nothing and document the build: the converter switch is real and works, so the reduced dataset stays a thing a user compiles, and this item closes as documentation. Costs nothing, keeps one release axis, and leaves the dataset out of reach for anyone who cannot run the converter — which is most of the people who want it. **(c)** publish it as an extra file set inside the existing `timezonefinder-data` wheel, selected at runtime. One release axis and one project, but it makes the download larger for every user in order to serve the users who wanted it *smaller*, which inverts the point. *Recommendation:* (b) until somebody asks for (a) by name. The item has been open since 2024 with no user in it asking to install a package; the concrete demand on record is for a smaller footprint, which (c) actively defeats and which the converter route already serves. *Reversibility:* (b) → (a) later costs nothing beyond the work itself; (a) → (b) means a published project that has to be yanked or left stale. *Unpriced:* how many of the ~63-zone dataset's would-be users can run the converter at all, and whether a second data axis stays in step across a `DATA_FORMAT_VERSION` bump without a second ordered release rehearsal.
- **Last touched:** 2026-09-04 — briefed for a decision once re-verification found nothing technical left in front of it.
