# DATA-BINARIES — stop committing the packaged data binaries


## Related memory

- [Data distribution, packaging, and release decisions](../../decisions/data-distribution-packaging-and-release-decisions.md)
- **Tracks:** nothing open. It was decision 2 of #446, which is closed; this entry is now its only home, which is why it carries the reasoning rather than a link.
- **What it is:** the data is already its own distribution (`timezonefinder-data`), but its binaries are still committed, at `packages/timezonefinder-data/timezonefinder_data/data/`. Until they stop being committed, every regeneration still adds ~61 MiB to this repository's history permanently, which is the constraint that makes all the data-format work expensive.
- **Value:** this is what dissolves the regeneration cost, and it unblocks FMT-2 and GH-522.
- **Both additive halves have shipped, and the blocker they waited on is gone** — `timezonefinder-data 2.2026.3` published on 2026-08-30, so the version the workspace pins resolves.
  - **Consuming.** `make bootstrap` (`scripts/bootstrap_data.py`) fetches that release, verifies its SHA-256 against the digest the index publishes, unpacks only `timezonefinder_data/data/`, and records which version it unpacked in `packages/timezonefinder-data/.bootstrapped-data-version` — beside the data directory, because everything inside it is package data and would be published with the next wheel. `make test`/`testint`/`testall`/`reports` and `tests/auxiliaries.py` refuse a missing *or stale* dataset by name. **Verified against the real artifact:** the fetched dataset is byte-identical to the committed one.
  - **Releasing.** `check_data_updates.yml` builds the wheel from the data it just compiled, uploads it as `artifact-data-wheel`, and records its run id in the root `DATA_BUILD_RUN`, which the same commit carries to the tag; `build.yml`'s `make-data-wheel` and `publish_data.yml` both obtain it through `.github/actions/obtain-data-wheel`, which downloads that artifact and builds only when no recorded run offers one. `tests/test_data_wheel_handoff.py` holds the agreements that would otherwise fail silently. **The artefact is bound to the tree, not just to the version** — review of #572 found that the filename settles only which release a wheel claims, while the package also ships a module and a licence, so a change landing on master inside the minutes an update takes to merge would be in the tagged tree and not in the wheel. The action accepts the artefact only when every *tracked* packaged input matches it, which is compared against `git ls-files` rather than the directory so the same rule survives the data no longer being committed: a wheel may carry payload the checkout lacks, never the reverse. Every mismatch falls back to building, because the tagged tree is on master and master's run tested it, and a tag that cannot publish is the one state this pipeline has no recovery for.
- **What remains is one step, and it is the destructive one.** Git-ignore `packages/timezonefinder-data/timezonefinder_data/data/`. It is decided and needs no maintainer question, and it is what makes every checkout depend on the two halves above already existing. Three things it owes:
  1. drop the data paths from the update job's `git add -A`;
  2. re-point whatever in `tests/test_package_contents.py` reads the committed tree rather than a built artifact;
  3. point `build.yml`'s *test matrix* at the same artifact `make-data-wheel` already takes — **not** at `make bootstrap`, which resolves the *published* wheel and would hand CI the previous release's data while the tag ships the new one. `make bootstrap` stays the path for a dev checkout and for CI on every pull request that is not a data update: one path per question, not one path overall. The matrix still reads the tree today, which is exactly why the hand-off could be verified against it.
- **Why the split.** The whole migration is not one reviewable, releasable pull request, and half-landing it is the expensive failure: the subtractive step is what makes the repository unusable if either additive half is missing. Additive first, exactly as the deliverable rule prefers.
- **Accepted costs, restated so they are not re-litigated:** `git bisect` across a format change stops working from a bare checkout unless the matching data version resolves per commit; and this does **not** shrink the existing 357 MiB pack — only GH-522 does, and strictly after this is in force, or the next data update re-adds ~61 MiB and the rewrite has to be repeated.
- **Decided, 2026-08-21 — keep the workspace member, git-ignore its `data/`, fetch it in one bootstrap step.** Chosen over resolving `timezonefinder-data` from PyPI (which would need the workspace source override put back for every format change, and makes a dev checkout's data version a resolver outcome rather than a stated one) and over Git LFS (which reclaims none of the existing history and puts a bandwidth quota in front of every fork and CI run).
- **Decided 2026-08-24 by the maintainer — the update job builds the wheel and the tag publishes that artifact.** **Why, and it is the property everything downstream leans on:** `publish_data.yml` states in its own header that the data is not re-validated at publish time because "it was compiled and checked by build.yml on the pull request". The update PR's matrix validates the exact bytes that ship, and this is the only option that keeps that true. It also keeps the bootstrap non-circular — the wheel is built by the job that generated the data, not by one that would have to regenerate it. Implemented as described above.
- **Refused, with the reason each loses.** *The publish job regenerates* — self-contained and reproducible from the tag alone, which is the one real thing it has, but it publishes bytes no CI run ever saw and makes every release depend on the upstream asset still being fetchable. **Refinement recorded so the refusal is not read as stronger than it is:** the converter is byte-deterministic — a fresh conversion of 2026c's upstream GeoJSON reproduced the packaged binaries exactly — so regenerating would in practice yield the bytes CI validated. What remains against it is narrower than "untested bytes": determinism was shown on one machine with one toolchain, and a release asset can be replaced upstream after the pull request was tested. The decision stands, on the narrower ground — and the implementation keeps regeneration as the *fallback*, for a release prepared outside the pipeline, rather than as the path a pipeline release takes. *A second repository for the binaries* — keeps them committed and reviewable, and re-poses this same question one level up; a data repository was already refused once on its own merits. *Leave the binaries committed* — this is the do-nothing option and it also drops GH-522. Upstream shipped 2 releases in 2024, 3 in 2025 and 4 in the first seven months of 2026; at ~61 MiB a regeneration that is ~244 MiB in those seven months alone — an annualised ~420 MiB onto a 357 MiB pack, and the cadence is still rising.
- **The carrier, and why it is a committed file.** A **published** GitHub Release cannot carry the wheel: `build.yml` fires on `release: types: [published]`, and `publish_data.yml` deliberately creates no Release precisely so that trigger cannot fire for a data tag; a draft release never published would work and sits one click away from firing it. So the run artifact carries the wheel — and the *run id* has to reach a tag push, which sees only the tagged tree and the API. Hence `DATA_BUILD_RUN`, committed with the data it describes, in the same family as `DATA_VERSION` and `DATA_SOURCE`; `update_data.sh` clears it, so "regenerated outside the pipeline" and "built by run N" cannot look alike. Version-addressing the artifact instead would need no file, but two runs can upload the same name and only the run id says which one produced the committed tree. Also worth not re-deriving: the recorded dead end *"reusing the master run's build artifacts on the tag run buys almost nothing"* **does not transfer to data** — it was measured on code wheels, where the copyable half (~1 min) was cheap next to the matrix (~10 min), whereas here the build *is* the expensive half.
- **One mechanic the bootstrap half found, worth not re-deriving.** The presence check cannot live where the data is read, and it cannot be a pytest hook: `tests/auxiliaries.py` builds a `PolygonArray` at *module import* and `tests/conftest.py` imports it, so `pytest_configure` runs after the `FileNotFoundError` has already been raised. The guard sits in `auxiliaries.py` ahead of that construction, which is the suite's single choke point on the dataset.
- **Status:** open — both additive halves shipped; git-ignoring `data/` is all that remains, and it is decided. Unblocks GH-522.
