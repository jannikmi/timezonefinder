# BUG-6 — `TimezoneFinder.cleanup()` releases nothing in the mapped mode


## Related memory

- [Query performance and shortcut decisions](../../decisions/query-performance-and-shortcut-index-decisions.md)
- **Location:** `timezonefinder/timezonefinder.py`, `AbstractTimezoneFinder.cleanup` and `__exit__`; `timezonefinder/polygon_array.py`, `PolygonArray`.
- **Defect.** `cleanup()` calls `close_resource(self.boundaries)` and `close_resource(self.holes)`, but `PolygonArray` has no `close()` — `close_resource` swallows the `AttributeError` and returns. Nothing reaches `FileCoordAccessor.cleanup()`, and `cleanup()` does not drop `self.boundaries` either, so with `in_memory=False` the coordinate file handle and its mapping stay open after `tf.cleanup()` and after a `with TimezoneFinder() as tf:` block exits. Reproduced on `master` at c27b452: `coord_file.closed` and `coord_buf.closed` are both `False` after the context manager exits, and the accessor still has its `words` attribute. Both are released only when the finder is garbage collected, which is what the context manager exists to make unnecessary.
- **Why it is written up as a defect rather than a cleanup.** `__exit__` is a documented public seam whose entire purpose is deterministic release, and a caller who opens finders in a loop under `in_memory=False` accumulates two open descriptors and one mapping per iteration until collection. It is not a wrong-answer defect, so it does not take the ranking's absolute top; it ranks on expected value like anything else.
- **What is already in place, so this is small.** `FileCoordAccessor.cleanup()` is correct on its own: called directly with no caller-held view it closes both the file and the mapping, and a caller's live view still refuses the close deliberately. What is missing is a route from the finder to it — `PolygonArray` needs a `cleanup()`/`close()` that drops `packed` before `coordinates` (its `__del__` already establishes that order and states why: on the C backend the wrapped buffers hold the mapping open), and `AbstractTimezoneFinder.cleanup()` needs to call it and drop its references.
- **The trade-off to name before implementing.** Making `cleanup()` actually release means a finder used after `cleanup()` raises `AttributeError` where it previously kept answering, because today's no-op leaves it fully usable. That is the documented contract already — `FileCoordAccessor.cleanup` says "the accessor must not be used afterwards" — but it has never been enforced through the public class, so it is a behaviour change a user could be relying on by accident, and it needs a changelog bullet in the main list rather than under `Internal:`. Check whether any test or example reuses a finder after `__exit__` before assuming nobody does.
- **Not on the lookup path.** Teardown only; no query-path measurement is required.
- **Status:** open.
- **Last touched:** 2026-09-06 — recorded while the accessor's own `cleanup()` ordering was fixed, which is what made the missing route from the finder visible.
