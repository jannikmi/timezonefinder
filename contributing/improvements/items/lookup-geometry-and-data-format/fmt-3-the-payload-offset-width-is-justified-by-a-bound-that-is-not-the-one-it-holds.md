# FMT-3 — the payload-offset dtype is justified by a bound 26x smaller than the one it holds

- **Location:** `timezonefinder/configs.py` — `BLOCK_PAYLOAD_OFFSET_DTYPE`; `timezonefinder/block_payload.py` — `derive_payload_offsets`; `timezonefinder/polygon_array.py` — `PolygonArray.__init__`.
- **What it is.** Both memory sites describe the array as ring-relative. `configs.py`: "Where a block's residuals begin **inside its own ring's payload** ... unsigned 32 bit because the largest packaged ring's payload is ~1.2 MB." `derive_payload_offsets`: "**Ring-relative rather than file-relative**, so that the kernels take the same word offset whether the payload came out of a mapping or out of a preloaded copy." **Neither is true of the array the kernels are handed.** `PolygonArray.__init__` immediately adds `self.coordinates.word_offsets` to it, making every entry an absolute word index into the whole collection's buffer — which the surrounding comment says plainly ("Made absolute against the coordinate buffer here"), and which both accessors support because each exposes the whole buffer as `words`.
- **The bound that actually applies, measured over the packaged 2026c data:** the boundaries collection's largest absolute offset is **7,933,908 words (~31.7 MB)** in a buffer of 7,933,923; the holes collection's is 23,703. The recorded justification bounds ~1.2 MB — the largest single ring — so it is the right dtype for the wrong reason, by a factor of ~26.
- **The failure mode, and why it is worth an entry rather than a comment fix in passing.** Nothing guards the absolute offsets. `validate_block_index` checks the *stored* `BLOCK_OFFSET_DTYPE` column; the absolute payload offsets are derived at load time and the `+=` in `PolygonArray.__init__` is unsigned 32-bit arithmetic that wraps silently. Today there is 540x of headroom, so this is not a live defect — but the next person asked whether the width still fits will check it against the stated bound, and the stated bound is not the quantity at risk. This is exactly the pairing the [narrow-dtype rule](../../improvement-register-rules.md) exists for: pick the narrowest dtype that fits, and state the bound it has to fit.
- **The fix.** Rewrite both claims to describe the absolute offset and bound it by the collection's payload size; move `derive_payload_offsets`' rationale sentence to say why the rebasing happens in the caller rather than asserting the opposite; and add the width check where the data is produced (`timezonefinder/_data_integrity.py`, beside `validate_block_index`) so the bound is checked rather than reasoned about. ~30 lines including the test.
- **Amend rather than append:** the ring-relative sentence has to be *replaced* in both files. Left standing above a correction it is the retired answer a skimming reader takes.
- **Status:** open — free, small, ranked low because no answer is wrong today.
- **Last touched:** 2026-09-05 — found in the query-flow discovery round while checking the packed payload's dtype widths.
