# FMT-1 — a latitude block index over the boundary polygons

- **No issue tracks this, so this entry is the complete record.** It supersedes GH-449 together with [FMT-2](fmt-2-a-frame-of-reference-payload-for-the-boundary-coordinates.md); issue #449 is left as it stands, describing a proposal that measurement refused, and nothing reads it any more.
- **What it is.** Split every boundary polygon's vertices into fixed blocks and store, per block, the range of latitudes its edges span. Ray casting then skips whole blocks whose range excludes the query latitude. The coordinate payload stays `int32` and byte-identical — this adds an index *beside* the coordinates rather than re-encoding them, which is what makes it separable from FMT-2 and cheap to review.
- **Why it is ranked at the top.** It is the only free item that gates the held format-2 window, and therefore the 2.x data release, DATA-BINARIES, GH-522 and the whole pending code release. On its own merits it is also the largest measured query win available: vertex-proportional time is **~30 % of a uniformly random workload's mean and ~49 % of `on_land`'s**, and the change removes ~98 % of the work that share pays for.
- **The count, which is the figure that travels.** Over the 4,827 real (point, polygon) pairs the `on_land` and `ambiguous` fixtures produce, today's kernel performs **70,992,626 edge tests**. At 128 vertices per block that becomes **1,398,797 edge tests plus 557,074 block range tests** — about 36x less geometry work, weighting a block test as one edge test. 32 and 512 were measured too (27x and 15x); 128 is the optimum, and the block size stays a tuning parameter for the implementing pass rather than a decided constant.
- **Where the tail actually is, since that is what motivated this.** Per-query `timezone_at` on the clang path in the default mapped mode: `on_land` runs p50 1.00 µs against **p99 39.71 µs and p99.9 82.58 µs**, and slicing that stratum by its own latency gives 0.94 µs / 0.00 point-in-polygon calls at p0-50 against 54.54 µs / 1.20 calls / **82,195 vertices** at p99-100. Time correlates with vertices tested at 0.92 and with candidate *count* at 0.76 — the tail is one ray cast across a huge ring, not many candidates. Read adversarially it still holds: in the largest polygon (192,960 vertices) the *worst* latitude anywhere touches 736 vertices at 32 per block, 0.38 %.
- **Why the answer cannot change, which is the property the whole item rests on.** The kernel flips parity on `(y > y1) ^ (y > y2)`, i.e. `min(y1,y2) < y <= max(y1,y2)`, so a flipping edge always lies inside a block whose stored range contains the query latitude — a skipped block provably contains no flipping edge. And parity is a sum mod 2 over *independent* per-edge predicates: the loop's `y1 = y2` carry is a cached comparison rather than a dependency, so blocks may be visited in any order or not at all. Both were verified rather than argued — `prototypes/polygon_block_encoding.py` replays 1,463 real query pairs across 410 polygons against `utils.inside_polygon` with **0 disagreements**.
- **What it costs, and the risk that decides it.** The filter has to live *inside* the C and numba kernels. The same filter written in numpy costs 2.73 µs per query at 128 vertices per block on the largest polygon — dispatch charged to every query however few blocks survive, which would swamp the ~1 µs median. So this is a kernel signature change on both backends (`(x, y, coords(2,N))` becomes view-plus-block-index, and numba's eager signature moves with it), not an addition around them. **That, not the index, is where the pass will spend its time**, and it is the reason the work count above is not yet a wall clock.
- **What it adds to the file:** ~0.50 MB at 128 vertices per block (one `int32` pair per block over 62,649 blocks), against 63.40 MB of coordinates. 29.7 % of polygons fit in a single block and pay one comparison for nothing; the median polygon is 3 blocks. Small polygons are already ~850 ns, so the item neither helps nor hurts them.
- **Measuring and publishing the latency difference is part of this item, not a follow-up — decided 2026-08-30 by the maintainer.** The reason it has to be stated is that **the tracked suite cannot see this win**: `benchmarks/test_timezone_finding.py` calls `benchmark(_run_over, tf.timezone_at, points)`, so one round is one pass over a 2,500-point batch and the tracked estimator is the `min` over rounds. A per-query distribution is averaged away before any estimator sees it, which means the change would be reported as a shift in a batch mean while the thing users actually feel — p99 and p99.9 — goes unmeasured and unstated. The deliverable therefore includes a per-query timing harness over the committed fixtures reporting p50/p90/p99/p99.9 before and after, on the clang path in the default mapped mode, and a published page saying what moved. `prototypes/polygon_block_encoding.py` already contains the harness in runnable form; what it does not have is a home in `benchmarks/` and a report page.
- **Three documentation targets, and the third is the one that would otherwise go stale silently.** `docs/benchmark_results_timezonefinding.rst` is where the distribution belongs; `docs/benchmarking_methodology.rst` has to say why a per-query distribution is reported beside the batch estimators rather than instead of them, since its whole estimator discipline is written for the batch form; and `docs/alternatives.rst` currently tells readers that `tzfpy` is faster "by more than an order of magnitude on the points that cost this package the most", which is exactly the row this item moves. Re-measure `benchmark_results_comparison` and restate that row rather than leaving a claim the change has invalidated.
- **Adjacent but not the same as BENCH-1**, which is about base-versus-head *comparison* tooling drifting between two runs. This is about resolution within one run: even a perfect comparison of two batch means cannot express a tail. Neither blocks the other.
- **Choosing where each ring starts is measured and refused — including starting at the minimum-latitude vertex, which is *worse*.** Blocks partition a ring from its first vertex, so the stored start index looks like a free parameter worth optimising; only offsets in `[0, B)` are even distinct, since rotating by a whole block relabels blocks without repartitioning them. Swept over the real query pairs: min-latitude start **1.026x** the edges of the shipped order, max-latitude 1.010x, the best single offset 0.988x, the per-polygon optimum 0.942x and the per-polygon worst 1.057x. **The mechanism is the seam** — a block's range includes its bridging vertex and the last block's bridge wraps to vertex 0, so putting a latitude extreme there stretches exactly that block; it survives 840 of 4,827 tests in shipped order against 1,367 rotated to min-latitude, which more than accounts for the whole regression. The entire rotation space spans ~5.7 % against the 36x the index itself buys, and the per-polygon optimum needs a stored offset per polygon plus a build-time search to save ~6 % of ~2 %. **Do not re-propose a canonical ring start for the index's benefit.** Note what is *not* the objection: `canonical_ring_key` in `scripts/utils.py` rotates only to build a comparison key and never rewrites a stored ring, so hole deduplication is rotation-invariant by construction and would survive any rotation — the idea is safe, just not worth it.
- **Format consequences.** Bump `POLYGON_LAYOUT_VERSION` to 2 and update `DATA_FORMAT_LAYOUT_VERSIONS` to match, but **leave `DATA_FORMAT_VERSION` at 2** — `tests/test_data_version.py::test_the_format_version_moves_with_the_layouts_it_is_made_of` wants the record to agree with the layouts in force, not the generation number to move. This is what rides the held window, and the [batching decisions](../../decisions/data-format-version-marker-and-release-batching-decisions.md) carry the exit condition: the hold ends when this item lands or is rejected. A format change cannot half-land, so it is prototyped and measured before it is migrated in one piece.
- **Not blocked by GH-542.** The precision question never touched this item — the payload is unchanged — and it no longer gates FMT-2 either, for the reason recorded there.
- **Status:** open. Gates the held 2.x release and the whole pending code release queued behind it.
