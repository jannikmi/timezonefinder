## Why it is recorded

Measured 2026-10-11: a grid tree — a dense grid aligned with longitude and latitude whose cells several zones can own refine into fixed blocks, every level reached by arithmetic — beats the resolution-4 H3 index on every axis measured, at less than H3's footprint. The recommended shape answers whole `timezone_at` calls about 29 % faster on random points and 27 % on land, 256-point batches 2.4–3.5x faster, tests 57 % and 42 % fewer polygons, and holds half H3's resident index memory, on both kernels. The decision record holds the numbers, the instrument and the refused variants; the grid-tree shapes were priced at the maintainer's request. What remains is whether to adopt it, which only the maintainer can decide: it changes the data format, the published dependencies and `TimezoneFinderL`'s answers, and undoing it takes another format release.

## What adopting it changes

- **Runtime:** `timezonefinder/shortcut_index.py` reads the tree — a root table and one block array per level — instead of the H3 slot table, and every `h3.latlng_to_cell` call in `timezonefinder/timezonefinder.py` becomes the tree's integer arithmetic, scalar and vectorised. `GridTree1` in `prototypes/latlng_index_bench.py` is the reference lookup, unrolled because a generic loop over the levels lost to a flat grid. `timezonefinder/_data_integrity.py` stops checking H3's bit layout.
- **Converter:** `scripts/shortcuts.py` and `scripts/hex_utils.py` compute candidates level by level as the prototype's `build_grid_tree` and `owned_pairs` do, and the work optimizer in `scripts/shortcut_ordering.py` takes a rectangle where it takes an H3 cell (`cell_region`, `cell_cap`).
- **Format and release:** a new shortcut layout, `DATA_FORMAT_VERSION` 4 and the ordered two-distribution release, carrying the held tie-order rebuild and PERF-10's costs with it.
- **Dependencies:** `h3` leaves the runtime dependencies once nothing above imports it, which changes the published metadata.
- **A test pinning the kernel's edge convention**, because the tree's exactness rests on it: a polygon owns a point on its east or north boundary, never its west or south.
- **Answers that move:** `TimezoneFinderL` answers move cell by cell. Points no polygon owns, on the −180° meridian and the −90° parallel, take the new index's last remaining zone: 146 of 200 sampled points at exactly −180° move under the recommended tree, mostly `Etc/GMT-12` to `Etc/GMT+12` and three Chukotka land points to the ocean. Giving those points an owner, by testing −180° as +180°, would change answers under either index and is a semantics choice to make with the adoption. Overlap answers follow per-cell legacy precedence, so they can move where a cell shape regroups an overlap's polygons; all 289 sampled overlap points kept their winner, and PREC-1 would make the winner independent of the index.
- **Elsewhere:** GH-657 closes as moot; GEOM-3 is re-scoped to rectangle predicates; half of PERF-7's reopening condition is met; FT-3 is moot once `h3` is gone; LITE-1 is phrased in H3 cells and needs rephrasing; `docs/data_format.rst` and every page describing the H3 index change.

## Decision needed

- **Decision needed:** should the resolution-4 H3 shortcut index be replaced by an aligned index, and if so which? Every option below is faster than H3 on scalar and batch lookups on both kernels, holds less resident index memory, and gave H3's answer on every sampled point a zone owns; adopting one costs a format bump with an ordered two-distribution release, moves the answers listed above, and lets `h3` leave the runtime dependencies. **(a) Grid tree: 0.9375° root, one level of 4×4 blocks** (507 KB on disk and resident, 18 % and 51 % below H3): 57 % and 42 % fewer polygon tests per random and on-land query than the H3 control, `TimezoneFinderL` agreement 97.6 / 93.7 % against the shipped 95.8 / 90.0 %, `timezone_at` 29–30 % and 26–28 % faster than H3, and, timed head to head, 6.5–6.6 % and 10–12 % faster than the flat equal-area grid of H3's size. A point reads at most two arrays. **(b) A flat aligned grid**, one table read per point and the simplest format: the equal-area grid of 0.375° rows (616 KB) or the equal-angle 0.46875° or 0.5° grids (611 or 539 KB). Every one is slower than (a) per call and tests more polygons, and the equal-angle ones lower `TimezoneFinderL` agreement by up to 0.6 points. **(c) A deeper grid tree, if H3's footprint bounds memory rather than disk:** a 1.875° root with two levels of 4×4 (957 KB on disk, 55 % more than H3, and 7 % less resident) tests 77 % and 66 % fewer polygons and is 29–32 % faster per call, with `TimezoneFinderL` agreeing on 98.6 / 96.2 %. **(d) Keep H3:** the held tie-order rebuild publishes as a post-release, and GH-657, GEOM-3 and FT-3 stay as they are. **Recommendation: (a)**, ahead of H3 and of every flat grid on every measured axis below H3's footprint; (c) only on reading "replace, never add" as a memory bound, since it spends half as much disk again; (b) only if one table is worth about a tenth of the scalar call. **Reversibility:** low, since undoing it is another format bump and data release. **Unpriced:** loading and construction time, `make memory`, mapped page residency, a second machine class, the rectangle port of the work optimizer, and overlap answers beyond the sample.
- **Size:** L — refine into slices when taken; the format change itself is one atomic migration.
- **Status:** needs — whether to replace H3 with an aligned grid tree, and which shape.
