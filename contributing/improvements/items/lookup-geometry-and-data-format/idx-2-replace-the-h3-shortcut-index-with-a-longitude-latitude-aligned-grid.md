## Why it is recorded

Measured 2026-10-11: a dense grid whose cells follow longitude and latitude, computed exactly from the integer coordinates the kernel reads and aligned with the 7.5° meridians the ocean zones share, beats the resolution-4 H3 index at H3's file size. Whole `timezone_at` calls are about a quarter faster on random points and a sixth faster on land, 256-point batches 2.5–3x faster on random points and 1.6–2x on land, and the index's resident arrays are ~40 % smaller, on both kernels. The decision record holds the numbers, the instrument and the refused variants. What remains is whether to adopt it, which only the maintainer can decide: it changes the data format, the published dependencies and `TimezoneFinderL`'s answers, and undoing it takes another format release.

## What adopting it changes

- **Runtime:** `timezonefinder/shortcut_index.py` reads a grid table instead of the H3 slot table, and every `h3.latlng_to_cell` call in `timezonefinder/timezonefinder.py` becomes the grid's integer arithmetic, scalar and vectorised. `UniformGrid` and `BandedGrid` in `prototypes/latlng_index_bench.py` are the reference lookups. `timezonefinder/_data_integrity.py` stops checking H3's bit layout.
- **Converter:** `scripts/shortcuts.py` and `scripts/hex_utils.py` compute candidates as the prototype's `owned_pairs` does, and the work optimizer in `scripts/shortcut_ordering.py` takes a rectangle where it takes an H3 cell (`cell_region`, `cell_cap`).
- **Format and release:** a new shortcut layout, `DATA_FORMAT_VERSION` 4 and the ordered two-distribution release, carrying the held tie-order rebuild and PERF-10's costs with it.
- **Dependencies:** `h3` leaves the runtime dependencies once nothing above imports it, which changes the published metadata.
- **A test pinning the kernel's edge convention**, because the grid's exactness rests on it: a polygon owns a point on its east or north boundary, never its west or south.
- **Answers that move:** `TimezoneFinderL` answers move cell by cell. Points no polygon owns, on the −180° meridian and the −90° parallel, take the new index's last remaining zone: 147 of 200 sampled points at exactly −180° move, mostly `Etc/GMT-12` to `Etc/GMT+12` and a few Chukotka and Fiji land points to the ocean. Looking −180° up in the grid's last column cuts that to 27 of 200 but cannot reproduce H3, whose answers there are its own fallback; giving those points an owner by testing −180° as +180° would change answers under either index, and is a semantics choice to make with the adoption. Overlap answers follow per-cell legacy precedence, so they can move where a cell shape regroups an overlap's polygons; all 289 sampled overlap points kept their winner, and PREC-1 would make the winner independent of the index.
- **Elsewhere:** GH-657 closes as moot; GEOM-3 is re-scoped to rectangle predicates; half of PERF-7's reopening condition is met; FT-3 is moot once `h3` is gone; LITE-1 is phrased in H3 cells and needs rephrasing; `docs/data_format.rst` and every page describing the H3 index change.

## Decision needed

- **Decision needed:** should the resolution-4 H3 shortcut index be replaced by a dense longitude/latitude-aligned grid, and if so which grid? Every grid option below is faster than H3 on scalar and batch lookups on both kernels, holds less resident index memory, and gave H3's answer on every sampled point that a zone owns. Adopting one costs a format bump with an ordered two-distribution release, moves the answers listed above, and lets `h3` leave the runtime dependencies. **(a) Equal-area grid with 0.375° rows and column counts a multiple of 48** (296,832 cells, 616 KB on disk, 619 KB resident): the most selective at H3's file size, with 26 % and 6 % fewer polygon tests per random and on-land query than the H3 control, and `TimezoneFinderL` agreement above the shipped index's; scalar calls 25 % and 17–18 % faster. The format carries one column width per row. **(b) Equal-angle grid at or under H3's file size:** 0.46875° (294,912 cells, 611 KB) is the simplest lookup, one or two points faster than (a) per random scalar call and level on land, but makes 3 % more polygon tests on land than the H3 control; 0.5° (259,200 cells, 539 KB) is 12 % smaller than H3 on disk and aligned with whole degrees too, at 6 % more tests on land. Their `TimezoneFinderL` agreement is 0.2–0.6 points below the shipped index's. **(c) A larger grid, if H3's footprint bounds memory rather than disk:** the equal-angle 0.375° grid (460,800 cells) is 30 % and 22–24 % faster per scalar call and tests 34 % and 16 % fewer polygons, at 943 KB both on disk, 53 % more than H3, and resident, 8.5 % less. **(d) Keep H3:** the held tie-order rebuild publishes as a post-release, and GH-657, GEOM-3 and FT-3 stay as they are. **Recommendation: (a)**, the only option no worse than H3 on any measured axis at H3's file size, counts included, and counts are what survive a change of machine; (b) if one uniform layout is worth more than that selectivity; (c) only on reading "replace, never add" as a memory bound, since it spends half as much disk again. **Reversibility:** low, since undoing it is another format bump and data release. **Unpriced:** loading and construction time, `make memory`, the page residency of a mapped grid table, a second machine class, the rectangle port of the work optimizer, which buys the shipped H3 index one point of `TimezoneFinderL` agreement on random points, and overlap answers beyond the sample.
- **Size:** L — refine into slices when taken; the format change itself is one atomic migration.
- **Status:** needs — whether to replace H3 with an aligned grid, and which grid.
