# PERF-7 — a single-block ring pays for a block index it can never skip with

- **No issue tracks this; found 2026-08-30 while measuring the latitude block index that created it.**
- **Withdrawn 2026-09-05: both halves are gone, removed by polygon layout 3 rather than by this item.** The entry is kept because the *shape* of the mistake recurs — an overhead measured against one kernel and carried forward as if the kernel were a constant — and because the two arguments below are the ones a later pass would otherwise re-derive from scratch.
- **The per-call half was already priced out of existence, and the fix it asked for is now impossible.** 29.7 % of boundary polygons fit in a single block, and for those the latitude filter cannot reject anything: `pip_with_bbox_check` has already rejected every point outside the ring's bounding box, and a single block's latitude range *is* that bounding box's. The proposed fix was for `PolygonArray.pip` to resolve `(start, stop)` from `block_offsets` and call the unblocked kernel when `stop - start == 1`. Under layout 3 there is no unblocked kernel to call: `inside_polygon_int` / `pt_in_poly_python` read an unpacked `int32` coordinate array, and a packed ring has none — reaching one means decoding the ring per point-in-polygon test, which costs far more than the single block-range comparison it would save. What that comparison costs was already down to tens of nanoseconds when this was re-measured on 2026-08-31 (`small` 537 ns clang / 818 ns numba against `medium` 567 / 891), the packed payload having removed the per-call slice and the third `ffi.from_buffer` that were most of the original price.
- **The per-edge half — then the larger of the two — is implemented, in both kernels.** It was measured at ~48 % more per scanned edge on clang and ~96 % on numba **against the layout 2 kernel**, and named two causes: the wrap test `j = i + 1; if (j == nr_coords) j = 0` on every edge, and a latitude comparison recomputed from scratch. Neither survives in the layout 3 kernels. A block stores its bridging vertex, so both endpoints of every edge it owns lie inside it and the loop runs over the block's own `n` edges **with no wrap-around case at all** — the wrap is encoded as the last block's bridging vertex being vertex 0. And the comparison is carried: both kernels end their inner loop with `y1 = y2; y_gt_y1 = y_gt_y2`, re-seeding only once per surviving block. See `inside_polygon_packed_int` in `timezonefinder/inside_poly_extension/inside_polygon_int.c` and `pt_in_poly_packed` in `timezonefinder/utils_numba.py`, whose docstrings both state the no-wrap property as a property of the layout.
- **What generalises.** A per-edge or per-call overhead is a property of a kernel, not of a query path, so it does not survive the kernel being rewritten — and a format change rewrites it. This item's figures were taken on layout 2 and read for eleven days as if they described the code. The item did say "re-measure before taking it"; what it could not say is that re-measuring would find the work already done. An overhead item that outlives the code it was measured against should be re-read against the current kernel *before* it is ranked, not before it is implemented.
- **The bounding-box precondition still holds and is no longer this item's business**, but it is worth knowing on its own: `pip` is reached only through `pip_with_bbox_check` today, from `certain_timezone_at` and the hole loop. A future caller that skips the bounding-box check would make a single block's filter genuinely selective.
- **Status:** withdrawn — layout 3 removed the per-call half's opportunity and implemented the per-edge half.
