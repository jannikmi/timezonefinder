# PERF-8 — calibrate shortcut ordering costs against runtime benchmarks

- **Status:** open — requested by the maintainer on 2026-09-10; planning recorded here, implementation and measurement remain to be done.
- **Size:** M, roughly 250–500 changed lines for calibration, provenance and validation, excluding generated measurement artifacts; revisit after identifying reusable benchmark machinery.
- **Location:** `scripts/shortcut_ordering.py` (`CheckCost`, `ShortcutOrderer.model`, `add_pip` and the stage-weight constants), `timezonefinder/timezonefinder.py` (`inside_of_polygon`), `timezonefinder/polygon_array.py` (`HoleArray.any_contains`), and `.github/workflows/benchmark.yml`.
- **Problem:** the optimizer minimizes a geometrically integrated proxy with rounded engineering weights, not a calibrated latency model. Its assumptions include charging all hole tests and the outer PIP after a successful hole would terminate execution, fixed dispatch/bbox costs, and latitude-active block work. Improving that proxy, or comparing an area heuristic against it, does not establish a runtime improvement. Changed runtime dispatch, packed kernels or hole gates can silently invalidate both weights and approximations.
- **Value and rank:** binds future ordering decisions to measured evidence and detects model drift; rank after immediate build/test/correctness defects and before general lint/readability work. No speedup or present regression is claimed. The optimizer is on master, so this has no dependency on covered-cell collapse or a candidate-generation repair.

## Implementation plan

1. Build a reusable calibration command around the current runtime predicates. Measure stage counts separately from time; cover outer-box rejection, hole-union rejection, individual holes, successful hole termination, PIP dispatch and active/inactive packed blocks. Use representative geometry sizes and candidate-rich cells, including lists above 14 candidates. Instrumentation must not enter production lookup; verify that stage instrumentation follows the actual early exits and that uninstrumented whole-query measurements confirm its conclusions.
2. Map benchmark features explicitly to every coefficient and approximation in `CheckCost`. Fit a simple nonnegative cost model only where measurements identify its terms; report uncertainty, feature correlation and residual structure. Do not force a constant-weight explanation of systematic hole, cache or backend effects. Revise the proxy or document a bounded limitation when coefficients cannot explain them. Validate assumptions as well as fitting constants.
3. Separate calibration cells/geometries from held-out validation cells to avoid fitting and scoring the same examples. Target uniform spherical query probability, with surface-area weighting when difficult cells are oversampled. Include independent seeds/repetitions and separately report the existing ambiguous, random, on-land and unique strata. Benchmark sampling is allowed for empirical validation; keep the converter's area integration sampling-free.
4. Evaluate ordering decisions, not only prediction error: compare predicted versus measured cost differences and ranking agreement among the existing optimizer, simple area-order alternatives and the calibrated variant. Report held-out aggregate and tail latency, the cost of wrong ordering choices among those measured alternatives, uncertainty and sensitivity to coefficient perturbations. Use identical candidate membership, overlap precedence and final-zone legality for every comparison. Do not label the current heuristic a global optimum or call model-error percentages latency changes.
5. Track clang with mapped data as the primary existing benchmark configuration; verify numba and in-memory modes and check the pure-Python fallback for regressions. Record CPU, interpreter, backend, storage mode, code/data hashes, fixture identity, fitting procedure and raw benchmark artifact. Avoid making the distributed binary depend on whichever machine runs conversion: choose and document a reference calibration policy, with explicit reviewed updates to versioned coefficients.
6. Add a freshness/reporting path to the existing benchmark workflow. Changes to modeled runtime stages, geometry/block format or model inputs must identify a calibration as stale and prompt revalidation. Keep noisy timing drift reporting separate from deterministic tests for schema/provenance, coefficient validity and reproducible conversion. A benchmark run must never silently rewrite or publish production constants; thresholds must follow measured repeatability rather than an invented percentage.

## Acceptance

- Each retained coefficient and structural approximation has measured support or an explicit residual limitation, linked to a reproducible artifact and the runtime feature it represents.
- Held-out ordering comparisons show whether the calibrated model predicts actual improvements, with uncertainty and backend sensitivity. If recalibration produces no reliable gain, retaining the current constants is a valid result when the validation/provenance connection ships and the finding is recorded.
- Repeated conversion with the same data and versioned model remains byte-identical, without timers or calibration samples in conversion. Any changed constants are reviewed with regenerated shortcuts, unchanged candidate membership and lookup-policy checks, and actual whole-query benchmark results.
- Fast tests exercise the calibration artifact contract and stale-input detection; the benchmark workflow actually invokes the validation/reporting path. No noisy wall-clock assertion enters ordinary pytest.
