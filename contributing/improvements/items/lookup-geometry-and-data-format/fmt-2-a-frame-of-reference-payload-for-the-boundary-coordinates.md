- **No issue tracks this, so this entry is the complete record.** It supersedes GH-449 together with the latitude block index, which shipped on 2026-08-30 and whose item file is gone with it; what that change built is described in `docs/data_format.rst` under *Latitude Block Index* and in `scripts/block_index.py`.
- **What it is.** Store each of the shipped latitude-index blocks as a per-block coordinate frame — an `int32` origin plus a bit width — with the vertices held as bit-packed residuals against that origin, instead of as fixed 32-bit absolutes. It reuses that block structure and its byte offsets wholesale and adds nothing to the query path's shape, only an unpack step on the blocks that survive the skip.
- **What it is worth:** the packaged coordinates go **63,402,504 B → 32,699,042 B**, 0.516 of today, at 128 vertices per block and a 10⁻⁶ scale. Median block width is 19 bits against today's fixed 32 (p99 25). Since `coordinates.bin` is essentially the whole distribution, that roughly halves what a user downloads and what the repository carries until GH-522.
- **Why the precision term is settled and costs nothing to decide.** GH-542 established that the upstream source carries six decimals, not seven, so quantising to 10⁻⁶ **cannot change an answer by construction** — the seventh digit is `coord2int` truncation, not information. At 10⁻⁷ the same encoding gives 39,357,762 B (0.621). Everything below 10⁻⁶ is a *separate, optional* lever this item does not need, which is why GH-542 no longer gates any of this work.
- **Why it decodes cheaply where GH-449's encodings did not.** A frame-of-reference block is randomly addressable and has no serial dependency: unpacking is shift-and-mask, data-parallel, with no prefix sum and no variable-length boundary scanning. Better still, nothing has to be reconstructed — every quantity in the ray-casting test is a difference, so translating the *query point* into a block's frame once is exact and the frame origin is never added back per vertex. Bit-packing is only affordable *because* the block index exists: it unpacks ~4 blocks per test rather than 190,000 values. `prototypes/polygon_block_encoding.py` verifies the round trip and the answers together — 0 blocks failed, 0 answers disagreed.
- **Why it was ranked below the block index rather than beside it.** It depends on that block structure, and it is the half that could wait: the index carries the entire query win, this carries only size. Splitting them is also what let the index ride the format-2 window without the hold having to cover a full re-encoding of 63 MB. The dependency is now satisfied — `POLYGON_BLOCK_SIZE` is 128, the ranges live in `block_ranges.npy` / `block_offsets.npy`, and every ring is already rotated to the start index those blocks are cheapest at.
- **The release it costs, accepted 2026-08-30 by the maintainer.** Only the block index rode the held window, which has since closed, so this item needs `DATA_FORMAT_VERSION` 3 and a second ordered two-distribution release. That is the price of shipping the query win sooner, and it is why this sits below DATA-BINARIES: DATA-BINARIES is exactly what makes a ~63 MB regeneration cheap in history, and GH-513 is the other format item that should share the format 3 rather than force a fourth.
- **Unmeasured, and worth settling before committing to bit-packing:** whether byte-aligned widths win instead. They cost ~8 MB more (47,870,722 B at 10⁻⁷) for a decode that is a plain widening load rather than shift-and-mask, and the comparison only means something measured inside the shipped blocked kernel, which now exists (`pt_in_poly_blocked` / `inside_polygon_blocked_int`).
- **Delete `prototypes/polygon_block_encoding.py` in the pull request that lands this**, along with its row in `prototypes/README.md`. The script is kept for one reason only: its `size` section is the pricing evidence for this item's payload encoding, and its `verify` section is what checked the bit-packed round trip. Once the encoding ships, the code is the evidence and the numbers belong to `docs/data_format.rst` and the changelog — the same rule the register applies to its own items. Its latitude-index half was already removed when that shipped, so what remains falls entirely with this item; nothing else cites it but the withdrawn GH-449 entry, whose reference should become a plain statement rather than a link.
- **Status:** open, and no longer blocked. The block structure it extends has shipped; what remains is the payload re-encoding, a format 3 and the byte-alignment question below.
- **Last touched:** 2026-08-30 — created when measurement refused GH-449's encodings and split what survived into the block index and this item; unblocked the same day when that index shipped.
