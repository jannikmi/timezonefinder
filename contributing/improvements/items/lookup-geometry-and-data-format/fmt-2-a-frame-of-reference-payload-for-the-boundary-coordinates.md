- **No issue tracks this, so this entry is the complete record.** It supersedes GH-449 together with [FMT-1](fmt-1-a-latitude-block-index-over-the-boundary-polygons.md).
- **What it is.** Store each of FMT-1's blocks as a per-block coordinate frame — an `int32` origin plus a bit width — with the vertices held as bit-packed residuals against that origin, instead of as fixed 32-bit absolutes. It reuses FMT-1's block structure and byte offsets wholesale and adds nothing to the query path's shape, only an unpack step on the blocks that survive the skip.
- **What it is worth:** the packaged coordinates go **63,402,504 B → 32,696,514 B**, 0.516 of today, at 128 vertices per block and a 10⁻⁶ scale. Median block width is 19 bits against today's fixed 32 (p99 25). Since `coordinates.bin` is essentially the whole distribution, that roughly halves what a user downloads and what the repository carries until GH-522.
- **Why the precision term is settled and costs nothing to decide.** GH-542 established that the upstream source carries six decimals, not seven, so quantising to 10⁻⁶ **cannot change an answer by construction** — the seventh digit is `coord2int` truncation, not information. At 10⁻⁷ the same encoding gives 39,355,810 B (0.621). Everything below 10⁻⁶ is a *separate, optional* lever this item does not need, which is why GH-542 no longer gates any of this work.
- **Why it decodes cheaply where GH-449's encodings did not.** A frame-of-reference block is randomly addressable and has no serial dependency: unpacking is shift-and-mask, data-parallel, with no prefix sum and no variable-length boundary scanning. Better still, nothing has to be reconstructed — every quantity in the ray-casting test is a difference, so translating the *query point* into a block's frame once is exact and the frame origin is never added back per vertex. Bit-packing is only affordable *because* FMT-1 exists: it unpacks ~4 blocks per test rather than 190,000 values. `prototypes/polygon_block_encoding.py` verifies the round trip and the answers together — 0 blocks failed, 0 answers disagreed.
- **Why it is ranked below FMT-1 rather than beside it.** It depends on FMT-1's block structure, and it is the half that can wait: FMT-1 carries the entire query win, FMT-2 carries only size. Splitting them is also what let FMT-1 ride the format-2 window without the hold having to cover a full re-encoding of 63 MB.
- **The release it costs, accepted 2026-08-30 by the maintainer.** Since only FMT-1 rides the held window and 2.x publishes once it lands, this item needs `DATA_FORMAT_VERSION` 3 and a second ordered two-distribution release. That is the price of shipping the query win sooner, and it is why this sits below DATA-BINARIES: DATA-BINARIES is exactly what makes a ~63 MB regeneration cheap in history, and GH-513 is the other format item that should share the format 3 rather than force a fourth.
- **Unmeasured, and worth settling before committing to bit-packing:** whether byte-aligned widths win instead. They cost ~8 MB more (47,870,722 B at 10⁻⁷) for a decode that is a plain widening load rather than shift-and-mask, and the comparison only means something once FMT-1's kernel exists to measure it in.
- **Status:** blocked by FMT-1, whose block structure and byte offsets it extends.
- **Last touched:** 2026-08-30 — created when measurement refused GH-449's encodings and split what survived into FMT-1 and this item.
