# PERF-10 — adopt the calibrated shortcut-ordering costs

- **Status:** open — measured 2026-10-09; waits only for a shortcut-index regeneration to ride along with.
- **Size:** ~10 lines of constants in `scripts/shortcut_ordering.py`, a re-recorded `benchmarks/shortcut_ordering_model.json`, and the regenerated shortcut index in the next data release.
- **Location:** `scripts/shortcut_ordering.py` (`BBOX`, `HOLE_UNION_PROBE`, `HOLE_LOOKUP`, `HOLE_BBOX`, `PIP_DISPATCH`, `BLOCK_PROBE`, `ACTIVE_VERTEX`).
- **Finding:** the production coefficients mis-rank a small set of cells. `make shortcut-calibration` (clang, mapped, Apple M1 Pro, data 2026d) fitted bbox 134, hole union 54, hole lookup 258, hole bbox 100, PIP dispatch 446, block probe 0.52 and active vertex 1.14 ns against production 160, 80, 120, 120, 700, 1 and 1. Re-ordering every ambiguous cell the fit never saw with the fitted set changes 646 of 30,439 cells. On uniform points in those cells every answer is identical, and the whole public call is 3.3–4.0% faster on all 8 seeds, winning 97–100% of rounds. The counted work prices the new orders at 84 ns *slower* under the production coefficients and 72 ns faster under the fitted ones, so the measurement sides with the fit. Those cells receive 0.24% of random, 0.42% of on-land and 1.76% of ambiguous-shortcut fixture queries, so no suite row will resolve it — an in-query A/B win on the touched path is the evidence the [benchmarking rules](../../../development/benchmarking-and-performance-validation.md) accept for exactly that case.
- **Caveats to settle while implementing:** hole-union probe and PIP dispatch are poorly separated by the fit (90% bootstrap intervals 0–503 and 0–501 ns), because every hole-union probe of a surviving outer box is followed by a dispatch. Round the fitted set, re-run the optimizer with the rounded set and check the changed-cell A/B still wins before adopting it. Confirm on the ubuntu-latest reference run (`benchmark.yml` dispatch with `calibrate_shortcuts`) as well as locally. The area-only alternative is 45% slower on the 788 cells it changes and is not a candidate.
- **Why it waits:** new coefficients change the shortcut binary, which ships in `timezonefinder-data`. A release for a 0.01–0.06% workload gain alone is not worth it; [TOOL-7](../data-pipeline-and-developer-tooling/tool-7-the-shortcut-ordering-leaves-its-ties-to-set-iteration-order.md) regenerates the same index, so take both in one rebuild.
- **Acceptance:** new constants in source; regenerated shortcut index with unchanged candidate membership and identical answers; `make shortcut-calibration` re-run on the regenerated data, with the fit no longer changing a material number of cells; the old-versus-new changed-cell A/B recorded in the pull request; `make shortcut-calibration-record`.
