## Finding

- **Where:** `TimezoneFinder.timezone_at` and `TimezoneFinder.certain_timezone_at` in `timezonefinder/timezonefinder.py`, and the batch forms beside them. Every public lookup returns exactly one zone: `timezone_at` returns the last remaining zone without a test, and `certain_timezone_at` returns on the first polygon that contains the point. No public method reports that a point lies in more than one zone, and neither `docs/1_usage.rst` nor the docstrings say which zone wins where zones overlap.
- **The dataset ships genuinely overlapping zones, and real queries land in them.** Collecting every containing zone over `_iter_boundaries_in_shortcut` with `inside_of_polygon`, measured 2026-09-18 on data 2026c: 28 of 10,000 `random_points`, 98 of 10,000 `on_land_points` and 163 of 5,000 `ambiguous_shortcut_points` lie in two zones. The pairs are `Asia/Urumqi` inside `Asia/Shanghai` (almost all of them — a real second local time in use), and disputed or dual-administered areas: `Africa/Khartoum`/`Africa/Juba` (Abyei), `Asia/Tbilisi`/`Europe/Moscow` (Abkhazia, South Ossetia), `Asia/Jerusalem`/`Asia/Hebron`, `America/Sitka`/`America/Vancouver`, `America/Punta_Arenas`/`America/Argentina/Rio_Gallegos`. For each, `timezone_at` silently picks one, and a user for whom the other answer is the right one cannot tell that a choice was made.
- **Both comparable libraries expose it.** `tzfpy.get_tzs` and node `geo-tz`'s `find` return every containing zone. A comparison against `geo-tz` 8.1.8 (its `all` product, the same 2026c boundaries) on the same fixtures reproduced exactly the counts above, and `timezone_at`'s answer was always among geo-tz's zones — so the information is in the packaged data already; only the API withholds it. geo-tz returns the zones in quadtree-dependent order, which makes its first element an unstable answer; a method here should not repeat that.
- **Likely shape, to be decided rather than assumed:** a scalar method testing every candidate polygon of the cell instead of stopping at the first match, returning the distinct zone names with `timezone_at`'s answer first so the two methods can never contradict each other. The hot path is untouched: only the new method pays for the full candidate loop, and a unique-zone cell answers it with a one-element list and no geometry.

## Interactions

- **PERF-7 removes exactly the information this needs.** PR #652 turns an ambiguous cell that one polygon covers entirely into a unique-zone entry, discarding the other zones' candidates for that cell. After it lands, a cell covered by `Asia/Shanghai` that also holds `Asia/Urumqi` answers a full-candidate loop with one zone. API-1 then needs either the discarded candidate list retained beside the entry or a separate overlap table; whichever lands second must price that, and the choice is cheaper made before PERF-7's format is released.
- **Completeness rests on candidate generation.** A missing candidate makes the method under-report. GEOM-3 records no sampled omissions but no proof either; the method's docstring must not promise more than `certain_timezone_at` already does.

- **Size:** M — one method (plus a batch form if decided), docstrings stating the ordering and the completeness caveat, a usage-docs section on overlapping zones, tests over the pairs above.
- **Status:** needs a decision on whether to add public API surface for it.
- **Decision needed:** add the method, or hold it like GH-505 until a user asks? **(a) Add a scalar `timezones_at(*, lng, lat) -> list[str]`** in the next minor, with `timezone_at`'s answer first, and document the overlapping zones in `docs/1_usage.rst` either way. Additive, so no major is needed; its cost is a permanent method and the PERF-7 interaction above. **(b) Conditional on demand**, as GH-505 is: nothing ships until an issue asks. Cheaper, but unlike GH-505 this is not a hypothesis about who wants a feature — the packaged data already holds answers the API hides, and both peer libraries expose them. **(c) Documentation only:** state which zone wins and list the overlaps, without a method. **Recommendation: (a)**, scalar only; a batch form waits for a user, because it would need the variable-length result shape the id arrays avoid.
