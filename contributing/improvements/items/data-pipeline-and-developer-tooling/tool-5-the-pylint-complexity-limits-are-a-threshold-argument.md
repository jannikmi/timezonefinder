# TOOL-5 — the pylint complexity limits are a threshold argument, not a defect list

- **Location:** `pyproject.toml`, `[tool.ruff.lint] select`, which does not contain `PLR`; there is no `[tool.ruff.lint.pylint]` section, so every limit would take ruff's default.
- **What it is.** `PLR09xx` prices function complexity against a number. Measured 2026-09-06 on ruff 0.15.22, against ruff's defaults: **15 sites** — `PLR0913` too many arguments 7, `PLR0915` too many statements 5, `PLR0912` too many branches 2, `PLR0911` too many return statements 1.
- **Why this is not an ordinary lint item.** Nothing here is wrong; the rule reports that a function is larger than a threshold nobody in this repository has chosen. Adopting it at ruff's defaults makes 15 existing functions non-compliant and commits every later change to the same limits, and the ones it names are the data-integrity validators and the converter entry points, which are long because they check many things in one pass rather than because they are tangled. Setting the limits above the current tree instead makes the rule a ratchet that never fires, which is a different decision with a different value.
- **Decision needed:** should `PLR09xx` be enforced, and at what limits?
  - **Consequences.** Enforcing it at ruff's defaults means refactoring 15 functions, several of them the validators whose value is that they are one exhaustive pass; enforcing it above the tree means the rule only ever catches *new* growth; not enforcing it means function size stays a review judgement, as it is today.
  - **Options.** (1) Do not select `PLR09xx`, and record the refusal so no later pass re-surfaces the 15 sites. (2) Select it with limits set just above the current tree, as a ratchet against new growth. (3) Select it at ruff's defaults and refactor the 15 sites, as its own sequence of items.
  - **Trade-offs.** (1) costs nothing and keeps the current review practice, but leaves the register re-discovering these counts. (2) is cheap and stops growth, but a limit chosen from today's worst function is an arbitrary number that reads as endorsed. (3) is the only one that actually shortens anything, and it is the most expensive by an order of magnitude and would rewrite validators the project deliberately keeps exhaustive.
  - **Recommendation:** (1). The named functions are long by design and the register has produced no finding that traces to their length; a complexity limit here would generate work rather than surface it.
  - **Reversibility:** cheap either way — selecting or unselecting a rule is one line — except that (3)'s refactors are not undone by unselecting it.
  - **Unpriced uncertainty:** whether any of the 15 functions is actually hard to change, which nobody has been asked; the counts above are ruff's, not a reading of the code.
- **Status:** needs a decision on whether complexity limits are adopted, and at what thresholds.
