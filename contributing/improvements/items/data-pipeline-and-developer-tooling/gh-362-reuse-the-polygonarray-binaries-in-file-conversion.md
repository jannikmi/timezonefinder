# GH-362 — reuse the `PolygonArray` binaries in file conversion

- **Tracks:** issue #362, `good-first-issue`.
- **A 2026-09-04 pass rejected this and the rejection was withdrawn 2026-09-06.** It was refused on the grounds that every reader in the repository already uses `PolygonArray`, so nothing is deduplicated, and that reading the binaries back costs a decode per access. The first is true and the second is measured, but neither is the question: the item is worth taking for **the shape of the converter's own code**, and converter wall clock is explicitly secondary to that — see the [data-pipeline rules](../../../development/data-pipeline-format-versioning-and-release-order.md). Withdrawing rather than deleting, because the measurement below still rules out one implementation of it and a later pass would otherwise re-derive it.
- **What is actually worth fixing.** `TimezoneData` holds a polygon collection as six parallel per-polygon structures — `polygons`, `polygon_lengths`, `poly_boundaries`, `hole_boundaries`, `inline_holes`, `holes_in_poly` — reached by index from callers that must keep them in step by hand: `Hex.is_poly_candidate` indexes `data.poly_boundaries`, `Hex.lies_in_cell` indexes `data.polygons` and calls `data.holes_in_poly`, `optimise_shortcut_ordering` indexes `data.polygon_lengths` and `data.poly_zone_ids`. `PolygonArray` is the same collection with the same accessors already named and grouped (`xmin`/`xmax`/`ymin`/`ymax`, `nr_vertices`, `coords_of`, holes through `poly_ref`). One collection object, with the runtime's vocabulary, is the clean-up — and it makes a reader of either side able to read the other, which is worth more here than anywhere because the converter is the part whose correctness is hardest to check.
- **The implementation this rules out, measured 2026-09-04.** Do *not* write the binaries early and read them back through `PolygonArray` per access: over the packaged boundaries (1,322 rings, 7,925,313 vertices, `in_memory=True`), **`coords_of` is 193 µs per call against 0.04 µs for indexing the in-memory list**, because the packed payload has to be decoded — that decode is what polygon layout 3 exists to charge `get_geometry()` for. `Hex.lies_in_cell` reads a ring once per (cell, candidate) pair while compiling the shortcut index, so this is not minutes but hours, which is past what "secondary" covers. Materialising every ring once into memory instead costs ~0.26 s and ~63 MB, which is affordable — but it buys nothing on its own, since the producers still have to run.
- **So the shape to aim for is a converter-side collection class, not the runtime reader over the written bytes.** Share the accessor *names* and the grouping; keep the in-memory rings. The issue's own third TODO says as much — "a specialised child class of `PolygonArray` for the file conversion script" — and its first two, which write the binaries early and read them back, are the half this measurement refuses.
- **How it gets verified**, and why it is not cheap: the only proof a converter refactor is neutral is regenerating and diffing the binaries. `make testparse` over `tests/test_input.json` exercises the same code paths for a few seconds and is the iteration loop; a full `make parse` plus `diff -rq` against a copy taken beforehand is the gate.
- **Status:** open — free, and ranked on clarity rather than on any measurement.
- **Last touched:** 2026-09-06 — rejection withdrawn; re-scoped onto the converter's own structure, with the read-back-per-access implementation ruled out by measurement.
