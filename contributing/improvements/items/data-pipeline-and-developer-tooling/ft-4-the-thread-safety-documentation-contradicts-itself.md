# FT-4 — the thread-safety documentation contradicts itself

- **Where:** `docs/architecture.rst`, the global-functions paragraph ("they are *not* thread-safe"); `docs/1_usage.rst`, both the usage note ("you **must** create separate `TimezoneFinder` instances for each thread/process. This is the only way to guarantee thread-safe concurrent timezone lookups") and the parallel-computation note; `timezonefinder/global_functions.py`, the module docstring and `timezone_at`'s note, which call the singleton thread-safe for concurrent reads, against `get_geometry`'s note in the same file, which calls itself *not* thread-safe; and the three `Thread Safety:` blocks in `timezonefinder/timezonefinder.py` — `TimezoneFinder`'s class docstring, which warns that sharing "can lead to race conditions and incorrect results", plus the two on `TimezoneFinderL` and the base class.
- **Defect:** two published pages state the opposite of each other about the same functions, so a reader gets whichever answer they happen to open first.
- **Which one is wrong, and why this is not a maintainer question:** the "not thread-safe" and "race conditions and incorrect results" statements are. There are no module-level caches and no `lru_cache` anywhere in `timezonefinder/`; the mapped path is `mmap` plus `np.frombuffer`, random access with no shared file position and therefore no seek to serialise; the loaded arrays are read-only, asserted by `tests/test_resource_management.py`; and `_get_tf_instance` initialises under double-checked locking.
- **One lookup-path write exists, and the item must state it rather than repeat the audit's absolute.** Issue #364 records that nothing on the lookup path assigns to `self`, and names #536's cache and BIG-1's lazy mapping as the changes that *would* introduce the first one. That is out of date: `_iter_boundary_ids_of_zone` in `timezonefinder/timezonefinder.py` already assigns `self._zone_positions` on first use, reached by `certain_timezone_at` and `get_geometry` — which is exactly why `get_geometry` carries the file's one "not thread-safe" note. The race is benign for the reason a benign publication race has to be benign, and the reason belongs in the docs rather than only in a code comment: the value is an immutable read-only array built from a file of 890 constant bytes, identical whichever thread wins, and it is published by a single attribute store, so a loser re-reads the file and stores an equal array. `tests/test_resource_management.py` asserts the arrays are read-only; it does not assert that no attribute is written, so do not cite it as proof of that.
- **What that changes about the fix:** "no state is mutated" is the wrong sentence to write. "The state a lookup reads is immutable, and the one attribute a lookup can write publishes an immutable value that is the same from any thread" is the true one, and it is what makes the correction survive the next lazily-initialised attribute instead of being falsified by it.
- **The correction the per-thread advice needs is the harder half.** "Create one instance per thread" is right and its stated reason is not: it is not needed for correctness, it is needed for *throughput*. A shared instance scales 1.60x at 8 threads against 4.84x per-thread on a free-threaded build, and `TimezoneFinderL` collapses identically with no polygon data at all — so this is reference-count contention on shared objects, not the mmap, the accessor or the candidate loop. On a GIL-enabled build the distinction is invisible (0.73x–0.99x either way). Say that, rather than deleting the advice or leaving a correctness claim standing under it.
- **What must not be written:** that a shared instance is as fast, or that per-thread instances are optional. Both readings are available from a careless fix, and both are wrong.
- **Size:** M — seven prose sites across two documentation pages and two modules, and they must end up saying one thing.
- **Status:** open.
- **Detail:** issue #364 carries the audit table and the scaling measurements.
