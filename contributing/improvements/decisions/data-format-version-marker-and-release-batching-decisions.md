# Data-format version-marker and release-batching decisions

Do not re-propose these settled release/versioning choices without new evidence.

- **One version marker per unreleased batch, not per change — and therefore batch the changes.** Settled first for `POLYGON_LAYOUT_VERSION`, which was briefly bumped to 2 in #509 so a released version would reject deduplicated hole data. It was reverted: layout 1 arrived with the per-axis coordinate encoding in #457, which is not an ancestor of 8.2.5, so no version in the wild reads or writes it and there was nothing to protect against. The bump would have rewritten the 63 MB boundary coordinate file for a single byte. Check whether the layout being superseded has actually shipped before bumping. **Generalised 2026-08-25 to `DATA_FORMAT_VERSION` and the data release itself**, which is the expensive instance: the number identifies a release rather than a change, so while a bump sits unreleased on `master` the next format change rides it for free and the ordered two-distribution release is paid once for both. The consequence is a *sequencing* rule and not just an accounting one — the ranking prices each format item as though it paid that release alone, which is true only of the first, so once a bump is pending the remaining format items should be taken consecutively and released together. This is the same shape as the API-major decision below and as the layout marker above: **what a release costs is paid per release, so work that forces one is cheaper in a batch than spread out.** Regenerating the packaged data needs no permission and parks no item; it only must not be *incidental*, since it can rewrite ~64 MB.

- **The rebuild with deterministic shortcut tie order waits for the H3 index's replacement and ships with it in one data release.** Decided 2026-10-09 by the maintainer: pricing longitude/latitude-aligned indexes against H3 could end in a replacement index, which would take `DATA_FORMAT_VERSION` to 4 and need an ordered two-distribution release, so the converter's [tie-order change](shortcut-ordering-and-fallback-semantics.md#legacy-shortcut-ordering-ties) is not published alone as `3.2026.4.post1` ahead of it. The pricing has since found an aligned grid ahead of H3 ([aligned-index decisions](longitude-latitude-aligned-index-decisions.md)), the maintainer decided on 2026-10-12 to adopt one, and it shipped as `DATA_FORMAT_VERSION` 4. The change itself is on `master`, because comparing indexes needed byte-reproducible builds, and that takes a deterministic converter, not a published release. **What the hold covers:** no data release is cut for the tie order alone, nor for PERF-10's recalibrated costs, which take the same rebuild, and a code release made during the hold keeps the `timezonefinder-data` floor at a published version and does not promise the revised order. **It ended on 2026-10-13**: the rebuild rode the format-4 bump, so the deterministic tie order is in the published data without a release having been cut for it. **PERF-10 did not ride it, and has since been withdrawn** - its fitted coefficients were measured over H3 cells, and a re-calibration against the grid tree read `unresolved` on all 8 seeds from a fit that prices a kernel dispatch at ~0 ns, so there was nothing shown to win by the time the release existed. That is the one thing this hold did not deliver, and the reason is worth keeping: a hold can batch a *change*, but it cannot batch a *measurement* whose subject the batch replaces. Either release's README summary carries the answers it moves, which the linked decision measured for 2026d. **Not covered:** an upstream boundary update. The weekly pipeline remains how new boundaries reach users, and any release it cuts compiles with the converter on `master`, so it delivers the tie order as a side effect without being a release made for it. **Why the cost is low:** the tie order changes no format and no runtime reader, so unlike the format-2 hold below, this hold blocks no `timezonefinder` release. The price is that published data keeps set-iteration tie order for as long as the adoption takes. Refused: publishing the post-release as soon as the converter change merged, which spends a release the batch makes free.

- **A branch compiles its data in CI; it never commits binaries to have something to test.** Decided 2026-08-31 by the maintainer, immediately after git-ignoring the dataset left hand-made branches without a producer. Every format change declares a `timezonefinder-data` version PyPI has never served, so `make bootstrap` has nothing to fetch — and the weekly update job is the only thing that recorded a `DATA_BUILD_RUN` for CI to read instead. `compile_data.yml` is the missing half: dispatched on the branch, it compiles the release the branch's own `DATA_VERSION` names, uploads the wheel as `artifact-data-wheel`, and reports the run to record. Every consumer already knew what to do with that. **Why it is not merely a convenience:** the wheel that run builds is the one the pull request's matrix installs and the one the `data-v*` tag publishes, so a format change reaches PyPI through a single build — the same invariant the weekly pipeline rests on, extended to the branches that previously could not have it.
  - **Refused: committing the branch's binaries** (`git add -f` past the ignore, `git rm -r --cached` once the data release publishes). It needs no machinery at all, which is exactly why it is the option to argue against: it puts ~63 MB into the history for every format change — reintroducing the growth the ignore was for, and leaving GH-522's rewrite conditional on no such branch being unmerged — and it returns the release to vouching for laptop-compiled bytes with a diff. It still physically works, since ignoring never affects a tracked file, and that is the fallback if a dispatch is impossible; it is not the plan.
  - **The costs, so they are not rediscovered.** The artefact has to outlive the branch's review, hence 90-day retention and a re-dispatch if it expires — the run id is the only reference to it. And the branch's committed fixtures and report pages were measured against the author's local compile, so CI's bytes must match: they do because the converter is byte-deterministic, and the fixture tests fail loudly on the branch if they ever do not.

- **`DATA_FORMAT_VERSION` 2 was held unpublished so that the polygon layout change could ride it, and it did — the window is now closed.** Decided 2026-08-29 by the maintainer, who raised the release cost the brief had missed; the exit condition fired on 2026-08-30 when the latitude block index landed and took `POLYGON_LAYOUT_VERSION` to 2. What the hold bought is exactly what it was for: one ordered two-distribution release covering both the format-2 bump and the block index, instead of two. **Format 2 now means polygon layout 2 and shortcut layout 2**, and `timezonefinder-data` 2.x is ready to publish.
  - **It published on 2026-08-30 as `timezonefinder-data` 2.2026.3**, which settled its meaning permanently and closed the window. The frame-of-reference payload took `DATA_FORMAT_VERSION` to 3 the day after — the second ordered two-distribution release the split below knowingly accepted. **Format 3 is the open window now**, on exactly the same terms: a layout change that lands before a 3.x publishes rides it, and one that lands after pays for a fourth release. The coordinate scale already rode it, and GH-513 — the remaining candidate — was refused on 2026-09-01, so nothing claims the window now.
  - **What the hold cost, and why it ends here:** `master` requires `timezonefinder-data>=2.2026.3,<3`, so no `timezonefinder` release could ship while 2.x was unpublished — the hold deferred the whole pending code release, not merely the format work. That is the reason it carried an exit condition at all, and the reason not to hold again for a further format change: the price is paid per day held, not per change batched.
  - **What the hold covered was narrowed 2026-08-30, when the sequential-encoding proposal was withdrawn and split in two.** It was one atomic re-encoding; its successors split into an additive index — the latitude block index, which shipped and closed the window — and a frame-of-reference payload, and the maintainer chose to hold only for the first. **The payload therefore took format 3 deliberately**, knowingly accepting the option refused below for the *second* half — the trade was a release against shipping the query win months sooner, and against a hold that would otherwise have had to cover a kernel rewrite plus a 63 MB re-encoding. It was paid: 2.2026.3 published on 2026-08-30, one day before the payload landed.
  - **Refused, with the reason each loses.** *Ship 2.x now and let the encoding pay for a format 3* — the do-it-anyway option, refused because it spends an ordered two-distribution release that costs nothing to avoid while the window is open. *Ship 2.x now but bind the encoding and GH-513 to one shared format 3* — better than the first, and still paying a release the hold makes free. Both remain the right answer the moment the exit condition fires.
