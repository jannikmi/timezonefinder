# Data-format version-marker and release-batching decisions

Do not re-propose this settled release/versioning choice without new evidence.

- **One version marker per unreleased batch, not per change — and therefore batch the changes.** Settled first for `POLYGON_LAYOUT_VERSION`, which was briefly bumped to 2 in #509 so a released version would reject deduplicated hole data. It was reverted: layout 1 arrived with the per-axis coordinate encoding in #457, which is not an ancestor of 8.2.5, so no version in the wild reads or writes it and there was nothing to protect against. The bump would have rewritten the 63 MB boundary coordinate file for a single byte. Check whether the layout being superseded has actually shipped before bumping. **Generalised 2026-08-25 to `DATA_FORMAT_VERSION` and the data release itself**, which is the expensive instance: the number identifies a release rather than a change, so while a bump sits unreleased on `master` the next format change rides it for free and the ordered two-distribution release is paid once for both. The consequence is a *sequencing* rule and not just an accounting one — the ranking prices each format item as though it paid that release alone, which is true only of the first, so once a bump is pending the remaining format items should be taken consecutively and released together. This is the same shape as the API-major decision below and as the layout marker above: **what a release costs is paid per release, so work that forces one is cheaper in a batch than spread out.** Regenerating the packaged data needs no permission and parks no item; it only must not be *incidental*, since it can rewrite ~64 MB.

- **`DATA_FORMAT_VERSION` 2 was held unpublished so that the polygon layout change could ride it, and it did — the window is now closed.** Decided 2026-08-29 by the maintainer, who raised the release cost the brief had missed; the exit condition fired on 2026-08-30 when the latitude block index landed and took `POLYGON_LAYOUT_VERSION` to 2. What the hold bought is exactly what it was for: one ordered two-distribution release covering both the format-2 bump and the block index, instead of two. **Format 2 now means polygon layout 2 and shortcut layout 2**, and `timezonefinder-data` 2.x is ready to publish.
  - **Nothing further may ride it.** The number is still unpublished, but its *meaning* is settled by what shipped on `master`; the next format change takes a format 3, which FMT-2 and GH-513 should share. Reopening the window for a second change would mean rewriting binaries `master` already carries under a version that claims to describe them.
  - **What the hold cost, and why it ends here:** `master` requires `timezonefinder-data>=2.2026.3,<3`, so no `timezonefinder` release could ship while 2.x was unpublished — the hold deferred the whole pending code release, not merely the format work. That is the reason it carried an exit condition at all, and the reason not to hold again for a further format change: the price is paid per day held, not per change batched.
  - **What the hold covered was narrowed 2026-08-30, when GH-449 was withdrawn and replaced by FMT-1 and FMT-2.** GH-449 was one atomic re-encoding; its successors split into an additive index (FMT-1, shipped) and a payload re-encoding (FMT-2), and the maintainer chose to hold only for the first. **FMT-2 therefore takes a format 3 deliberately**, which is the option refused below being knowingly accepted for the *second* half — the trade is a release against shipping the query win months sooner, and against a hold that would otherwise have to cover a kernel rewrite plus a 63 MB re-encoding.
  - **Refused, with the reason each loses.** *Ship 2.x now and let the encoding pay for a format 3* — the do-it-anyway option, refused because it spends an ordered two-distribution release that costs nothing to avoid while the window is open. *Ship 2.x now but bind the encoding and GH-513 to one shared format 3* — better than the first, and still paying a release the hold makes free. Both remain the right answer the moment the exit condition fires.
