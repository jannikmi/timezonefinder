# Data-format version-marker and release-batching decisions

Do not re-propose this settled release/versioning choice without new evidence.

- **One version marker per unreleased batch, not per change — and therefore batch the changes.** Settled first for `POLYGON_LAYOUT_VERSION`, which was briefly bumped to 2 in #509 so a released version would reject deduplicated hole data. It was reverted: layout 1 arrived with the per-axis coordinate encoding in 5947b1b, which is not an ancestor of 8.2.5, so no version in the wild reads or writes it and there was nothing to protect against. The bump would have rewritten the 63 MB boundary coordinate file for a single byte. Check whether the layout being superseded has actually shipped before bumping. **Generalised 2026-08-25 to `DATA_FORMAT_VERSION` and the data release itself**, which is the expensive instance: the number identifies a release rather than a change, so while a bump sits unreleased on `master` the next format change rides it for free and the ordered two-distribution release is paid once for both. The consequence is a *sequencing* rule and not just an accounting one — the ranking prices each format item as though it paid that release alone, which is true only of the first, so once a bump is pending the remaining format items should be taken consecutively and released together. This is the same shape as the API-major decision below and as the layout marker above: **what a release costs is paid per release, so work that forces one is cheaper in a batch than spread out.** Regenerating the packaged data needs no permission and parks no item; it only must not be *incidental*, since it can rewrite ~64 MB.

- **The pending `DATA_FORMAT_VERSION` 2 release is held open until GH-449 lands, so the polygon encoding rides format 2 rather than forcing a format 3.** Decided 2026-08-29 by the maintainer, who raised the release cost the brief had missed. The window is real and closes on publication: `DATA_FORMAT_VERSION` is 2, `POLYGON_LAYOUT_VERSION` is 1, and PyPI holds `timezonefinder-data` `1.2026.3` alone — so format 2 has never shipped and what it *means* is still editable. GH-449 bumps `POLYGON_LAYOUT_VERSION` to 2, which `tests/test_data_version.py::test_the_format_version_moves_with_the_layouts_it_is_made_of` requires be paired; landing it before 2.x publishes updates the recorded layout pairing and keeps the number, landing it after needs a format 3 and a second ordered two-distribution release. Once 2.x is on PyPI with polygon layout 1, format 2 is frozen — redefining it would let the resolver hand old code data it cannot read, which is the failure the marker exists to prevent.
  - **What the hold costs, accepted:** `master` requires `timezonefinder-data>=2.2026.3,<3`, so no `timezonefinder` release can ship until 2.x publishes — the hold therefore defers the whole pending code release, not merely the format work. **Bugs come first inside the hold** (the [register rules](../improvement-register-rules.md) carry the general precedence), and the hold does not stop them being fixed on `master`, only shipped.
  - **Exit condition, so the hold cannot run on inertia:** it ends when GH-449 lands **or** is rejected, whichever comes first. GH-449 may fail its own decode-cost constraint — a candidate loop that has already lost its ~4.9 µs per-candidate fetch leaves a decode step nothing to hide behind — and a rejection is as good a reason to publish 2.x as a success.
  - **Refused, with the reason each loses.** *Ship 2.x now and let GH-449 pay for a format 3* — the do-it-anyway option, refused because it spends an ordered two-distribution release that costs nothing to avoid while the window is open. *Ship 2.x now but bind GH-449 and GH-513 to one shared format 3* — better than the first, and still paying a release the hold makes free. Both remain the right answer the moment the exit condition fires.
