# Unattended data-update pipeline decisions

Do not re-propose these settled or refused options without new evidence. The weekly data update compiles, validates, merges and tags a new `timezonefinder-data` release with no human reading the diff, and these are the decisions that make that defensible: what the guardrails are for, which of them block, who is allowed to trigger the acting jobs, and which bytes the tag is permitted to publish. Split out of the [distribution and release decisions](data-distribution-packaging-and-release-decisions.md) because that file reached the 2,000-word budget `tests/test_contributor_memory.py` enforces, and because an unattended pipeline's safety is a bounded subject on its own - the choices below constrain each other and are read together.

- **Has a timezone-boundary-builder release ever been bad? No.** So the guardrails on the data-update pipeline — the download digest check, and the frozen-sample answer baseline the update rewrites — are preventive, not corrective. That lowers their urgency but not their value: the argument never rested on a past incident, it rests on the pipeline auto-merging and auto-tagging with no human diff review. It is also why the payload-size band was measured before it was made a gate rather than guessed at, which cost four conversions and shipped the signal report-only in the meantime.

- **A tripped data-update guardrail blocks the auto-merge, and the size gate is symmetric.** Settled 2026-08-23 by the maintainer. Every signal made a gate blocks; signals the calibration ruled report-only stay report-only, so this does not turn zone changes into a gate. Refused: *report only*, which leaves an unattended pipeline publishing whatever it downloaded, and *block on the two hard signals only*. **Also overruled, with its reasoning:** the four-release calibration concluded the size gate should be asymmetric because boundary data has grown monotonically, making a decrease the anomaly. Four releases of monotone growth do not establish that — ordinary refinement produces the same pattern, and upstream may legitimately simplify boundaries. Small reductions pass. **What overruling it cost:** the asymmetric band was the only calibrated number, so the symmetric one had to be measured first — 2025c, 2026a, 2026b and 2026c converted with the current code put the largest legitimate move at 1.38 % of the boundary payload and 2.58 % of the hole payload, and the ±5 % and ±10 % bands in `scripts/data_update_guard.py` sit 3.6x and 3.9x above them. The earlier hole figures (−0.07 %, +0.09 %, −0.31 %) did not survive re-measurement under the current binary format, which is why a band is never carried over from an older one.

- **A branch-name prefix is not an authorization check.** Settled in #519. The `workflow_run` jobs that merge and tag a data update select their work with `startsWith(head_branch, 'data-update-')`, and any fork can open a pull request from a branch with that prefix — the condition says which runs are *interesting*, never which are *trusted*. What gates the merge is the head repository's owner, checked in one shared composite action (`.github/actions/resolve-update-pr`) that every acting step resolves its pull request number through, so no step can grow a second copy that omits it. The same reading applies to any future workflow keyed on a branch, tag or path pattern.

- **A data release publishes the bytes CI validated, never bytes rebuilt at tag time.** Settled 2026-08-24. `publish_data.yml` skips re-validating the data because the update pull request's matrix already compiled and checked it, and that is a real invariant rather than an optimisation: it is why an auto-merged, auto-tagged pipeline is defensible at all. So the update job builds the wheel and the tag publishes *that artifact*; `.github/actions/obtain-data-wheel` implements it, and accepts the artefact only while every packaged input still matches the checkout. Refused: having the publish job regenerate — reproducible from the tag alone, which is its one merit, at the cost of publishing bytes nothing tested; and moving the binaries to a second repository, which re-poses the question one level up. **Two mechanics:** a *published* GitHub Release cannot carry it — `build.yml` fires on `release: types: [published]`, which `publish_data.yml` creates no Release to keep dead — so a run artifact does, addressed by a run id committed with the data. And the dead end below, *reusing the master run's artifacts on the tag run buys almost nothing*, **does not transfer to data**: measured on code wheels, the copyable half was the cheap one; here the build is a ~62 MB download plus a full convert.
