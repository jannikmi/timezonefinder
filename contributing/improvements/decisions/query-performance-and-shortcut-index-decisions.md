# Query performance and shortcut index decisions

Do not re-propose these settled or refused options without new evidence.

- **Accelerating the slot arithmetic with numba or the C extension — measured 2026-08-23 and refused; the algebra was the win instead.** The lookup's bit arithmetic looked like a candidate for `njit`. It is not, and the measurement forecloses the whole family rather than one attempt: **an empty `njit` call costs ~98 ns**, against ~152 ns for the entire stage it would replace, so dispatch alone eats two thirds of the budget before any kernel runs. Both variants came out slower than plain Python (156 and 166 ns against 152), and the C extension is worse on the same grounds. This generalises — **no scalar per-query stage in the single-digit-hundreds of nanoseconds can be worth a dispatch boundary**. **Applied and shipped 2026-09-06, and the *form* of the fix is the part to keep:** `is_valid_lat`, `is_valid_lng` and `coord2int` were the last scalar stages paying a dispatch. The decorator came off them rather than their call sites inlining the bodies, which was measured and refused: ~40 ns more, for a second definition of the coordinate bounds. Worth -12.3 % of a random query on numba and **nothing without numba**, where `njit` was already transparent and no dispatch existed to remove.

- **What pays on such a stage is an algebraic reduction, not an accelerator.** The cell arithmetic is the one stage every query runs before any geometry, so look for an identity that collapses it - the win there was folding a six-operation slot computation into one shift and mask, worth **-5.1 % of a unique-zone query with 43 of 61 rounds faster**, both estimators agreeing, which is the bar. An identity over any 64-bit value beats a property of the cells that happen to exist, because the cells get replaced and the identity does not.


- **Justify the shortcut structure on load, memory and file size — never as a speedup.** Measured full `timezone_at`, paired and order-alternated: neutral to slightly ahead, too small for any headline. It changes how a cell's candidate list is stored, never which candidates come back, so it avoids exactly the same point-in-polygon tests. Two designs that suggested otherwise were discarded: an isolated lookup omits the `match value: case int(zone_id)` the old code ran on the dict's answer, and a fixed A-then-B order credited the new structure with 13.3 % that was the first path warming shared code for the second.

- **A raster fast-path in front of the shortcut index — dropped.** A ~2 MB lookup table answering unambiguous cells with one array index, the index otherwise. It buys query time with storage, the dimension this package can least afford.

- **Ocean-ness is tested with `str.startswith` on the scalar path, and with an id-indexed flag array only where a batch pays for one.** Settled 2026-08-20, extended when the land batch shipped. `OCEAN_TIMEZONE_PREFIX` is `r"Etc/GMT"`, which has no regex metacharacters, and `re.match` anchors at the start — so `startswith` is exactly equivalent and captures the whole measured saving (~250 ns per `timezone_at_land`, ~6 % of a mixed workload, inside the noise floor) in one line. Precomputing a boolean array indexed by zone id was refused *for the scalar path* on cost, not on merit: `timezone_at_land` receives a name and `is_ocean_timezone` takes one, so an id-indexed table means restructuring both plus a per-instance array. The batch form is what changed the price rather than the argument — it holds ids already, and testing each answer's name per point is the work a batch exists to remove — so `ZoneNames.ocean_flags()` builds that array lazily on first use, with the trailing sentinel slot and the same race argument as the names gather array beside it. The part still refused: making the *scalar* path go through ids. The decoupling it would also buy — an upstream rename of the `Etc/GMT` family cannot silently change which results count as ocean — is had for the batch and not for the scalar method; re-propose extending it only against an actual rename.

- **An accessor-lifetime export of the mmap is not forbidden, and `FileCoordAccessor` holds one — which is why `cleanup()` drops it before the close and not after.** Settled 2026-08-23, when the mapped fetch was refused on the noise floor; that half is superseded 2026-09-06 ([ranking rule](../improvement-ranking-and-eligibility.md)) and the resource-semantics half, which is what this entry is for, stands. The `BufferError` fixed in 8.3.0 made "never hold a live export" read like a standing rule. It is not one, but it is not free: an export left live at the close makes `mmap.close()` raise `BufferError`, `close_resource` swallow it, and the unmapping fall to collection. Both orderings are now right and pinned — `test_cleanup_closes_the_mapping_when_no_caller_holds_a_view` and `test_finder_cleanup_closes_the_mapping`. **Any further export inherits that obligation**, at whichever level holds it — drop it before the close, or every teardown silently goes back to a refused close. `PolygonArray.cleanup` is the other one: its `packed` kernel buffers export the same words on both backends, so they go before it releases the accessor. A *caller's* view still refuses the close, deliberately. So do not refuse a future held view on resource-semantics grounds alone, nor propose one on a per-fetch microbenchmark. **The generalisable half:** a per-fetch figure and a workload share are different quantities, and converting one into the other is where that refusal's own arithmetic went wrong — ~370 ns per fetch in isolation was written up as "~3 % of a mixed workload", and measured inside the query it was ~0.8 %, indistinguishable from noise at 9 of 15 rounds. Nearly 4x apart, and the ranking rule takes the second. Measure inside the query, alternating within one process.

- **Numba is not the fast path, and since 2026-09-22 the dispatch says so: the C extension is bound wherever it loaded, numba only where it did not.** "Numba is the fast path" was the natural reading of the tox matrix and of `utils.py` preferring it, and it is not what the numbers say: on the packed kernel a lookup runs, numba is behind clang across the size strata and behind on `timezone_at` too, both estimators agreeing and no round won. Do not quote a ratio from here — `make acceleration-paths` regenerates `docs/benchmark_results_acceleration_paths.rst`, the one place the ranking is stated, and a measurement putting numba ahead there reopens the order. Two consequences. **The import went into the branch with it**: `utils.py` imports `utils_numba` only where the extension is missing, since that import *is* the compilation, so such a process never loads numba: 39 MiB resident, the plain install's own figure, against 152 MiB with the import unconditional. Its converters are NumPy in `utils.py` now; keep new helpers out of `utils_numba` unless the compiler earns them, or every process pays that import again. And `using_numba()` reports the *binding*, false wherever the extension won, while reports need numba's *presence* - a labelling hazard the [comparison rules](../../development/designing-a-candidate-comparison.md) own. *Superseded evidence, #497, on the bare kernel before polygon layout 3:* the two were then within 5 %. Sound for what it measured; the packed kernel does not behave that way, and the njit'd validators it also blamed came off in #644.

- **Precomputing `last_zone_change_idx` into the shortcut binaries — refused twice, and reversed 2026-08-23.** Proposed as issue #256, closed in 2025 because throughput is dominated by point-in-polygon work, and as draft PR #348. The refusal rested on two legs: #497 sizes the win at 149 ns on numba and 283 ns on clang of an ambiguous query and nothing on a unique one — ~1 % of a random workload, below the 3–9 % noise of the machine that would have to demonstrate it — and the cost was a shortcut-layout version bump, therefore `DATA_FORMAT_VERSION`, therefore an ordered two-distribution release. **The shortcut index format change spent that bump for its own reasons, so the second leg went**, and the maintainer took it: it ships as one `uint8` per *distinct* candidate list — 2.5 KiB, since it depends only on the list and deduplicates with it — where the ~1 % is what offsets the extra indirection that structure introduces. Kept here rather than deleted because the *standalone* verdict is unchanged: on its own it is still ~1 % for a release, and the 2025 reasoning was right. What moved is that the price became sunk, not that the win grew.

- **Three rules outlive any particular set of cells, and a change to the shortcut index's shape owes all three.** The shape itself is priced in the [aligned-index decisions](longitude-latitude-aligned-index-decisions.md); these are the constraints on getting there.

  * **Price a level by what it costs per candidate polygon it removes, not by what it gains.** Finer cells always test fewer candidates; the question is the exchange rate, and it degrades steeply with depth, because a table over a regular grid grows with the level while the boundaries it indexes do not. A gain that is real is still refused when the memory per polygon removed is an order worse than the level before it.
  * **The file stamps its own grid shape, because the binary layout cannot distinguish one from another.** `layout_version` is the same at every shape, so a stale data directory would silently index the wrong cells; the header carries the shape and the reader rejects a mismatch. Any shape parameter a reader's arithmetic depends on belongs in that header.
  * **Shrinking cells must be re-checked for correctness, not merely re-timed.** An index built before the edge-crossing test answered a point in the Strait of Malacca wrongly, because the candidate rule ignored polygon edges crossing a cell - a defect class that *grows* as cells shrink while every timing improves. [`scripts/audit_shortcut_candidates.py`](../../../scripts/audit_shortcut_candidates.py) is what re-checks it.

- **The `unique` and `ambiguous` benchmark strata are not comparable across a change to the shortcut index.** Both are a *classification by that index*, so changing it re-labels the points: the easy members of the old ambiguous set become unique and leave a harder residue, and a row moving is the relabelling rather than the change. `FIXTURE_VERSION` exists to be bumped for exactly this. Compare `random` and `on_land`, which are sampled independently of the index, or classify one shared point set by *each* index and time the subsets.
