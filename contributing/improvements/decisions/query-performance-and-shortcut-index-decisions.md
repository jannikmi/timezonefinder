# Query performance and shortcut index decisions

Do not re-propose these settled or refused options without new evidence.

- **Accelerating the slot arithmetic with numba or the C extension — measured 2026-08-23 and refused; the algebra was the win instead.** The lookup's bit arithmetic looked like a candidate for `njit`. It is not, and the measurement forecloses the whole family rather than one attempt: **an empty `njit` call costs ~98 ns**, against ~152 ns for the entire stage it would replace, so dispatch alone eats two thirds of the budget before any kernel runs. Both variants came out slower than plain Python (156 and 166 ns against 152), and the C extension is worse on the same grounds. This generalises — **no scalar per-query stage in the single-digit-hundreds of nanoseconds can be worth a dispatch boundary**. **Applied and shipped 2026-09-06, and the *form* of the fix is the part to keep:** `is_valid_lat`, `is_valid_lng` and `coord2int` were the last scalar stages paying a dispatch. The decorator came off them rather than their call sites inlining the bodies, which was measured and refused: ~40 ns more, for a second definition of the coordinate bounds. Worth -12.3 % of a random query on numba and **nothing without numba**, where `njit` was already transparent and no dispatch existed to remove.

- **What did pay was noticing the arithmetic reduces.** H3 puts the base cell immediately above the digits, so `base * stride + digits` is one contiguous bit field and the six-operation expression collapses to `(hex_id >> SLOT_DIGITS_SHIFT) & SLOT_MASK`. An identity over any 64-bit value, not a property of the cells that exist. Arithmetic 91 -> 40 ns, whole stage 152 -> 101 ns, and on a paired whole-query A/B **-5.1 % on a unique-zone query with 43 of 61 rounds faster** - both estimators agreeing, which is the bar. Shipped.


- **Justify the shortcut structure on load, memory and file size — never as a speedup.** Measured full `timezone_at`, paired and order-alternated, 61 rounds x 2,000 points on four fixture strata: neutral to slightly ahead, and small enough to stay off any headline. It changes how a cell's candidate list is stored, never which candidates come back, so it avoids exactly the same point-in-polygon tests. Two measurement designs that suggested otherwise were discarded: an isolated lookup omits the `match value: case int(zone_id)` the old code ran on the dict's answer (84 → 188 ns, and the table needs no equivalent), and a fixed A-then-B order credited the new structure with 13.3 % that was the first path warming shared code for the second.

- **Raster fast-path in front of the H3 index — dropped.** A ~2 MB lookup table answering unambiguous cells with one array index, falling through to H3 otherwise. Rejected: it buys query time with storage, and storage is the dimension this package can least afford to spend on.

- **Ocean-ness is tested with `str.startswith` on the scalar path, and with an id-indexed flag array only where a batch pays for one.** Settled 2026-08-20, extended when the land batch shipped. `OCEAN_TIMEZONE_PREFIX` is `r"Etc/GMT"`, which has no regex metacharacters, and `re.match` anchors at the start — so `startswith` is exactly equivalent and captures the whole measured saving (~250 ns per `timezone_at_land`, ~6 % of a mixed workload, inside the noise floor) in one line. Precomputing a boolean array indexed by zone id was refused *for the scalar path* on cost, not on merit: `timezone_at_land` receives a name and `is_ocean_timezone` takes one, so an id-indexed table means restructuring both plus a per-instance array `make memory` would show. The batch form is what changed the price rather than the argument — it holds ids already, and testing each answer's name per point is the work a batch exists to remove — so `ZoneNames.ocean_flags()` builds that array lazily on first use, with the trailing sentinel slot and the same race argument as the names gather array beside it. The part still refused: making the *scalar* path go through ids. The decoupling from zone naming the array would also buy — an upstream rename of the `Etc/GMT` family cannot silently change which results count as ocean — is now had for the batch and not for the scalar method; re-propose extending it only against an actual rename.

- **An accessor-lifetime export of the mmap is not forbidden, and `FileCoordAccessor` holds one — which is why `cleanup()` drops it before the close and not after.** Settled 2026-08-23, when the mapped fetch was refused on the noise floor; that half is superseded 2026-09-06 ([ranking rule](../improvement-ranking-and-eligibility.md)) and the resource-semantics half, which is what this entry is for, stands. The `BufferError` fixed in 8.3.0 made "never hold a live export" read like a standing rule. It is not one, but it is not free: an export left live at the close makes `mmap.close()` raise `BufferError`, `close_resource` swallow it, and the unmapping fall to collection. Both orderings are now right and pinned — `test_cleanup_closes_the_mapping_when_no_caller_holds_a_view` and `test_finder_cleanup_closes_the_mapping`. **Any further export inherits that obligation**, at whichever level holds it — drop it before the close, or every teardown silently goes back to a refused close. `PolygonArray.cleanup` is the other one: its `packed` kernel buffers export the same words on both backends, so they go before it releases the accessor. A *caller's* view still refuses the close, deliberately. So do not refuse a future held view on resource-semantics grounds alone, nor propose one on a per-fetch microbenchmark. **The generalisable half:** a per-fetch figure and a workload share are different quantities, and converting one into the other is where that refusal's own arithmetic went wrong — ~370 ns per fetch in isolation was written up as "~3 % of a mixed workload", and measured inside the query it was ~0.8 %, indistinguishable from noise at 9 of 15 rounds. Nearly 4x apart, and the ranking rule takes the second. Measure inside the query, alternating within one process.

- **Numba is not the fast path, and its scalar dispatch is why.** Recorded because "numba is the fast path" is the natural reading of the tox matrix and of `utils.py` preferring it, and it is not what the numbers say. On the packed kernel a lookup actually runs, numba is measurably behind clang across the size strata, both estimators agreeing, and behind on `timezone_at` too: `validate_coordinates` calls two njit'd scalar functions whose dispatch costs more than the pure-Python comparisons they replace, and every query pays that before any geometry. Do not quote a ratio from here — `make acceleration-paths` regenerates `docs/benchmark_results_acceleration_paths.rst`, the one place the current ranking is stated. Any future argument reaching for a faster kernel has to say which kernel. *Superseded evidence, #497, measured on the bare kernel before polygon layout 3:* the two were then within 5 % across three size strata — 239 against 252 ns on a 114-vertex polygon, 22.18 against 22.27 µs on a 47k-vertex one — the clang path's ~500 ns per candidate in `ffi.from_buffer` separating them on an ambiguous query, and the validator costing 270 against 218 ns. Sound for what it measured; the packed kernel does not behave that way.

- **Precomputing `last_zone_change_idx` into the shortcut binaries — refused twice, and reversed 2026-08-23.** Proposed as issue #256, closed in 2025 because throughput is dominated by point-in-polygon work, and as draft PR #348. The refusal rested on two legs: #497 sizes the win at 149 ns on numba and 283 ns on clang of an ambiguous query and nothing on a unique one — ~1 % of a random workload, below the 3–9 % noise of the machine that would have to demonstrate it — and the cost was a shortcut-layout version bump, therefore `DATA_FORMAT_VERSION`, therefore an ordered two-distribution release. **The shortcut index format change spent that bump for its own reasons, so the second leg went**, and the maintainer took it: it ships as one `uint8` per *distinct* candidate list — 2.5 KiB, since it depends only on the list and deduplicates with it — where the ~1 % is what offsets the extra indirection that structure introduces. Kept here rather than deleted because the *standalone* verdict is unchanged: on its own it is still ~1 % for a release, and the 2025 reasoning was right. What moved is that the price became sunk, not that the win grew.

- **What order a cell's candidates are tested in is its own record** - the [shortcut candidate ordering decisions](shortcut-candidate-ordering-decisions.md). Every alternative key is refused there, with the optimum constructed and priced, and the finding that the candidate loop is overhead-bound rather than geometry-bound.

- **Which H3 resolution the index is built at, and why 5 is refused, is its own record** - the [shortcut index resolution decisions](shortcut-index-resolution-decisions.md). Any argument that reaches for a finer or coarser index belongs there.
