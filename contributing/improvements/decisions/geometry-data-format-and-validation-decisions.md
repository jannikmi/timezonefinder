# Geometry, data format, and validation decisions

Do not re-propose these settled or refused options without new evidence.

- The shortcut index's binary shape, and the six alternatives refused while settling it, live in [shortcut index binary shape decisions](shortcut-index-binary-shape-decisions.md).

- **The ring rotation minimises a *size-weighted* span sum over *every* rotation — do not simplify either half back.** Expected edges scanned is `Σ size_b · span_b`, so dropping the weight counts a ragged block holding one edge like a full block holding 128; and bounding the search at `POLYGON_BLOCK_SIZE` misses the minimum for most rings, because a whole-block rotation moves the ragged block rather than merely relabelling. Measured on edges actually scanned over the real query pairs, against the original bounded-and-unweighted version: fixing both gives **0.941x**, and **fixing the search alone gives 1.001x — worse**. `scripts/block_index.py` carries the mechanism, the cost and the remaining numbers.
  - **The generalisable half:** widening a search against a wrong objective finds a better answer to the wrong question. Check what is being minimised before enlarging the space it is minimised over, and weight an expected cost by the units that actually cost — a count of blocks is not a count of edges.

- **Six decimal places, and the packaged data is stored on that grid — settled 2026-08-31, and it retired GH-542.** timezone-boundary-builder publishes at most six decimals, so six is not a choice this package makes but the resolution its source has. **Coarser loses real geometry:** five decimals changes **48.8 % of sampled border locations at 10 cm, 2.3 % at 50 cm** (PR #576, closed unmerged — this is the only surviving record). **Finer does not exist:** over 3,589,489 sampled 2026c coordinate literals the decimals published are `{1: 307, 2: 2064, 3: 12778, 4: 57575, 5: 430811, 6: 3085954}`, never seven. **And the seventh digit the package used to store was an error:** `coord2int` truncates toward zero — right for a query, wrong for the source — so the vertex published as `13.358` shipped as `133579999`, 1.1 cm short, on 6.27 % of all coordinates. Rounding onto the source grid reproduces it for 400,000 of 400,000 sampled, worst error 0; **flooring does not** (93.73 %, worst error 11 cm), which is why `scripts.utils.source_coord2int` rounds.
  - **What it bought:** residuals counting source steps rather than storage steps is log2(10) ~ 3.3 bits off every field, taking `coordinates.bin` 38,318,592 B → 31,735,692 B — half of the 63,423,696 B this format generation began at. It costs one multiply per residual read, and a hard requirement that compiled data sit on the grid.
  - **Refused: keeping the seventh digit as a bitplane.** Every value is `10*m - e`, `e` in `{0, 1}`, so it could be kept losslessly in one bit — but `e` is 1 for 6.06 % of them, so that bit carries 0.33 bits. ~33.5 MB against ~31.9 MB, and roughly double the decode, to preserve a truncation artifact. Entropy-coding it down would reintroduce the variable-length decode this format exists to avoid.
  - **The precondition is checked:** an upstream publishing a seventh decimal would have information rounded away silently, every downstream check still passing. `source_coord2int` refuses it; `tests/test_coordinate_precision.py` holds the packaged data to the grid from the other side.

- **A polygon encoding that decodes sequentially is refused, however well it compresses — settled 2026-08-30.** Delta+zigzag+LEB128 and int16-delta-with-escape lose on the same ground: LEB128 element boundaries are only found by scanning and delta carries a prefix-sum dependency, so each puts an O(N) serial pass in front of the O(N) ray cast. **That ray cast is where this package's worst latency already is** — `on_land` runs p50 1.00 µs against p99 39.71 µs, and query time correlates 0.92 with vertices tested but only 0.76 with candidate *count*: the tail is one test against a huge ring, not many candidates. **The generalisable half:** compression paid per *query* competes with the geometry it decorates, and here the geometry is the expensive thing. A block-structured encoding is randomly addressable and compresses as well, and both halves of that shipped: the latitude block index and then the frame-of-reference payload it carries, which reaches 31,735,692 B from 63,423,696 B with a decode that is two loads, a shift and a multiply (`docs/data_format.rst`, *Latitude Block Index* and *Block Payload*).
- Generic payload compression and install-time unpacking are separately refused in [payload-compression and install-time-unpacking decisions](payload-compression-and-install-time-unpacking-decisions.md).

- **Hole polygons cannot be dropped, and the reason is a cycle rather than a measurement — settled 2026-09-02, closing GH-513.** Coverage is not removability: every hole is covered by other zones, which says the right zone is among the candidates, not that it is reached first. Dropping holes needs a precedence relation over *zones* — as the H3-independence decision below requires — and **the one the geometry demands is cyclic**, so no candidate ordering satisfies it and no ordering work would unblock this. It is structural: precedence relates zones, containment relates rings, and a second-order enclave maps two opposite ring relations onto one zone pair. Deriving precedence from zone size fails separately, systematically on the ocean zones — huge by area and *first* by the vertex-count key `optimise_shortcut_ordering` sorts on. **The generalisable half:** "contained implies smaller" is a claim about containment, which overlap does not inherit. Dropping only the contradictory holes keeps the whole subsystem, so #509's reference encoding is permanent. Evidence: [the item file](../items/lookup-geometry-and-data-format/gh-513-drop-hole-polygons-entirely.md) and the two hole prototypes; `tests/test_hole_lookup_regression.py` is the gate.

  * **A zone-precedence *engine* is rejected with it** — political rules, overlap scoring and caching, explored on the #350 branch. There is no relation for it to encode, and it would make answers depend on hand-maintained political configuration: an accuracy liability for a package that does not simplify. Also in `prototypes/README.md`.

- **Precedence between two *overlapping* zones is decided by containment — settled 2026-09-08, and it is not the engine above.** Of two overlapping zones, the one for which the shared area is the larger share of *itself* is the enclave and wins. It is derived from the geometry, not configured; it is computed once per zone pair, so it is the same wherever they meet and states nothing in terms of the H3 index; and it is *applied* only inside a shortcut cell one boundary polygon covers entirely, which is what makes it tractable — the relation there is acyclic where GH-513's hole relation was cyclic. `scripts/zone_precedence.py` holds the rule, the reduction that spares it any polygon clipping, and the guards. Refused with it, so that neither is re-proposed: **lower polygon or zone id wins**, since ids follow upstream GeoJSON feature order and an added zone flips a winner with no geometry change; and **deciding per cell** from whichever polygon covers that cell, which is not a property of the zones at all and gave 2 of 7 pairs opposite winners in different cells, so two points either side of a cell boundary would be answered differently. **Smaller total zone area wins** is not a third option: the two ratios containment compares share the shared area as their numerator, so within this scope it is algebraically the same rule, which is why it was measured to disagree on 0 of 118 overlapping pairs.

- Format-marker and release-batching decisions live in [data-format version-marker and release-batching decisions](data-format-version-marker-and-release-batching-decisions.md).

- **No boundary polygon's coordinates can be dropped, and the unique-zone cells create no candidates for it.** Settled 2026-08-23, measured against release 2026c. The proposal was to delete the geometry of polygons reachable only through single-zone shortcut cells — a query answered from such a cell reads no geometry, so such a polygon would be paying for nothing — and to degrade `get_geometry` to a bounding box for them. There are none, and the reason is structural rather than a property of the release or the index resolution. The reasoning, the measurements and the three separate objections to the weaker form of the idea — dropping the polygons `timezone_at` returns by elimination without ever testing — are documented under *Why the index makes no polygon redundant* in `docs/data_format.rst`, next to the hole sections they parallel. Rejected with it: keeping the bounding boxes as a `get_geometry` fallback, which is what would make the failure a silent wrong answer rather than a loud missing one. The bbox vectors are already separate per-polygon files, so the fallback is cheap to build — that is the trap, not the argument for it.

- **A correctness property is never expressed in terms of the H3 shortcut index.** Settled 2026-08-21, while removing GH-301 as GH-513's blocker. Zone precedence — which zone a query should reach first where several cover a point — is a property of the zones and their geometry. Stating it per H3 cell would make correctness depend on the spatial index, whose resolution, layout and hybrid unique-zone encoding are implementation details the package is free to change; a future resolution change would then silently move answers rather than only performance. The index is a candidate *filter* and may be reordered, rebuilt or replaced freely, which is exactly why nothing load-bearing may be derived from its structure. It is what forced GH-513's question into the zone-level form that turned out to be cyclic, and it binds any future argument that reaches for the shortcuts to prove something about answers.

- **A coordinate-reading interface never infers which column is which.** Settled in #504. Its first cut read bare `lng,lat` pairs positionally; for any longitude between -90 and 90 — most of the populated world — the swapped pair is still a valid coordinate, so a wrong order returns a real but wrong zone rather than raising. 13 of 15 major cities tested have a silently valid swap, and the wrong answers look plausible (Moscow's pair swapped gives `Asia/Tehran`). What shipped resolves columns by header name or by an explicit flag, and rejects input it cannot resolve instead of guessing. The same reasoning binds any interface that takes coordinates in bulk, and the batch lookups are built on it: one keyword array per axis, an `(N, 2)` array rejected rather than read by column position. It still binds a file format or an `update_data`-style subcommand.
