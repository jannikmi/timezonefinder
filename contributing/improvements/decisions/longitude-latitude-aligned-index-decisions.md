# Longitude/latitude-aligned index decisions

Do not re-propose these settled or refused options without new evidence. The index they are priced against — H3 at resolution 4, chosen over 3 and 5 — and the refused raster fast path are in the [query performance and shortcut index decisions](query-performance-and-shortcut-index-decisions.md).

- **The shortcut index is an aligned grid tree, and every family measured against it is refused**; the table prices the families at a 0.9375° root, and the configuration to ship is the sweep's below. A grid tree is a dense grid aligned with longitude and latitude whose cells that several zones can own refine into fixed k×k blocks, each level reached by one floor division per axis — a quadtree whose top levels are flattened into a grid and whose lower levels need no search. The sweep that chose it compiled 35 candidates and controls from the packaged 2026d boundaries and answered each through the real query path, ordering candidate lists by the converter's own rule, against a resolution-4 H3 control ordered the same way: Intel Xeon (Cascade Lake, 2.8 GHz) on 4 vCPUs of a KVM cloud VM, Linux, Python 3.13.16, mapped, ranges spanning clang and numba, every time below a win in 26–31 of 31 paired rounds, resident figures being index array bytes rather than a process measurement. That H3 run is `prototypes/latlng_index_bench.py` at `47b50d4`, whose timing filter has to admit the −180-meridian probes its trees answered from the wrong column; the script now prices every candidate against the shipped grid tree instead, and `h3` is not installed by any dependency group.

  * **Why it wins.** The scalar gain is the `h3.latlng_to_cell` call, replaced by integer arithmetic before a table read; the batch gain is that a grid cell vectorises and an H3 cell does not. Selectivity comes from exact cells: computed from the truncated integer coordinates the kernel reads, each owns its north and east edges, the kernel's own convention — a polygon contains a point on its east or north boundary, never its west or south — so the zone across an edge is not a candidate. Alignment pays most on the 7.5° meridians the ocean zones share: unaligned grids of the same size test 14–24 % more polygons per random query. A flat grid then spends 2 bytes on every cell, ocean included; the tree spends them where borders are, reaching 0.234° cells there at 507 KB, and timed head to head the recommended tree beats the flat equal-area grid by 7–8 % per random and 10–11 % per on-land scalar call and 14–28 % per batch.
  * **The tree's speed is in its lookup.** Unrolled per depth, it costs a flat grid's integer arithmetic plus one read per level a point descends; a generic loop over the levels lost to the flat grid. Head to head, one level of 4×4 blocks is 4–6 % faster per scalar call than two levels of 2×2 with the same cells (22–24 of 31 rounds) and 8–15 % faster per batch, for 65 KB more.
  * **Within the [800 KB cap on the index binary](../../project/project-purpose-runtime-constraints-and-non-goals.md), the configuration to ship is a 0.75° root with one level of 4×4 blocks (0.1875° cells, 696 KB).** `prototypes/grid_tree_config_sweep.py` swept 165 configurations - roots aligned with the 7.5° meridians, one to three levels with a block side each, full and selective refinement - under a rule fixed before its deciding run, on two x86-64 Xeon VMs. Against a legacy-order control of the shipped 0.9375° cells it is faster in all four cells, scalar and 256-point batch on random and on-land points, on both machines - 3-10 % per scalar call and 3-20 % per batch - and faster than the 0.9375° shape head to head, in three cells on one machine and all four on the other, for 182 KB more. It refines every multi-zone cell and fits `int16`, so the shipped reader reads it once `SHORTCUT_ROOT_COLUMNS` is 480; the sweep's FINDINGS and committed runs hold the figures. The 1.25° root with 2×2 then 4×4 blocks, faster than the control in three cells, loses to it head to head per random scalar call and batch. Over the cap, the 1.875° root with two levels of 4×4 (957 KB) and the flat 0.25° equal-angle grid (2.1 MB) are refused however large their margin.
  * **Exact cells against touch-inclusive ones**, against the same control in the same run: counting every polygon that touches a cell edge, the 0.5° grid tests 50 % more polygons per random query and gives up 8–11 points of random scalar speed and 2–6 on land.
  * **What a cell shape trades away on the axes measured here — file and array bytes, counts, paired query time: nothing.** What it does move is `TimezoneFinderL`, whose answer *is* a cell's fallback zone, so changing the cells changes it cell by cell; agreement with the full lookup rises with every tree refining to 0.234° or finer. **It can also move `timezone_at` in the two places where candidate order decides rather than geometry** — a point no polygon owns as spelled, and a point two zones cover — because the legacy order ranks a cell's zones by their vertex totals *inside that cell*. Price both before adopting a cell shape; the [fallback semantics](shortcut-ordering-and-fallback-semantics.md) settle the first of them independently of any index, and a replacement index has to wrap −180° to the last column rather than clamp it to the first, which `tests/test_minus_180_meridian_and_minus_90_parallel.py` fails on.
  * **Unpriced:** loading and construction time and `make memory`, which the resolution decision priced; mapped page residency; an ARM server class; a rectangle port of the work optimizer; and overlap precedence beyond the sample — the legacy order ranks zones by their vertex totals within a cell, so a new cell shape can move an overlap's winner, though all 289 sampled points in two zones kept H3's. None can reverse the scalar or batch result.
  * **The exactness rests on the kernel's edge convention, which `tests/test_point_in_polygon_boundary_convention.py` pins on every kernel**: a kernel change moving boundary points to the other polygon would make aligned cells misanswer one-unit strips along every aligned border while every sampled test passed. All 24 candidates the script builds match the shipped tree's answers on 30,000 fixture points, on points on and beside their own cell edges and on the 7.5° and whole-degree lines borders follow, the −180 meridian included, on both kernels, through both the scalar and the batch path. Every candidate offers the Strait of Malacca witness's polygon.

- **Refining selectively under the cap is refused for this package's NumPy batch reader, however the cells are chosen.** A selective tree refines only the multi-zone cells whose expected work pays for their block, so it spends the cap where queries cost most and tests the fewest polygons of any tree within it. It loses where it is timed, for two reasons better selection cannot touch. The batch descent pays a fixed cost per level and per selective check on every 256-point batch, whatever share of its points descends, and every multi-level or selective tree `prototypes/grid_tree_config_sweep.py` screened was slower than the control on random batches. And the polygon loop a finer leaf shortens is a minor share of a query, so the bytes a one-level tree leaves under the cap buy a few per cent of scalar time at most, below what a paired comparison reads as faster. One level refined selectively, choosing cells by expected work that counts vertices as `scripts/shortcut_ordering.py` prices a candidate, beats the sweep's stop-index rule on counts and is still no faster per scalar call and slower per random batch; so is the encoding the shipped reader reads unchanged, which points every unrefined cell at one uniform block per distinct list and pays a block per list. The exploratory `selective` stage of `prototypes/grid_tree_config_sweep.py` holds the counts and the times. Reopen only with a compiled batch lookup, where a level costs nanoseconds rather than array passes, and then select by the ordering optimiser's exact area integrals rather than a point sample, which leaves single-digit training points in most cells.

- **Refused, as replacements for this package's Python reader.** These families were timed only on consumer hardware, so their times are not kept; what refuses them is the sizes, the counts and a lookup that searches where the tree divides, and their code is gone, so a re-proposal rebuilds them and times them on server hardware against the shipped tree.
  * **Linear quadtrees**, `node-geo-tz`'s world quadrants and the same under 7.5° roots. The 7.5°-rooted one at depth 5 makes exactly the recommended tree's polygon tests at 757 KB, but finds a leaf by `bisect` over a sorted key array, a search per lookup where the tree does one division per level. The grid tree is that layout question answered.
  * **`tzf-rs`'s tile pyramid**, exact Web Mercator tiles at zooms 3–10 or 3–11 probed coarsest first over a 1° candidate grid: one binary search per zoom, and Mercator edges cannot follow the integer grid.
  * **The two-tier split**, an exact one-zone layer before a coarse candidate grid: larger than the grid it splits and a third more polygons tested.
  * **Three levels of 2×2.** Reaching 0.234° cells from a 1.875° root saves bytes for a third descent on every refined lookup, and every three-level tree the sweep screened read slower than the control per random batch. Reaching 0.117° from a 0.9375° root is over the cap however it is stored: its middle level indexes more blocks than `int16` holds, 1,048 KB in `int32` and 860 KB even if it fit.
  * **Flat grids, aligned or not, and touch-inclusive cells** — dominated by the grid tree, and the latter by exact cells. An earlier verdict that grids are slower than H3 came from touch-inclusive cells and a per-row lookup never paired with a control.
