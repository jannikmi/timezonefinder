# Longitude/latitude-aligned index decisions

Do not re-propose these settled or refused options without new evidence. The index they are priced against — H3 at resolution 4, chosen over 3 and 5 — and the refused raster fast path are in the [query performance and shortcut index decisions](query-performance-and-shortcut-index-decisions.md).

- **Measured 2026-10-11: an aligned grid tree beats the resolution-4 H3 index on every axis measured here, at less than H3's footprint; on 2026-10-12 the maintainer decided to replace H3 with the shape in bold below, implemented as [IDX-6](../items/lookup-geometry-and-data-format/idx-6-replace-the-h3-shortcut-index-with-the-grid-tree.md) and the slices it lists.** A grid tree is a dense grid aligned with longitude and latitude whose cells that several zones can own refine into fixed k×k blocks, each level reached by one floor division per axis — a quadtree whose top levels are flattened into a grid and whose lower levels need no search. `prototypes/latlng_index_bench.py` compiled 35 candidates and controls from the packaged 2026d boundaries and answered each through the real query path, ordering candidate lists by the converter's own rule, against an H3 control ordered the same way. Apple M1 Pro, Python 3.14.2, mapped; ranges span clang and numba, and every time below won all 31 paired rounds. Resident figures are index array bytes, not a process measurement. Rerunning the prototype from `master` at 87be6bef reproduces the grids and grid trees, counts exactly; the refused families below were measured by its 2026-10-11 version and have since been dropped from it.

  * **Why it wins.** The scalar gain is the `h3.latlng_to_cell` call, about half a unique query by the [measured baseline](../query-performance-measurement-baseline.md), replaced by integer arithmetic before a table read; the batch gain is that a grid cell vectorises and an H3 cell does not. Selectivity comes from exact cells: computed from the truncated integer coordinates the kernel reads, each owns its north and east edges, the kernel's own convention — a polygon contains a point on its east or north boundary, never its west or south — so the zone across an edge is not a candidate. Alignment pays most on the 7.5° meridians the ocean zones share: unaligned grids of the same size test 14–24 % more polygons per random query. A flat grid then spends 2 bytes on every cell, ocean included; the tree spends them where borders are, reaching 0.234° cells there at 507 KB, and timed head to head the recommended tree beats the flat equal-area grid by 6.5–6.6 % per random and 10–12 % per on-land scalar call and 15–25 % per batch.
  * **The tree's speed is in its lookup.** Unrolled per depth, it costs a flat grid's integer arithmetic plus one read per level a point descends; a generic loop over the levels cost ~280 ns more per lookup and lost to the flat grid. Head to head, one level of 4×4 blocks is at least as fast per scalar call as two levels of 2×2 with the same cells (2–4 %, three of four pairings unresolved) and 8–14 % faster per batch, for 65 KB more.
  * **Exact cells against touch-inclusive ones**, against the same control in the same run: counting every polygon that touches a cell edge, the 0.5° grid tests 50 % more polygons per random query and gives up about 8 points of random scalar speed, up to 2 on land.
  * **What it trades away on the axes measured here — file and array bytes, counts, paired query time: nothing.** `TimezoneFinderL` answers move cell by cell, its fallback zone belonging to a cell; its agreement with the full lookup rises with every tree refining to 0.234° or finer. Points no polygon owns, on the −180° meridian and the −90° parallel, take the new index's last remaining zone: 146 of 200 sampled points at exactly −180° move under the recommended tree, 141 of them from `Etc/GMT-12` to `Etc/GMT+12`, three Chukotka points from `Asia/Anadyr` and two from `Etc/GMT-11`, and no test pins any. The shipped index's one-point lead over the control in `TimezoneFinderL` agreement on random points is the converter's H3-specific work optimizer; on the query it is within noise (at most 3 %, unresolved). Dropping `h3` saves its ~20 ms import and 2.3 MB install only once the converter and `timezonefinder/_data_integrity.py` stop using it too.
  * **Unpriced:** loading and construction time and `make memory`, which the resolution decision priced; mapped page residency; a second machine class; a rectangle port of the work optimizer; and overlap precedence beyond the sample — the legacy order ranks zones by their vertex totals within a cell, so a new cell shape can move an overlap's winner, though all 289 sampled points in two zones kept H3's. None can reverse the scalar or batch result.
  * **The exactness rests on the kernel's edge convention, so an adoption pins it with a test**: a kernel change moving boundary points to the other polygon would make aligned cells misanswer one-unit strips along every aligned border while every sampled test passed. All 34 gated candidates matched the control on 30,000 fixture points, on points on and beside their own cell edges and on the 7.5° and whole-degree lines borders follow, on both kernels, through both the scalar and the batch path, except the unowned points above. Every candidate offers the Strait of Malacca witness's polygon.

- **Refused in the same measurement, as replacements for this package's Python reader:**
  * **Linear quadtrees**, `node-geo-tz`'s world quadrants and the same under 7.5° roots. The 7.5°-rooted one at depth 5 makes exactly the recommended tree's polygon tests at 757 KB, but finds a leaf by `bisect` over a sorted key array, which costs more than the H3 call: scalar calls 10–16 % slower than H3, and 4–53 % across the family. The grid tree is that layout question answered.
  * **`tzf-rs`'s tile pyramid**, exact Web Mercator tiles at zooms 3–10 or 3–11 probed coarsest first over a 1° candidate grid: one binary search per zoom, scalar calls 2.4–2.7x slower, batches 12–28 % faster, and Mercator edges cannot follow the integer grid.
  * **The two-tier split**, an exact one-zone layer before a coarse candidate grid: larger than the grid it splits and a third more polygons tested.
  * **Three levels of 2×2.** Reaching 0.234° cells from a 1.875° root saved 139 KB against the chosen shape for 4–9 points of scalar speed; reaching 0.117° from a 0.9375° root was about as fast as two levels of 4×4 at 84 KB more.
  * **Flat grids, aligned or not, and touch-inclusive cells** — dominated by the grid tree, and the latter by exact cells. A 2026-09-26 run that used touch-inclusive flat grids judged them slower than H3; its counts equal this run's touch-inclusive control, and its timing came from a per-row lookup never paired with a control.
