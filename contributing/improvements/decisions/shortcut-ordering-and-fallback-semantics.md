# Shortcut ordering and fallback semantics

## Coverage and the two lookup contracts

Settled by the maintainer, 2026-09-09: the full dataset including ocean timezones may be treated as covering the globe for `timezone_at()`. Uncovered slivers are not a blocker for shortcut ordering, and proving coverage cell by cell is not required to justify its untested final-zone fallback. This is an accepted dataset assumption, not a claim that a geometric overlay proves exact coverage.

Users who want to avoid that fallback use `certain_timezone_at()`, which checks containment and can return `None`. Do not require the main lookup to adopt that contract. The full-coverage assumption is specific to the dataset with oceans; it is not evidence that an arbitrary custom or land-only dataset covers the globe.

## Overlap ties

When compared spherical zone areas are equal, use the timezone identifier string as the secondary key, in ascending lexicographic order. This maintainer decision replaces leaving equal-area precedence unresolved. Use the identifier, not a numeric zone index or iteration order. Equality means equality of the computed area values; no near-equality tolerance was requested. This completes the tie rule, without making a polygon's area clipped to an H3 cell a semantic precedence rule. Holes remain excluded from their owning polygons.

## Legacy shortcut-ordering ties

When two zones have equal legacy per-cell vertex totals, the timezone identifier string decides, in ascending lexicographic order; within one zone, equal polygon vertex counts fall back to the polygon id, which reorders nothing a zone answer depends on. Decided by the maintainer on 2026-09-26 and implemented in `optimise_shortcut_ordering`. The primary key is unchanged, and the converter's cross-zone precedence no longer depends on set iteration, numeric zone ids or the spatial index, so the same boundary release always compiles to the same `shortcuts.bin`. **Why a tie rule can move answers when the optimizer cannot:** the work optimizer's guarantee is relative. It reorders a cell only where `safe_to_reorder` certifies that its candidates are disjoint across zones and cover the cell's envelope, and that leaves the full lookup's answers unchanged. Where the gate refuses, an overlap or gap may exist, so the legacy order *is* the definition of the answer there and the optimizer keeps it. The tie rule changes that definition rather than reordering against it: in tied cells, the definition had been set iteration order, which follows polygon ids modulo the set's table size. So it can move `timezone_at` only for a point in an overlap or gap, and `TimezoneFinderL` for the whole cell, because that lookup answers the untested final zone. The optimizer never promised `TimezoneFinderL` anything either; it may pick any final zone where the gate passes. Measured against the published 2026d index, the rule moves 3 of 288,122 cells:

- `84a9447ffffffff` reorders two equal polygons of one zone, so no answer can move.
- `84eeaa9ffffffff` (71.4°S, 17°W) holds only the 5-vertex sector polygons of `Antarctica/Rothera` and `Etc/UTC`, which split it 48:52 with no overlap or gap among 20,000 sampled points. Rothera's name now sorts first, making `Etc/UTC` the final zone, so every `TimezoneFinderL` answer in the cell moves from Rothera to `Etc/UTC`. `timezone_at` moved none of 20,000 sampled points. The gate refused this cell only because its envelope, the padded bounding box of the cell's cap, reaches a corner outside the cell that is `Etc/GMT+1` (0.33 % of the envelope), and `Etc/GMT+1` is not a candidate. That is the envelope's documented conservatism, not a defect. A tighter enclosure is GEOM-3's planar-versus-spherical question, not a tie-rule matter.
- `84eeaa1ffffffff` swaps the same two sectors ahead of a final `Etc/GMT+1`, so `TimezoneFinderL` is unchanged. Its refusal is real: the 12,362-vertex `Etc/GMT+1` boundary and the sectors' straight edges leave quantization gaps under 1 mm wide, 41 m² in all, along their shared borders. Only a point in such a gap could move, and none of 20,000 sampled did.

Not yet published: the [release-batching decisions](data-format-version-marker-and-release-batching-decisions.md) hold the rebuild for the H3 index's replacement, [IDX-6](../items/lookup-geometry-and-data-format/idx-6-replace-the-h3-shortcut-index-with-the-grid-tree.md). **Refused:** replacing the primary key with spherical zone area, because that would take part of PREC-1 before its broader precedence decision; and determinizing only within a zone, because that would leave cross-zone binaries unreproducible, and comparing replacement indexes needs reproducible ones. **Do not drop either secondary key as redundant:** a build that falls back to set order differs only in tied cells and still validates, so only the permutation test in `tests/test_shortcut_ordering.py` notices.

## Precedence is independent of the index

- **A correctness property is never expressed in terms of the H3 shortcut index.** Settled 2026-08-21, while removing shortcut-candidate ordering as GH-513's blocker. Zone precedence — which zone a query should reach first where several cover a point — is a property of the zones and their geometry. Stating it per H3 cell would make correctness depend on the spatial index, whose resolution, layout and hybrid unique-zone encoding are implementation details the package is free to change; a future resolution change would then silently move answers rather than only performance. The index is a candidate *filter* and may be reordered, rebuilt or replaced freely, which is exactly why nothing load-bearing may be derived from its structure. It is what forced GH-513's question into the zone-level form that turned out to be cyclic, and it binds any future argument that reaches for the shortcuts to prove something about answers.
