# Payload compression and install-time unpacking decisions

Do not re-propose these settled or refused options without new evidence. Recorded in their own file because the [distribution and release decisions](data-distribution-packaging-and-release-decisions.md) sit at the 2,000-word budget `tests/test_contributor_memory.py` enforces, not because compressing the payload is a separate topic from distributing it.

- **Shipping the packaged data compressed and unpacking it once at install — rejected, 2026-08-30.** Proposed three times — #293, the closed #392 attempt, and again once the data became its own distribution — so the refusal is recorded with its numbers rather than re-derived a fourth time. **What the split did not change:** a wheel has no install-time hook. `pip` unpacks the zip and runs no project code, and `timezonefinder-data` is a wheel, since `publish_data.yml` builds `--wheel` only; moving the payload into its own distribution changed what is inside the zip, not whether anything runs while it is unpacked. **What the split did change, and why that still loses.** The earlier refusal rested on *an sdist install would force a compiler on every user*, which no longer holds for a distribution that is data plus one constant — so sdist-only is now buildable by anyone, and it is still refused. Collecting the win means publishing **no** wheel, because pip prefers one whenever both exist: that breaks every `pip install --only-binary=:all:` and puts a build-backend download in front of installs that work from a local wheelhouse today. It buys the download axis (#317) alone, and on the installed-footprint axis #293 actually asked about it goes *backwards*, since pip keeps the wheel it built in `~/.cache/pip/wheels` beside the unpacked data. **Measured 2026-08-30 over the packaged `coordinates.bin` (63,423,696 B), against the 51.5 MB wheel shipping it today:** solid zstd −19 → 40.3 MB and solid xz −9 → 25.8 MB, both needing the whole file written out before the first lookup; independent-block lzma −9 at 256 KiB → 34.0 MB is the only variant that keeps random access, and therefore the only one that shrinks the *install* rather than the download. **That last row is what settles it.** The measured delta+varint candidate reaches 35.3 MB losslessly at the same precision — 1.3 MB behind the best random-access codec — and pays none of its costs: no codec dependency, no unpack step, no writable-directory requirement, no read-only-container failure mode, and it decodes to a plain integer array rather than to a block with no zero-copy path. Generic compression is dominated by the format work already ranked ahead of it. **Refused alongside, because it is the next thing suggested:** a `.pth` file, the closest thing to an install hook that exists — it does execute, but on every interpreter start in that environment, before any import, and its failure mode is a broken interpreter rather than a failed import. **And the pressure this was for has largely dissolved:** a data release is now one `py3-none-any` artifact of ~51.5 MB in a PyPI project of its own, which [PYPI-1](../items/packaging-distribution-and-release/pypi-1-the-pypi-project-holds-11-37-gb-of-pre-split-releases.md) measures at order 190 data releases of quota headroom — so the storage argument that carried #317 no longer reaches the payload at all, and the quota actually near its limit is the `timezonefinder` project's 11.37 GB of pre-split releases, which compressing the data does not touch. **Re-propose only with** an argument that survives the wheel having no install hook, or a measurement showing a random-access codec beating delta+varint by enough to pay for the dependency.
