# Repository and workspace layout decisions

Do not re-propose these settled or refused options without new evidence. Recorded in their own file because the [data distribution, packaging, and release decisions](data-distribution-packaging-and-release-decisions.md) sit at the 2,000-word budget `tests/test_contributor_memory.py` enforces, and because how many repositories and workspace members this project has is a bounded subject on its own - both decisions below answer the same recurring proposal to restructure the tree, and neither says anything about what the distributions contain.

- **One repository, two distributions — the data does not get its own repository.** Settled in
  #446, which was opened proposing an org holding `timezonefinder` and `timezonefinder-data`
separately. Publishing two PyPI projects from one repository is routine (a `uv` workspace, two Trusted Publishing entries, prefixed tags), so the question was only ever whether a second *repository* buys anything a second *distribution* does not. The argument that it did — every regeneration adds ~61 MiB to this repository's history permanently — **does not survive**: deleting the data directory leaves every past blob in place, so the clone stays ~357 MiB either way. Only a history rewrite reclaims it (GH-522), and that is available to a single repository; what stops the *growth* is not committing the file again (done 2026-08-31), likewise topology-independent. Against a second repository stand the writer/reader format sync the [data-pipeline rules](../../development/data-pipeline-format-versioning-and-release-order.md) already flag for `COORD2INT_FACTOR` / `DECIMAL_PLACES_SHIFT`, the deliberately shared `timezonefinder/_data_integrity.py`, doubled CI and release tooling for a solo maintainer, and a harder format-change bootstrap: across two repositories every format change needs a pre-release data wheel published from one before the other's pull request can go green. The generalisable part, worth applying to the next proposal of this shape: **ask whether a proposed repository split is really a distribution split.** Packaging, release cadence and download size are properties of the distribution; only history and access control are properties of the repository.

- **The workspace is asymmetric on purpose: `timezonefinder/` stays at the repository root and only `timezonefinder-data` lives under `packages/`.** Refused 2026-09-06 (GH-524, issue #524). The root `pyproject.toml` doubling as both the workspace root and the code package's own manifest is legal and `uv` supports it, so the asymmetry costs nothing until a *third* distribution appears — which is the move's only real justification, and by the issue's own words it is otherwise close to cosmetic. That trigger is not coming: GH-332 is the only third distribution on record and was answered "publish nothing" on 2026-09-05. Parking the move on the trigger was refused for the same reason a park needs a reachable trigger. The move itself is a wide, low-insight diff across exactly the machinery whose failure mode is "no release goes out" — `setup.py`'s root-relative `cffi_modules`, the seven dotted names in `[tool.setuptools] packages`, a `MANIFEST.in` that both `recursive-include timezonefinder` and `prune packages` so a naive move silently drops the code from the sdist, the `check-manifest` ignore list, and `build.yml`'s `cibuildwheel` step running against the repository root with no `package-dir` — plus a rebase across a rename for every open branch. **Whoever ever takes it needs a tag-ref rehearsal, not a green pull request:** the publish guard from #529 runs only on tag refs, so the first run that can report a broken wheel build root is the one already publishing. Applies to the next proposal to tidy the layout: **symmetry is not a reason; a second member of the symmetric set is.** The full rewiring inventory is kept in the [GH-524 entry](../items/packaging-distribution-and-release/gh-524-move-timezonefinder-under-packages-for-a-symmetric-workspace-layout.md) so a third distribution does not rediscover it.
