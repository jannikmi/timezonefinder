# Shortcut index cell shape and resolution decisions

Do not re-propose these settled or refused options without new evidence. This file holds which cells the shortcut index is made of; how the index is stored and what a lookup costs around it are in the [query performance and shortcut index decisions](query-performance-and-shortcut-index-decisions.md).

- **Raster fast-path in front of the H3 index — dropped.** A ~2 MB lookup table answering unambiguous cells with one array index, H3 otherwise. It buys query time with storage, the dimension this package can least afford.

- **The H3 shortcut resolution moved from 3 to 4 — measured 2026-08-23, with 5 refused.** Built, not modelled: every resolution below was compiled from the 2026c boundaries and priced in the shipped layout. Restated here rather than left in `prototypes/single_resolution_bench.py`, because a prototype is deletable and this verdict has to outlive it.

  | res | cells | unique | file | resident | candidates tested /10k queries |
  |---|---|---|---|---|---|
  | 3 | 41,162 | 74.5 % | 103 KiB | 143 KiB | 3,877 |
  | **4** | **288,122** | **89.1 %** | **596 KiB** | **1,000 KiB** | **1,566** |
  | 5 | 2,016,842 | 95.4 % | 4,029 KiB | 7,832 KiB | 667 |

  * **What resolution 4 bought, paired and order-alternated against a resolution 3 index in one process:** random −41.6 %, on_land −37.8 %, both 0 of 61 rounds where resolution 3 won. The committed report page moved from ~3.40 µs to ~2.02 µs per random lookup. The unique stratum is unchanged (−1.1 % on minima, 40 of 61 rounds — the estimators disagree, so: no effect), which is the expected shape: a unique-cell query does the same work at either resolution, and what changes is *how many* queries are unique.
  * **What it cost:** `TimezoneFinderL`'s heap 176 KiB → 1.01 MiB, the default finder's 1.13 → 1.96 MiB, construction 7.98 → 8.28 ms. **The mapped mode's resident set went down**, 32.4 → 26.1 MiB, because far fewer candidate polygons are fetched and so far fewer coordinate pages are faulted in — a second-order effect worth remembering when pricing a future level.
  * **The `ambiguous` benchmark stratum is not comparable across this change**, and neither is `unique`. Both are a *classification by the shortcut index*, so changing its resolution re-labels the points: the easy members of the old ambiguous set became unique, leaving a harder residue. `FIXTURE_VERSION` was bumped for exactly this. Compare `random` and `on_land`, which are sampled independently of the index.
  * **Resolution 5 is refused on the exchange rate, not on its gains, which are real.** Memory paid per candidate polygon removed is 0.019 KiB going 2→3, 0.371 KiB going 3→4 and **7.600 KiB going 4→5** — each level about twenty times worse than the last. The table is `122 * 8**res`, fixed by the resolution rather than by the data, so it is 99.7 % of the index at resolution 5. 7.8 MiB resident is more than the entire index format generation 1 used, and would take `TimezoneFinderL` from ~176 KiB to ~7.9 MiB.
  * **Resolutions above 5 are not worth measuring** — the table grows eightfold per level, so resolution 6 is ~63 MiB resident, the size of the polygon data it indexes.
  * **A hierarchical index over several H3 resolutions measured worse**, prototype deleted: the maximum resolution dominates the size, H3 cells do not nest so parents stay beside children, and extra probes cost more than they saved. **Not a refusal of multi-level indexes** (maintainer, 2026-09-19): exactly nesting cells were priced on 2026-10-11, below, and lose on the scalar call rather than on size.
  * **A resolution change is only safe because the file now stamps its own.** The binary layout is identical at every resolution, so `layout_version` cannot distinguish them and a stale data directory would silently index the wrong cells. The reader rejects a mismatch by name.
  * **It was also only safe after the edge-crossing test.** A resolution 4 index built before that answered a point in the Strait of Malacca wrongly, because the overlap test ignored polygon edges crossing a cell — a defect that grows as cells shrink. Any future level must re-check that class before being adopted, not merely re-time.

## Longitude/latitude-aligned cells against H3

- **Measured 2026-10-11: an aligned grid tree beats the resolution-4 H3 index on every axis measured here, at less than H3's footprint, and replacing H3 is [IDX-2](../items/lookup-geometry-and-data-format/idx-2-replace-the-h3-shortcut-index-with-a-longitude-latitude-aligned-grid.md)'s decision.** A grid tree is a dense grid aligned with longitude and latitude whose cells that several zones can own refine into fixed k×k blocks, each level reached by one floor division per axis — a quadtree whose top levels are flattened into a grid and whose lower levels need no search. `prototypes/latlng_index_bench.py` compiled 35 candidates and controls from the packaged 2026d boundaries and answered each through the real query path, ordering candidate lists by the converter's own rule, against an H3 control ordered the same way. Apple M1 Pro, Python 3.14.2, mapped; ranges span clang and numba, and every time below won all 31 paired rounds. Resident figures are index array bytes, not a process measurement. [Compact numbers](../measurements/latlng-index-2026-10-11.json).

  | index | file | resident | tests per random / on-land query | `timezone_at` random / on land | 256-point batch random / on land | `TimezoneFinderL` agrees |
  |---|---|---|---|---|---|---|
  | H3 resolution 4, shipped | 617 KB | 1,031 KB | 0.110 / 0.196 | — | — | 95.8 / 90.0 % |
  | H3 control | 610 KB | 1,024 KB | 0.112 / 0.200 | baseline | baseline | 94.8 / 90.0 % |
  | **grid tree: 0.9375° root, one level of 4×4** | 507 KB | 507 KB | 0.048 / 0.115 | −29 to −30 / −26 to −28 % | −71 to −72 / −59 to −61 % | 97.6 / 93.7 % |
  | grid tree: 0.9375° root, two levels of 2×2 | 442 KB | 442 KB | 0.048 / 0.115 | −26 to −28 / −23 to −25 % | −67 to −68 / −56 to −57 % | 97.6 / 93.7 % |
  | grid tree: 1.875° root, two levels of 4×4 | 957 KB | 957 KB | 0.026 / 0.068 | −30 to −31 / −29 to −32 % | −73 / −69 to −70 % | 98.6 / 96.2 % |
  | flat grid: equal-area, 0.375° rows | 616 KB | 619 KB | 0.083 / 0.189 | −24 / −17 to −18 % | −64 to −67 / −46 to −50 % | 96.2 / 90.4 % |
  | flat grid: equal-angle 0.46875° | 611 KB | 611 KB | 0.095 / 0.206 | −25 to −26 / −15 to −17 % | −62 to −65 / −40 to −45 % | 95.7 / 89.7 % |

  * **Why it wins.** The scalar gain is the `h3.latlng_to_cell` call, about half a unique query by the [measured baseline](../query-performance-measurement-baseline.md), replaced by integer arithmetic before a table read; the batch gain is that a grid cell vectorises and an H3 cell does not. Selectivity comes from exact cells: computed from the truncated integer coordinates the kernel reads, each owns its north and east edges, the kernel's own convention — a polygon contains a point on its east or north boundary, never its west or south — so the zone across an edge is not a candidate. Alignment pays most on the 7.5° meridians the ocean zones share: unaligned grids of the same size test 14–24 % more polygons per random query. A flat grid then spends 2 bytes on every cell, ocean included; the tree spends them where borders are, reaching 0.234° cells there at 507 KB, and timed head to head the recommended tree beats the flat equal-area grid by 6.5–6.6 % per random and 10–12 % per on-land scalar call and 15–25 % per batch.
  * **The tree's speed is in its lookup.** Unrolled per depth, it costs a flat grid's integer arithmetic plus one read per level a point descends; a generic loop over the levels cost ~280 ns more per lookup and lost to the flat grid. Head to head, one level of 4×4 blocks is at least as fast per scalar call as two levels of 2×2 with the same cells (2–4 %, three of four pairings unresolved) and 8–14 % faster per batch, for 65 KB more.
  * **Exact cells against touch-inclusive ones**, against the same control in the same run: counting every polygon that touches a cell edge, the 0.5° grid tests 50 % more polygons per random query and gives up about 8 points of random scalar speed, up to 2 on land.
  * **What it trades away on the axes measured here — file and array bytes, counts, paired query time: nothing.** `TimezoneFinderL` answers move cell by cell, its fallback zone belonging to a cell; its agreement with the full lookup rises with every tree refining to 0.234° or finer. Points no polygon owns, on the −180° meridian and the −90° parallel, take the new index's last remaining zone: 146 of 200 sampled points at exactly −180° move under the recommended tree, 141 of them from `Etc/GMT-12` to `Etc/GMT+12`, three Chukotka points from `Asia/Anadyr` and two from `Etc/GMT-11`, and no test pins any. The shipped index's one-point lead over the control in `TimezoneFinderL` agreement on random points is the converter's H3-specific work optimizer; on the query it is within noise (at most 3 %, unresolved). Dropping `h3` saves its ~20 ms import and 2.3 MB install only once the converter and `timezonefinder/_data_integrity.py` stop using it too.
  * **Unpriced:** loading and construction time and `make memory`, which the resolution decision priced; mapped page residency; a second machine class; a rectangle port of the work optimizer; and overlap precedence beyond the sample — the legacy order ranks zones by their vertex totals within a cell, so a new cell shape can move an overlap's winner, though all 289 sampled points in two zones kept H3's. None can reverse the scalar or batch result.
  * **The exactness rests on the kernel's edge convention, so an adoption pins it with a test**: a kernel change moving boundary points to the other polygon would make aligned cells misanswer one-unit strips along every aligned border while every sampled test passed. All 34 gated candidates matched the control on 30,000 fixture points, on points on and beside their own cell edges and on the 7.5° and whole-degree lines borders follow, on both kernels, through both the scalar and the batch path, except the unowned points above. Every candidate offers the Strait of Malacca witness's polygon.

- **Refused in the same measurement, as replacements for this package's Python reader:**
  * **Linear quadtrees**, `node-geo-tz`'s world quadrants and the same under 7.5° roots. The 7.5°-rooted one at depth 5 makes exactly the recommended tree's polygon tests at 757 KB, but finds a leaf by `bisect` over a sorted key array, which costs more than the H3 call: scalar calls 10–16 % slower than H3, and 4–53 % across the family. The grid tree is that layout question answered.
  * **`tzf-rs`'s tile pyramid**, exact Web Mercator tiles at zooms 3–10 or 3–11 probed coarsest first over a 1° candidate grid: one binary search per zoom, scalar calls 2.4–2.7x slower, batches 12–28 % faster, and Mercator edges cannot follow the integer grid.
  * **The two-tier split**, an exact one-zone layer before a coarse candidate grid: larger than the grid it splits and a third more polygons tested.
  * **Flat grids, aligned or not, and touch-inclusive cells** — dominated by the grid tree, and the latter by exact cells. A 2026-09-26 run that used touch-inclusive flat grids judged them slower than H3; its counts equal this run's touch-inclusive control, and its timing came from a per-row lookup never paired with a control.
