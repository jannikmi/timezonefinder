# Shortcut index cell shape and resolution decisions

Do not re-propose these settled or refused options without new evidence. This file holds which cells the shortcut index is made of; how the index is stored and what a lookup costs around it are in the [query performance and shortcut index decisions](query-performance-and-shortcut-index-decisions.md).

- **Raster fast-path in front of the H3 index — dropped.** A ~2 MB lookup table answering unambiguous cells with one array index, H3 otherwise. It buys query time with storage, the dimension this package can least afford.

- **The H3 shortcut resolution moved from 3 to 4 — measured 2026-08-23, with 5 refused.** Built, not modelled: every resolution below was compiled from the 2026c boundaries and priced in the shipped layout. Restated here rather than left in `prototypes/single_resolution_bench.py`, because a prototype is deletable and this verdict has to outlive it.

  | res | cells | unique | file | resident | candidates tested /10k queries |
  |---|---|---|---|---|---|
  | 3 | 41,162 | 74.5 % | 103 KiB | 143 KiB | 3,877 |
  | **4** | **288,122** | **89.1 %** | **596 KiB** | **1,000 KiB** | **1,566** |
  | 5 | 2,016,842 | 95.4 % | 4,029 KiB | 7,832 KiB | 667 |

  * **What resolution 4 bought, paired and order-alternated against a resolution 3 index in one process:** random −41.6 %, on_land −37.8 %, both 0 of 61 rounds where resolution 3 won. The committed report page moved from ~3.40 µs to ~2.02 µs per random lookup. The unique stratum is unchanged (−1.1 % on minima, 40 of 61 rounds — the estimators disagree, so: no effect), which is the expected shape: a unique-cell query does the same work at either resolution, and what changes is *how many* queries are unique.
  * **What it cost:** `TimezoneFinderL`'s heap 176 KiB → 1.01 MiB, the default finder's 1.13 → 1.96 MiB, construction 7.98 → 8.28 ms. **The mapped mode's resident set went down**, 32.4 → 26.1 MiB, because far fewer candidate polygons are fetched and so far fewer coordinate pages are faulted in — a second-order effect worth remembering when pricing a future level.
  * **The `ambiguous` benchmark stratum is not comparable across this change**, and neither is `unique`. Both are a *classification by the shortcut index*, so changing its resolution re-labels the points: the easy members of the old ambiguous set became unique, leaving a harder residue. `FIXTURE_VERSION` was bumped for exactly this. Compare `random` and `on_land`, which are sampled independently of the index.
  * **Resolution 5 is refused on the exchange rate, not on its gains, which are real.** Memory paid per candidate polygon removed is 0.019 KiB going 2→3, 0.371 KiB going 3→4 and **7.600 KiB going 4→5** — each level about twenty times worse than the last. The table is `122 * 8**res`, fixed by the resolution rather than by the data, so it is 99.7 % of the index at resolution 5. 7.8 MiB resident is more than the entire index format generation 1 used, and would take `TimezoneFinderL` from ~176 KiB to ~7.9 MiB.
  * **Resolutions above 5 are not worth measuring** — the table grows eightfold per level, so resolution 6 is ~63 MiB resident, the size of the polygon data it indexes.
  * **A hierarchical index over several H3 resolutions measured worse**, prototype deleted: the maximum resolution dominates the size, H3 cells do not nest so parents stay beside children, and extra probes cost more than they saved. **Not a refusal of multi-level indexes** (maintainer, 2026-09-19): exactly nesting cells were priced on 2026-10-11, below, and lose on the scalar call rather than on size.
  * **A resolution change is only safe because the file now stamps its own.** The binary layout is identical at every resolution, so `layout_version` cannot distinguish them and a stale data directory would silently index the wrong cells. The reader rejects a mismatch by name.
  * **It was also only safe after the edge-crossing test.** A resolution 4 index built before that answered a point in the Strait of Malacca wrongly, because the overlap test ignored polygon edges crossing a cell — a defect that grows as cells shrink. Any future level must re-check that class before being adopted, not merely re-time.

## Longitude/latitude-aligned cells against H3

- **Measured 2026-10-11: a dense grid aligned with longitude and latitude beats the resolution-4 H3 index on every axis at H3's file size, and replacing H3 is [IDX-2](../items/lookup-geometry-and-data-format/idx-2-replace-the-h3-shortcut-index-with-a-longitude-latitude-aligned-grid.md)'s decision.** `prototypes/latlng_index_bench.py` compiled every candidate from the packaged 2026d boundaries and answered through the real query path, ordering each candidate list by the converter's own rule and comparing against an H3 control ordered the same way. Apple M1 Pro, Python 3.14.2, mapped, both kernels; time ranges span clang and numba, and every one won at least 30 of 31 paired rounds. The [compact numbers](../measurements/latlng-index-2026-10-11.json) hold all 26 candidates.

  | index | cells | file | resident | tests per random / on-land query | `timezone_at` random / on land | 256-point batch random / on land | `TimezoneFinderL` agrees |
  |---|---|---|---|---|---|---|---|
  | H3 resolution 4, shipped | 288,122 | 617 KB | 1,031 KB | 0.110 / 0.196 | — | — | 95.8 / 90.0 % |
  | H3 control | 288,122 | 610 KB | 1,024 KB | 0.112 / 0.200 | baseline | baseline | 94.8 / 90.0 % |
  | equal-area, 0.375° rows, 7.5°-aligned | 296,832 | 616 KB | 619 KB | 0.083 / 0.189 | −24 / −16 to −18 % | −64 to −67 / −46 to −50 % | 96.2 / 90.4 % |
  | equal-angle 0.46875°, 7.5°-aligned | 294,912 | 611 KB | 611 KB | 0.095 / 0.206 | −25 to −27 / −17 to −20 % | −60 to −65 / −39 to −45 % | 95.7 / 89.7 % |
  | equal-angle 0.5°, 7.5°- and 1°-aligned | 259,200 | 539 KB | 539 KB | 0.097 / 0.211 | −26 / −14 to −16 % | −61 to −64 / −39 to −45 % | 95.6 / 89.5 % |

  * **Why it wins.** The scalar gain is the `h3.latlng_to_cell` call, about half a unique query by the [measured baseline](../query-performance-measurement-baseline.md), replaced by integer arithmetic before the same single table read. The batch gain is that a grid cell vectorises, where H3 has no vectorised form. Selectivity holds because the cells are exact: computed from the truncated integer coordinates the kernel reads, each owns its north and east edges, which is the kernel's own convention — a polygon contains a point on its east or north boundary, never its west or south — so the zone across an edge is not a candidate. Alignment then pays most on the 7.5° meridians the ocean zones share: unaligned twins of the same size test 17–24 % more polygons per random query.
  * **What it trades away, measured: nothing on the axes the resolution decision used.** `TimezoneFinderL` answers move cell by cell, because its fallback zone belongs to a cell; its agreement with the full lookup rises above the shipped index's with the equal-area grid and stays within 0.6 points below it with the equal-angle ones. The shipped index owes its one-point lead in that agreement on random points to the converter's work optimizer, which is H3-specific today; on the query itself the optimizer is within noise (−1 to −2 %, unresolved). Dropping `h3` saves its ~20 ms import and 2.3 MB install only once the converter and `timezonefinder/_data_integrity.py` stop using it too.
  * **Unpriced:** loading and construction time, `make memory`, the page residency of a mapped dense table (H3's must be expanded when loaded, a grid's need not be), a second machine class, and a rectangle port of the work optimizer. None of them can reverse the scalar or batch result; `make memory` and the page residency set how large the memory win is.
  * **The exactness rests on the kernel's edge convention, so an adoption pins it with a test.** A kernel change that moved boundary points to the other polygon would make aligned cells misanswer one-unit strips along every aligned border while every sampled test still passed. The gate found no disagreement with the control on 30,000 fixture points, on points on and beside each candidate's edges, or on the 7.5° and whole-degree lines borders follow, on both kernels; that includes the 289 fixture points lying in two overlapping zones, so each candidate's per-cell order picked H3's winner there too. The only disagreements were points on the −180° meridian and the −90° parallel, which no polygon owns, so both indexes answer the "last remaining zone" fallback there. Every candidate offers the Strait of Malacca witness's polygon.

- **Refused in the same measurement, as replacements for this package's Python reader:**
  * **Quadtrees**, both `node-geo-tz`'s world quadrants and the same under 7.5° root cells. They buy the most selectivity per byte: the rooted one at depth 5 tests 57 % and 42 % fewer polygons per random and on-land query at 757 KB. But a leaf is found by a `bisect` over a mapped key array, which costs more than the H3 call it would replace: scalar calls are 8–52 % slower, with one configuration unresolved, while batches gain as much as the grids' do. The refusal is of this reader's scalar path, not of quadtrees for a native one.
  * **`tzf-rs`'s tile pyramid**, exact Web Mercator tiles at zooms 3–10 or 3–11 probed coarsest first over a 1° candidate grid. One binary search per zoom makes scalar calls 2.4–2.7x slower, and batches gain only 12–27 %. Mercator tile edges cannot follow the integer grid either, so its exact tiles are conservative.
  * **The two-tier split**, an exact one-zone layer in front of a coarse candidate grid. It is dominated by the single grid it splits: larger, and a third more polygons tested.
  * **Unaligned grids**, dominated by their aligned twins at equal size; and **grids larger than H3's file** (0.66–2.1 MB), which win more but break "replace, never add".
  * **Touch-inclusive cells.** Counting every polygon that touches a cell edge discards the alignment, and with grids sized to H3's padded slot table rather than its 288,122 cells, and per-row reads for uniform grids, a 2026-09-26 run priced the 0.5° grid 7–9 % slower than H3 per scalar call. Exact cells measure the same grid 14–26 % faster.
