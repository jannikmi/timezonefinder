# Data pipeline, format versioning, and release order

- `update_data.sh` downloads a timezone-boundary-builder release into `tmp/` and runs `scripts/file_converter.py`, which scales coordinates by 10^7 into int32. A data update releases the **separate `timezonefinder-data` distribution** and nothing else: `update_data.sh` sets that package's version from the tag it parsed and records the release in `packages/timezonefinder-data/README.md`. `timezonefinder`'s version and `CHANGELOG.rst` are not touched, and the tag namespace is `data-v*` — a bare version tag publishes the *code*
- **`update_data.sh` verifies the download and records what it verified, so a regeneration that skips the script leaves `DATA_SOURCE` describing the wrong release.** The archive is checked against the byte size and SHA-256 the GitHub release API publishes for that asset (`scripts/upstream_release.py`) and re-unpacked, both on every run — `tmp/` caches the download, never the unpacked GeoJSON, so nothing the converter reads predates the verification — and the verified digest is staged in `tmp/` and installed as the root `DATA_SOURCE` in the same step that writes `DATA_VERSION` — both stamps advance only after a successful parse, so a run that dies in between cannot leave them disagreeing. `tests/test_data_version.py` asserts the two name the same release — which is what catches data compiled by hand from an archive nobody checked
- **The packaged data is obtained, not committed.** `packages/timezonefinder-data/timezonefinder_data/data/` is git-ignored: a fresh clone has no dataset and `make bootstrap` fetches the `timezonefinder-data` release the workspace declares, digest-checked against what PyPI publishes for it. CI does the same through `.github/actions/obtain-data`, with one difference that is the whole reason the action exists — when `DATA_BUILD_RUN` names a run whose `artifact-data-wheel` carries the declared version, the dataset comes out of *that* wheel. It has to: a data update bumps the version to one PyPI will not have until the tag publishes, so on that pull request the published release is the dataset *before* the one under test, and `make bootstrap` alone would validate the wrong bytes and pass
- **A branch declaring a data version nobody has published yet has to carry its own binaries.** Every format change is in that position, and outside the update pipeline there is no run holding an `artifact-data-wheel` for it. Ignoring a path never affects files already in the index, so the answer is `git add -f packages/timezonefinder-data/timezonefinder_data/data` on that branch — CI then reads the tree exactly as it did before this rule existed, and the data release is built from it. Drop them again with `git rm -r --cached` in the first commit after that `data-v*` tag publishes, and say so in the pull request that adds them, because nothing else will
- **The data distribution's major version is `DATA_FORMAT_VERSION`** (`timezonefinder/configs.py`), and the root declares `timezonefinder-data>=…,<N+1`. Bumping either per-file layout version (`POLYGON_LAYOUT_VERSION`, `SHORTCUT_LAYOUT_VERSION`) obliges a `DATA_FORMAT_VERSION` bump — `tests/test_data_version.py` asserts the pairing, because nothing else would notice. A format change is therefore a **two-distribution, ordered release: publish the data first**, then the code requiring it, or `timezonefinder` is briefly uninstallable
- **An unreleased version bump is free to reuse, so format changes belong back to back.** The number identifies a *release*, not a change: while a `DATA_FORMAT_VERSION` bump sits unreleased on `master`, the next format change to land rides the same number and the ordered two-distribution release is paid once for both. The moment one format change lands, every other one is temporarily cheaper than its entry says, so take them consecutively and let them go out together. State in the pull request whether a bump is already pending. Regenerating packaged data is normal and needs no special permission, but it must not be incidental: copy the directory aside first (`cp -r packages/timezonefinder-data/timezonefinder_data/data tmp/data-before`) and check that `diff -rq tmp/data-before packages/timezonefinder-data/timezonefinder_data/data` lists only binaries the change had a reason to move — git no longer holds a baseline to diff against, so one has to be kept
- **Generators write to `scripts.configs.SOURCE_DATA_DIR`, never `DEFAULT_DATA_DIR`.** The latter now resolves to wherever `timezonefinder_data` is *installed*, which under a non-editable install is inside `site-packages` — and since `make parse` passes no paths, a converter defaulting to it would rewrite the installed wheel instead of the checkout
- Benchmark fixtures in `tests/fixtures/benchmarks/` are pinned to the `DATA_VERSION` they were generated against and the loader refuses mismatches. `make data` regenerates them; use `make benchmark-fixtures` only when just the fixtures need refreshing
- When modifying a FlatBuffers schema, delete previously generated binary artifacts so they regenerate consistently
- `.github/workflows/check_data_updates.yml` opens an update PR weekly when upstream has a new release; `release_data_update.yml` merges it and pushes the tag with a GitHub App token (the default `GITHUB_TOKEN` would not trigger `build.yml`)
- **One wheel per data release, built where the data was compiled.** `check_data_updates.yml` builds `timezonefinder-data` from its converter output, uploads it as `artifact-data-wheel` and records its run id in the root `DATA_BUILD_RUN`, which travels to the tag with the commit. `build.yml` and `publish_data.yml` both go through `.github/actions/obtain-data-wheel`, which downloads that artefact and falls back to building only when no recorded run offers one — the artefact expired, or the data was regenerated outside the pipeline, which `update_data.sh` makes visible by clearing the stamp. That fallback now bootstraps before it builds, since the tree it builds from carries no dataset, so it reproduces a *published* release exactly and refuses by name when the declared version is one PyPI does not have and the recorded run is gone. `.github/actions/obtain-data` reads the same artefact from the other end, for the dataset rather than the wheel. This is what keeps `publish_data.yml`'s stated invariant true: it does not re-validate the data because the update PR's matrix did, and that holds only while both read the same wheel. Do not add a second build; `tests/test_data_wheel_handoff.py` asserts there is exactly one, plus the action's fallback
