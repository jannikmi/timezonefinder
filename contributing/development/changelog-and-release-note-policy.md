# Changelog and release-note policy

Every change needs one changelog bullet, filed as a **fragment** rather than written into `CHANGELOG.rst`: a single `.rst` file under `changelog.d/user/` for a user-facing change or `changelog.d/internal/` for dev tooling / refactors / CI / test infrastructure. The directory decides the placement, so no fragment says where it goes and no two concurrent changes edit the same lines — which is the whole reason the unreleased section is no longer written directly. This is easy to forget for changes that don't touch `timezonefinder/` at all (docs, `scripts/`, CI config, fixtures); those still need one.

A fragment holds the bullet text only, on one line, without the leading `* `; the filename is a kebab-case slug describing the change, unique across both directories. `make changelog` previews the assembled section and `tests/test_changelog_fragments.py` runs the same validation, so a malformed fragment fails CI rather than a release. `changelog.d/README.md` carries the mechanics. **Never edit the `X.X.X (unreleased)` section of `CHANGELOG.rst` directly** — the release assembles it from the fragments (`make changelog-assemble`) and then curates it. Everything below about *what* earns a bullet and how it is written applies unchanged to the fragment's text.

**Exception: the contributor-memory layer gets no entry at all, not even an `Internal:` one — and therefore no fragment.** That is `CONTRIBUTING.md`, the pointer stubs, provider workflow adapters, everything under `contributing/`, and tests whose only subject is the memory graph or improvement-register structure. None of it ships or changes package behaviour, and the register lists work *not* done. `Internal:` remains the user's changelog. A change touching memory and something else is not covered by the exception: describe the something else.

**Exception: refreshing a locked dependency version gets no entry either, in neither list.** `uv.lock` and the pre-commit hook revisions record which versions this checkout resolves; they are not what a `pip install timezonefinder` gets, and "the locked *X* moves from *A* to *B*" tells a reader nothing they can act on. Bumping them is routine maintenance, and a changelog that logs it buries the changes that are not. What *does* get an entry is a change to the **published** dependency metadata — `[project] dependencies` and `[project.optional-dependencies]`, the constraints that ship in the wheel and that every install inherits — described by what it means for installing the package, not by which line of `pyproject.toml` moved. A lock bump taken deliberately to unblock something still gets no entry: record that reasoning at the decision site or in the improvement register, which is where the next contributor looks for it.

The changelog is read by users, not by reviewers of the PR that produced it. Describe the **end state**, never the path taken to it:

- **Amend, don't append.** When a follow-up commit, review round, or fix changes something already described, edit that fragment so it describes where the code landed — a second fragment correcting the first is the same failure as a second bullet. Adding a second bullet that corrects, tunes, or extends the first one is what makes the section unreadable — a released version should read as if the feature arrived in one step.
- **One bullet per user-visible change**, not per commit or per PR. A feature delivered over several commits (with its tests, docs, CI wiring and follow-up tuning) is one fragment.
- Keep the *why* only when it's decision-relevant for a reader — a deliberate trade-off, a non-obvious constraint, a gotcha. Drop tuning history ("raised from X to Y, then to Z" → state the final value), superseded intermediate states, and self-review narration.
- Keep bullets to a few sentences. Details that belong to contributors, not users, go in the narrow contributor-memory module or a docstring, and the bullet points there.
- Before finishing a task, re-read `make changelog`: if two bullets describe the same feature, merge them into one fragment.
- **Remember to acknowledge outside contributions**, in the form the existing `Thanks to …` bullets use. Credit the contributor's own PR, which is not the maintainer PR that superseded it.
