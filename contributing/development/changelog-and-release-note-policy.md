# Changelog and release-note policy

Every atomic change needs its own changelog bullet, filed as a **fragment** rather than written into `CHANGELOG.rst`: a single `.rst` file under the matching `changelog.d/breaking-changes/`, `new-features/`, `changed/`, `bug-fixes/`, `documentation/`, or `internal/` directory. “Atomic” means a reader can understand, assess, and locate the change without also understanding another outcome that happened to ship in the same pull request or commit. One pull request may therefore owe several fragments. Supporting implementation, tests, and documentation stay with the behavior or tooling change they support; they are not separate outcomes. The directory decides placement, so no fragment says where it goes and no two concurrent pull requests touch the same lines — which is the whole reason the unreleased section is no longer written directly. This is easy to forget for changes that don't touch `timezonefinder/` at all (docs, `scripts/`, CI config, fixtures); those still need one.

A fragment holds the bullet text only, on one line, without the leading `* `; the filename is a kebab-case slug describing the change, unique across all section directories. `make changelog` previews the grouped section and `tests/test_changelog_fragments.py` runs the same validation, so a malformed or unclassified fragment fails CI rather than a release. `changelog.d/README.md` carries the mechanics. **Do not add a pending section to `CHANGELOG.rst` while filing a change** — the release generates `X.X.X (unreleased)` from the fragments with `make changelog-assemble`, then curates wording, atomicity, duplicates, and omissions within that temporary structure before dating it. Between releases, `CHANGELOG.rst` contains released history only. Everything below about *what* earns a bullet and how it is written applies unchanged to the fragment's text.

**Exception: the contributor-memory layer gets no entry at all, not even an `Internal:` one — and therefore no fragment.** That is `CONTRIBUTING.md`, the pointer stubs, provider workflow adapters, everything under `contributing/` and `prototypes/`, and tests whose only subject is the memory graph, the improvement-register structure, or a prototype. None of it ships or changes package behaviour, and the register lists work *not* done. `Internal:` remains the user's changelog. A change touching memory and something else is not covered by the exception: describe the something else.

**`prototypes/` joined that layer on 2026-09-07, decided by the maintainer.** It had been the one contributor-only tree owing fragments, and the asymmetry was an accident of the exception being written as a list of paths rather than as a rule: `MANIFEST.in` excludes `prototypes/` from the sdist in the same block as `contributing/`, `CLAUDE.md` and `AGENTS.md`, nothing there is imported by a packaged module, and a study is a record of *how a decision was reached* — which is the register's subject, not the changelog's. A reader of `Internal:` cannot act on a correction to an exploratory script's `FINDINGS` block. The test clause widens with it, because a test whose only subject is a prototype cannot owe an entry that the prototype itself does not: `tests/test_query_stage_profile.py` is the one that exists.

**Exception: refreshing a locked dependency version gets no entry either, in neither list.** `uv.lock` and the pre-commit hook revisions record which versions this checkout resolves; they are not what a `pip install timezonefinder` gets, and "the locked *X* moves from *A* to *B*" tells a reader nothing they can act on. Bumping them is routine maintenance, and a changelog that logs it buries the changes that are not. What *does* get an entry is a change to the **published** dependency metadata — `[project] dependencies` and `[project.optional-dependencies]`, the constraints that ship in the wheel and that every install inherits — described by what it means for installing the package, not by which line of `pyproject.toml` moved. A lock bump taken deliberately to unblock something still gets no entry: record that reasoning at the decision site or in the improvement register, which is where the next contributor looks for it.

The changelog is read by users, not by reviewers of the PR that produced it. Describe the **end state**, never the path taken to it:

- **Amend corrections; split independent outcomes.** When a follow-up commit, review round, or fix changes an outcome already described, edit that fragment so it describes where the change landed. When it adds another independently understandable behavior, tool, contract, or migration step, give that outcome its own fragment even if both shipped in one pull request. A released version should read as final atomic changes, not as commit history or a bundled PR summary.
- **One bullet per atomic change**, not per commit or per pull request. A single behavior delivered over several commits keeps its tests, documentation, and CI wiring in one fragment. A pull request delivering several behaviors gets several fragments. If a bullet needs “separately”, “also”, or an unrelated semicolon to introduce another result, split it.
- **Do not report performance changes in the changelog.** No benchmark numbers, speedup or slowdown claims, memory deltas, throughput claims, or qualitative “faster”/“smaller” summaries belong here. The generated benchmark, latency, memory, comparison, and data reports are the retrospective record and name their measured configuration. A changelog bullet may describe the mechanism or compatibility consequence of performance-motivated work, but must leave its measured effect to those reports.
- Classify each fragment when authoring it; assembly groups the six directories as ``Breaking changes:``, ``New features:``, ``Changed:``, ``Bug fixes:``, ``Documentation:``, and ``Internal:``, omitting empty groups. Do not postpone classification until release curation or repeat a group's label inside its bullets. Apply release-section restructuring only to the release being prepared; do not restyle historical entries for consistency.
- Keep the *why* only when it is decision-relevant for a reader — a deliberate compatibility trade-off, a non-obvious constraint, or a migration gotcha. Drop tuning history, superseded intermediate states, and self-review narration.
- Keep bullets to a few sentences. Details that belong to contributors, not users, go in the narrow contributor-memory module or a docstring, and the bullet points there.
- Before finishing a task, re-read `make changelog`: merge duplicate descriptions of one atomic change, split bullets containing independent outcomes, and remove performance claims.
- **Remember to acknowledge outside contributions**, in the form the existing `Thanks to …` bullets use. Credit the contributor's own PR, which is not the maintainer PR that superseded it.
