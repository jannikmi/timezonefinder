# Documentation maintenance rules

Rules for what documentation prose may say and how it stays true. Markup validity, links, the docs toctrees and generated report pages are in [documentation markup, links and generated pages](documentation-markup-links-and-generated-pages.md).

- **`docs/` is for people using the library; maintenance procedure belongs in `contributing/`.** A docs page may explain how a number is measured, what it means and how to reproduce it. When to re-run a check, what enforces it, how to record a result, and mechanisms tried and dropped go in the matching `contributing/development/` file, which links the docs section. The test for a sentence is who would act on it: if only a maintainer would, it is in the wrong tree.
- **Write `docs/` for a downstream reader and keep it short.** A page says what a feature or number means, how to use or reproduce it, and what it does not tell you - enough for a user to act, and no more. How it is implemented, why a constant has its value, the measurements a design was chosen on and the alternatives it beat belong at the decision site in code, where the next contributor looks, and a page that restates them grows until no user reads it. Name the script or constant that holds the detail instead of paraphrasing it. A page that needs more than a few short sections to explain one topic is usually explaining the implementation.
- **A docs page describes the package as it is, never as it changed.** A reader of `docs/` has no access to a superseded design, so a sentence comparing the current one to it ("the envelope used to be derived from a spherical cap", "through release 9.0.0 the prologue was the H3 call") carries nothing they can act on and goes stale on the next change. Say why the thing is what it is, in the present tense, and name the property the explanation rests on rather than the alternative it replaced. The one place a release-to-release difference belongs is [the changelog](changelog-and-release-note-policy.md): a page describing what can move an answer points there for which release moved which, instead of restating it. State a mechanism over the property it actually depends on, too — candidate order follows from cell *size*, so writing it as a consequence of cell *shape* is wrong the moment the shape changes again
- **Four passages are duplicated on purpose — edit every copy or they drift.** The badge block lives in `README.md` and `docs/badges.rst` because the docs `include` it and an `include` does not render on PyPI; the two are in different markups, so a badge is re-spelled rather than copied between them. The *How it works* summary — the lookup pipeline, the no-simplification trade-off, the ocean-zone consequence for `timezone_at()` — lives in `README.md` *and* `docs/index.rst`, because both are front doors reached without going through the other, with `docs/architecture.rst` holding the long form. A change to the lookup flow (the shortcut index's cells, holes-before-outer-ring, the unique-cell short-circuit) has to land in all three. The `LICENSE` section — the MIT/ODbL split and the `timezone-boundary-builder` attribution — is the third, in `README.md` and `docs/3_about.rst`, because a reader deciding whether they may redistribute the data reaches one page or the other and neither can defer to the other: the README is the PyPI long description, and a docs page that only linked out for its license would be the one page a reader came for. A change to either license, or to the upstream dataset the data follows, lands in both. The *Used by* section — the most-downloaded claim, the named dependents and the citation pointer — is the fourth, in `README.md` and `docs/3_about.rst`, for the same reason as the license: it is social proof a PyPI reader and a docs reader each reach without the other. It states magnitudes only ("thousands of repositories"), never a count, and every name in it must be checkable against the dependent's own manifest; [recheck the adoption claims](../workflows/recheck-the-adoption-claims.md) runs over both copies before each release. A copy this list does not declare drifts, because nothing sends a reader to it. Prefer deleting a copy to declaring it; declare only the ones that cannot be deleted. All four are deliberate exceptions to the [core contract](../core-contributor-contract.md)'s rule against copying a rule to make it more visible
- **Never copy an exact measured figure into hand-written prose** — whether it comes from a generated page, a measurement artifact, a local run or a pull-request description. That means counts and sizes (vertices, polygons, bytes, MiB), rates (queries/s, speed-ups, win rates), affected-cell counts and a run's data version. A re-run updates the source and silently leaves every copy wrong, and a copy spreads: one figure quoted in prose is typically quoted in three more places before anyone re-measures. The enumeration above is exhaustive on purpose — a figure from a measurement artifact or a local run is a measured figure, and a rule naming only generated pages reads as permitting the others. State a magnitude that survives a data update ("single-digit MiB", "hundreds of thousands of queries/s") and link where the current number lives — the generated page, or the committed artifact recording the run. A section on a measurement method describes the method and links its result. Exact figures belong in dated records: register items, changelog fragments and pull-request bodies. Figures fixed by a constant rather than by the data are fine to state exactly — `~1 cm` resolution follows from `COORD2INT_FACTOR`, and every cell count and cell size in the shortcut index from `ROOT_COLUMNS`, `ROOT_ROWS` and `BLOCK_SIDE`
- **A zone name in a snippet is example output, not a constant** — `tz = timezone_at(...)  # 'Europe/Berlin'`. It is an answer from the packaged dataset, so a data update can change it, and a comment copied from a page written against a different dataset is wrong on arrival with nothing to catch it. The dataset to watch for is the *reduced* `timezones-now` set, whose answer at a given coordinate is often a neighbouring zone rather than the shipped one, and such a comment spreads by being copied from one snippet to the next. Run the lookup against the packaged data and paste what it returns
- **Prose that paraphrases a machine-readable file goes stale silently**, because the file changes and nothing re-reads the prose. Three such pairs exist deliberately, each because the reasoning is worth more than the indirection:
  - `docs/0_getting_started.rst` names the runtime dependencies → `[project] dependencies` in `pyproject.toml`. Names only, on purpose: version bounds stay in `pyproject.toml`, so a bump cannot falsify the page, but adding or dropping a dependency does
  - `docs/architecture.rst` *How it ships* → `.github/workflows/build.yml`, `[tool.cibuildwheel.*]` and `setup.py`. Changing the wheel targets, the abi3 base interpreter, the `abi3audit` repair step, what the end-to-end job asserts, or the on-master check changes what that section claims
  - `docs/result_stability.rst` → the safety gate documented at the top of `scripts/shortcut_ordering.py`, `TimezoneFinder._zone_id_among`, `TimezoneFinder.timezones_at` and `TimezoneFinderL._fallback_zone_of`. **The lookup is order-sensitive and the page's stability guarantee is the converter's, not the query's**: `_zone_id_among` returns the first candidate containing the point and, past `stop_index_of`, returns the final zone *without any test*, so candidate order decides the answer for a point inside two zones' polygons and for one inside none of a cell's candidates. What the page promises users is that a regenerated index cannot move a `TimezoneFinder` answer, and the only thing making that true is the gate refusing a final-zone change or cross-zone interleaving unless it certifies cell coverage and the absence of cross-zone positive-area overlap. Widening when that is permitted, or making either method consult the order differently, falsifies a published guarantee - `tests/test_ordering_answer_invariance.py` fails on the runtime half of it (mutating the stop index or the untested tail is caught), and `tests/test_shortcut_ordering.py` on the converter half, but nothing asserts that a positive gate verdict is *correct*, so widening the gate's own conditions is the change that can still move answers with every test green. Such a change is also user-visible and owes a changelog bullet for its compatibility consequence rather than an `internal/` one — reordering candidates, or changing which cells the index is made of, changes what `TimezoneFinderL` returns in a multi-zone cell, and a user pinning that answer has no other way to learn it moved
  - `prototypes/README.md` → one row per script in `prototypes/`. When you touch one side, re-read the other. Describing *why* a choice was made survives longer than restating *what* the file says — prefer it. **The trigger that gets missed is the opposite one**: a study's row and its `FINDINGS` block go stale when the work they recommended *ships*, not when the script changes, so the pull request that lands a prototype's conclusion — or retires the item carrying it — is the one that owes the re-read. **A study of something the package no longer has is deleted in the pull request that replaces it, never kept as legacy**, together with its row and every dependency only it needed (a `proto` group entry included): move what stops a re-proposal into the matching decision file first, and port a study that still prices a live question so its control is the shipped structure. A prototype kept runnable against a retired structure is legacy code with a maintenance bill and no reader. `tests/test_contributor_memory.py` checks that page's links and line breaks; nothing checks whether its claims are still true

Update README and docs for behavior, flags, datasets, and internal tooling; file the matching changelog fragment under `changelog.d/documentation/`, or under another section when documentation supports that change rather than being the outcome. A purely cosmetic docs change — a moved or retitled section, a typo, a repointed cross-reference, an acknowledgement — owes no fragment at all; the [changelog policy](changelog-and-release-note-policy.md) states that exception. Keep comments concise around geometry, tolerances, and shortcuts.

For a data update, document the upstream boundary release. `update_data.sh` releases only `timezonefinder-data`, records its version in `packages/timezonefinder-data/README.md`, regenerates fixtures, and runs `make reports`; it does not change `timezonefinder`'s version or changelog. Any other fixture regeneration requires `make benchmark-fixtures` then `make reports`. `make parse` and `make testparse` change neither data version nor fixtures; `make parse` does rewrite `docs/data_report.rst`, because it compiles the packaged directory that page describes, while `make testparse` leaves the checkout clean — the converter writes its report beside the binaries it compiled.

Re-read the paired prose when changing the lookup flow (README, `docs/index.rst`, `docs/architecture.rst`), project dependencies (`docs/0_getting_started.rst`), build/ABI configuration or test matrix (`docs/architecture.rst`), docs headings (README anchors), prototype scripts (`prototypes/README.md`), or packaged data (example-output comments in README and docs).
