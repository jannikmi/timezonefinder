# Designing a candidate comparison

Comparing two *candidate* implementations of one stage - or one implementation across two environments - is a different measurement from the suites in [benchmarking and performance validation](benchmarking-and-performance-validation.md), which compare one implementation across commits or machines.

Hand-rolled designs for it have produced wrong answers here, all of them flattering the newer candidate; `benchmarks/candidate_comparison.py`'s docstring records those failures.

- **Use `benchmarks/candidate_comparison.py`'s `compare_candidates` instead of writing the harness again.** Pass two named callables that each perform the *whole public call* for one input, never the stage in isolation; the harness alternates their order round by round, samples inputs at random, and reports `unresolved` when its two estimators disagree rather than the one that shows an effect.
- **Sweeping a parameter is a ladder of paired comparisons, and four of its failure modes are not obvious.** `scripts/measure_batch_break_even.py` is the worked example and carries the reasoning at each constant.
  1. **Hold the work per round constant across rungs** and normalise by what a round actually answered, not by the nominal target: a fixed call count per round puts the smallest and largest rungs in different measurement regimes and plots them as one curve. Only a top rung that would get fewer than `MIN_CALLS_PER_ROUND` calls gets more points per round (`points_per_round_for`); a longer round can only bias it slower.
  2. **Draw the samples within one batch without replacement**: a repeated coordinate is answered from the batch's own cell lookup, which fakes exactly the amortisation curve being measured. Cap the ladder at half the pool, since one possible batch is not sampling, and when that cap ends the ladder too early, extend the pool from the fixture generator's own sampler and classification rule rather than enlarging the committed fixtures, which feed every tracked benchmark.
  3. **`compare_candidates` charges a fixed cost per timed item**, which a per-point normalisation spreads as `h/N`. It puts a real 1/N ramp into the smallest rungs of a curve that should be flat, so a control statistic over the rungs must exclude them (`CONTROL_MIN_BATCH_SIZE`).
  4. **A saturation point is read from rungs beyond it**, so the ladder must run past the plateau, and a curve that turns slower again (the batch outgrowing the cache) has stopped improving too. Pay for the top rungs by thinning the bottom ones: with constant work per round, a rung near N=1 costs a whole batched call per point.
- **Read a saturation point off the absolute quantity and a crossing off the ratio; they are not interchangeable, and they do not survive a noisy machine equally well.** Whether a bigger batch still buys anything is a property of the batched side alone, and the speed-up ratio mixes in the scalar baseline's noise. A crossing is a comparison, so it comes from the within-rung ratio, where drift over the run cancels. **Gate the absolute-quantity claim on the control rather than publishing it unconditionally:** repeat runs of one sweep moved saturation by a factor of two and then off the ladder as the control spread grew from 5 % to 22 %, while the crossing did not move. Withhold the figure from a run whose control failed and say so; more rounds do not fix drift.
- **A sweep's pull request commits its code and its qualitative findings, never its measurements.** The prototype's `FINDINGS` and the matching decision file say which candidate wins, against what, on which hardware class, and the mechanism that makes it win; the sweep's own commands re-derive the numbers. No stage output is committed and no exact figure is quoted, including timings no machine reproduces identically - stricter than [contributor memory's rule for figures](../contributor-memory-rules.md), which keeps a hard-to-reproduce one. A side question a run answers with a refusal goes into the decision file as that refusal, not into the pull request as a second study. Read the diff stat before opening the pull request: committed run output, or a script far larger than its question, is the bloat this keeps out.
- **Committed report charts are drawn with matplotlib or seaborn, by the renderer, from stored JSON** (`scripts/batch_break_even_chart.py` and `scripts/measure_tzfpy_agreement.py`, using the `benchmark` dependency group). Use seaborn when its long-form data and semantic grouping remove real plotting machinery; direct matplotlib is enough for a small fixed-series chart. The group is deliberately outside `test` and outside `$(BENCHMARK_ENV)` so no measured process ever imports the plotting stack; chart tests skip in those environments and run together in tox's `charts` environment. matplotlib's SVG writer is not deterministic by default and a committed chart that churns on every render hides the numbers that moved: set `svg.hashsalt` (ids are otherwise salted from `uuid4`), `svg.fonttype="none"` (glyphs are otherwise machine-dependent path outlines) and `savefig(metadata={"Date": None})`, and pin a matplotlib *ceiling* as well as a floor. Pin every committed chart byte for byte to its stored input in a test.
- **A pair that would have to cross a process is not a pair — measure each pair in one process and refuse the ratio that cannot be.** Alternating order, one shared draw and a round-level win count are properties of one loop holding both candidates; across processes only the best-round ratio survives, which is the estimator the harness exists to avoid. `make acceleration-paths` is the shape to copy: Numba and pure Python are one source decorated or not, so each is compared *in its own environment* against the C extension both environments hold, and the Numba-against-pure-Python ratio is not computed. The shared C-extension baseline is published as the reader's comparability check, not used as a gate.
- **Never state which acceleration path is fastest anywhere but the generated page.** Prose tends to read a dispatch rule as a speed claim and copy a figure that later stops matching anything measurable. The ranking moves with the kernels and the data format and differs across workloads, since a query the shortcut index answers reaches no kernel at all. `docs/benchmark_results_acceleration_paths.rst` states it, `make acceleration-paths` regenerates it, and prose and code comments elsewhere point there instead of quoting it.
- **A process that merely has Numba installed is not the configuration a plain install runs**, because `benchmarks/test_inside_polygon.py`'s `*_python` rows time `utils_numba` directly and are JIT-compiled there, under node ids the trend chart joins on. That is what `--expect-interpreted python` refuses for every tracked measurement. **Name a measurement's path by the binding, and its environment by `utils_numba.using_numba`:** `TimezoneFinder.using_numba()` answers the binding (false wherever the extension won), so a report asking whether numba is installed asks the module, and labels read `using_clang_pip` first, since reading the numba flag first mislabels clang runs. **Costs a process pays once before either candidate runs cannot be paired**, so `scripts/_startup_probe.py` measures a cold process per environment and the page states the difference. Two traps: the kernels compile when `utils_numba.py` is imported (eager signatures), which constructing a finder triggers, not in the first query; and `cache=True` makes only the first process in a fresh environment compile, so report a median over repetitions and say the steady state is what is published.
