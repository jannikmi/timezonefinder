**lookups are faster, and most of it lands on installs that have Numba.** ``is_valid_lat``, ``is_valid_lng`` and ``coord2int`` were compiled with ``numba``, and each takes one number and performs one operation - so the dispatch cost about twice what the body did, on stages that run on every query. They are ordinary Python functions now. A plain ``pip install`` never paid that dispatch, so on it these three change nothing; with Numba installed, coordinate validation falls from 270 ns to 212, which is what it already cost without it. Separately and on both, a cell's candidate polygons had their zone ids gathered into a NumPy array before any point was tested, only to read one element of it - the lookup reads that element directly. Measured as a paired A/B inside one process with the rounds alternated, 2,500 committed fixture points per round and the minimum over 25 rounds, winning every round except where noted: with Numba, ``timezone_at`` is **11.2 % faster on uniformly random points**, 13.0 % on on-land points, 16.3 % on points that reach the polygon tests and 7.4 % on points a single zone's H3 cell answers; on the C extension the same four are 4.7, 8.3 and 15.2 %, and unchanged on the last, which reaches neither the gather nor a dispatch. The batch lookups gain 5.5-7.5 %. Every coordinate gets the same answer as before, and no public method or signature moves. One behaviour difference is a fix: ``coord2int`` no longer wraps silently into 32 bits under Numba for a value outside the valid coordinate range, which is what the no-Numba path always did.
