New page `Result stability and reproducibility <https://timezonefinder.readthedocs.io/en/latest/result_stability.html>`__: a lookup is a pure function of the coordinates and the installed data, which leaves two axes that can still move an answer. A ``timezonefinder-data`` update can change it through boundary geometry, polygon precedence at shared borders, or shortcut composition and ordering; a code release can change it through a bug fix, a documented semantic change, or an optimization of the query logic - 9.0.0's candidate reordering changed what ``TimezoneFinderL`` returns in a multi-zone cell. A point strictly inside exactly one polygon is decided by geometry alone and none of it reaches that point. ``timezonefinder-data`` versions read ``<format>.<year>.<letter>[.postN]`` and are not semantic versions: no data bump promises unchanged answers, dataset changes reach an unpinned install without a code release, and the code changelog does not record them. Pinning the data freezes the artefacts and pinning the code freezes the rules that read them, so reproducibility across deployments needs both.
