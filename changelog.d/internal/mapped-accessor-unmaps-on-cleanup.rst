``FileCoordAccessor.cleanup()`` drops its own whole-file word view of the mapping before it attempts ``mmap.close()``, so the close succeeds rather than being refused by that view and swallowed as a ``BufferError`` on every teardown - which deferred the unmapping to whenever the accessor happened to be collected, in the mode that exists so the coordinate data need not be resident. A view a *caller* still holds refuses the close as before, which is the case the suppression exists for and the only one left. No lookup code moved and no public teardown path reaches this yet, so nothing a user calls behaves differently.
