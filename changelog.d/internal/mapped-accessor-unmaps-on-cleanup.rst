``FileCoordAccessor.cleanup()`` drops its own whole-file word view of the mapping before it attempts ``mmap.close()``, so an accessor cleaned up on its own unmaps there and then instead of having its close refused by that view and swallowed as a ``BufferError`` - which deferred the unmapping to whenever the accessor happened to be collected, in the mode that exists so the coordinate data need not be resident. Any view a *caller* holds still refuses the close, which is the case the suppression exists for: an accessor owned by a ``PolygonArray`` is one, since the wrapped kernel buffers export the same words, and there ``PolygonArray.__del__`` is what orders the release. No lookup code moved and no public teardown path reaches this yet, so nothing a user calls behaves differently.
