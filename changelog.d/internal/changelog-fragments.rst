The directory - ``user/`` or ``internal/`` - carries the placement, so no two concurrent pull requests touch the same lines of the last file every non-exempt change had to edit. ``scripts/changelog_fragments.py`` validates them (classification, kebab-case names, one bullet on one line, unique slugs, deterministic order), previews the assembled section, and folds them into the changelog at release time - which ``make release`` and the release job both refuse to skip, since a fragment surviving the tag is a change published with no entry in ``CHANGELOG.rst`` and none in the distribution either; assembly is additive, so existing bullets are never rewritten and the release's end-state rewrite stays the deliberate act the changelog policy describes. ``CHANGELOG.rst`` remains the published artifact, so nothing about installing or reading the package changes
