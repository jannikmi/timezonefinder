The compiled C extension is now the point-in-polygon implementation wherever it loaded, and the optional ``numba`` extra is the fallback for an installation that has none - an ordering `the acceleration path comparison <https://timezonefinder.readthedocs.io/en/latest/benchmark_results_acceleration_paths.html>`__ measures backwards the other way round, with the JIT kernel slower than the extension on every polygon size and never faster on a whole lookup. **Numba is no longer imported at all where the extension answers queries**: ``timezonefinder.utils`` imports ``timezonefinder.utils_numba`` only in the branch a missing extension takes, since that import is what compiles it, so an installation carrying both now holds the resident memory and the start-up time of a plain install rather than ~100 MiB and a compilation more. The coordinate converters that module used to supply (``int2coord``, ``convert2coords``, ``convert2coord_pairs``) are NumPy implementations in ``timezonefinder.utils`` now, returning exactly what they returned before. ``TimezoneFinder.using_numba()`` consequently reports whether the JIT kernel is what a lookup *runs*, which is ``False`` on an installation whose extension loaded however Numba is installed; ``TimezoneFinder.using_clang_pip()`` is unchanged, and the two are mutually exclusive again.
