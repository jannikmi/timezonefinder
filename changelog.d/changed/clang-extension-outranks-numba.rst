The compiled C extension is now the point-in-polygon implementation wherever it loaded, and the optional ``numba`` extra is the fallback for an installation that has none. Until now Numba took precedence whenever it was importable - an ordering that predates both the C extension and the packed payload the kernels read today, and that `the acceleration path comparison <https://timezonefinder.readthedocs.io/en/latest/benchmark_results_acceleration_paths.html>`__ has since measured backwards: the JIT kernel is slower than the extension on every polygon size and never faster on a whole lookup. An installation holding both therefore gets the faster kernel without reinstalling anything, and the extra keeps serving the case it was always needed for, where no compiler is available and its rival is the pure-Python fallback. ``TimezoneFinder.using_numba()`` is unchanged in meaning - Numba is imported and compiling this process's helper functions - but it no longer implies that a lookup runs the JIT kernel: ``TimezoneFinder.using_clang_pip()`` is what answers that, and on an installation with both, both are now ``True``.
