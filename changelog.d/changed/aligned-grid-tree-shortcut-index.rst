The shortcut index is now a longitude/latitude-aligned grid tree instead of an H3 hexagon grid: 0.9375° cells, each refining into a 4×4 block of 0.234375° cells where several zones meet. The cell is two integer divisions per level rather than a library call, so it vectorises over a batch, and the cells are exact in the coordinate frame the point-in-polygon kernel reads, so a zone whose polygons only reach across a cell edge is no longer a candidate inside it. Random ``timezone_at()`` lookups measured ~1.5x faster and ``timezone_ids_at()`` batches 5x on uniformly random points and ~25x where a single zone covers the cell, against a 20 % smaller index on disk and half the resident index arrays; ``TimezoneFinderL``'s footprint roughly halves. ``TimezoneFinder`` answers are essentially unchanged: 200,000 area-weighted random points, 14,742 points inside two overlapping zones, both poles and both antimeridian spellings answer exactly as before, and over all 4,113,237 distinct stored boundary vertices 18 answers move. Those 18 are the two cases where candidate order decides rather than geometry, and the legacy order is per cell: 17 are points inside no polygon at all - slivers on the 7.5° meridians where the ocean zones meet, where ``timezone_at()`` returns the final candidate untested and never promised otherwise - and one is a point inside both ``Australia/Brisbane`` and ``Etc/GMT-9``, where the first containing candidate wins and both answers are equally truthful. ``TimezoneFinderL`` is an approximation *by cell*, so its answers move wherever a cell does, and it now agrees with the full lookup more often. This is a binary format change: ``DATA_FORMAT_VERSION`` is 4 and the required ``timezonefinder-data`` floor moves with it.
